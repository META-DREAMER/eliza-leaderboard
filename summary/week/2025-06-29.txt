## 🎯 Summary

Currently, the CLI uses a mix of input libraries (`inquirer`, Bun's global `prompt()`, and `@clack/prompts`). We should standardize on `@clack/prompts` for a consistent user experience and better styling across all CLI interactions.

## 📋 Current State

Most of the CLI already uses `@clack/prompts` properly, but there are **2 main files** still using other input methods:

### 1. `src/utils/plugin-creator.ts` - Using `inquirer` 📦

This file has multiple `inquirer.prompt()` calls that need to be migrated:

- **Plugin specification collection** (~line 172-290):
  - Plugin name input
  - Plugin description input  
  - Plugin features input
  - Component selection (checkbox)
  - Action names input
  - Provider names input
  - Evaluator names input
  - Service names input

### 2. `scripts/generate-unit-tests.ts` - Using global `prompt()` 🔧

- **Test generation confirmation** (~line 165):
  ```typescript
  const answer = prompt('Generate tests? (y/n): ');
  ```

## ✨ Benefits of Migration

1. **Consistent UX** - All CLI interactions will have the same look and feel
2. **Better styling** - Clack provides superior visual design and animations
3. **Better error handling** - Clack has built-in cancellation handling
4. **Reduced dependencies** - Can remove `inquirer` from package.json
5. **Type safety** - Better TypeScript integration

## 🔧 Implementation Examples

### For `plugin-creator.ts`:

**Before (inquirer):**
```typescript
const answers = await inquirer.prompt([
  {
    type: 'input',
    name: 'name',
    message: 'Plugin name (without "plugin-" prefix):',
    validate: (input: string) => input.length > 0 || 'Plugin name is required'
  }
]);
```

**After (clack):**
```typescript
const name = await clack.text({
  message: 'Plugin name (without "plugin-" prefix):',
  validate: (input) => input.length > 0 ? undefined : 'Plugin name is required'
});

if (clack.isCancel(name)) {
  clack.cancel('Operation cancelled.');
  process.exit(0);
}
```

### For `generate-unit-tests.ts`:

**Before:**
```typescript
const answer = prompt('Generate tests? (y/n): ');
```

**After:**
```typescript
const answer = await clack.confirm({
  message: 'Generate tests?',
  initialValue: true
});

if (clack.isCancel(answer)) {
  console.log('Cancelled.');
  return;
}
```

export function looksLikeBase64(content?: string | null): boolean {
  if (!content || content.length === 0) return false;

  const cleanContent = content.replace(/\s/g, '');

  // Too short to be meaningful Base64
  if (cleanContent.length < 16) return false;

  // Must be divisible by 4
  if (cleanContent.length % 4 !== 0) return false;

  // Check for Base64 pattern with proper padding
  const base64Regex = /^[A-Za-z0-9+/]*={0,2}$/;
  if (!base64Regex.test(cleanContent)) return false;

  // Additional heuristic: Base64 typically has a good mix of characters
  const hasNumbers = /\d/.test(cleanContent);
  const hasUpperCase = /[A-Z]/.test(cleanContent);
  const hasLowerCase = /[a-z]/.test(cleanContent);

  return (hasNumbers || hasUpperCase) && hasLowerCase;
}

## Problem

When ElizaOS is deployed in horizontally scaled environments (Kubernetes, server clusters), multiple instances starting simultaneously may attempt to run migrations at the same time, causing:
- Race conditions around table/constraint creation
- PostgreSQL errors such as "relation already exists"
- Partial or inconsistent schema state if migrations fail mid-way

## Solution

This PR introduces a robust migration locking mechanism that ensures only one instance can run migrations at a time:

### Key Features
- **PostgreSQL Advisory Locks**: Uses `pg_advisory_lock` for efficient, automatic cleanup
- **Fallback Table-Based Locking**: For databases without advisory lock support
- **Migration History Tracking**: Prevents re-running completed migrations
- **Stale Lock Cleanup**: Handles crashed processes gracefully
- **Configurable Timeout**: Default 60 seconds with automatic retry

### Implementation Details

1. **MigrationLockManager** class:
   - Acquires/releases locks using PostgreSQL advisory locks when available
   - Falls back to table-based locking for other databases
   - Tracks lock ownership with process info (PID@hostname)
   - Cleans up stale locks from crashed processes

2. **Migration History Table**:
   - Records all executed migrations with timestamps
   - Stores schema checksums to detect version changes
   - Tracks both successful and failed migrations

3. **Updated DatabaseMigrationService**:
   - Wraps all migration operations with lock acquisition
   - Ensures proper lock release even on failure
   - Works for both core system and plugin migrations
