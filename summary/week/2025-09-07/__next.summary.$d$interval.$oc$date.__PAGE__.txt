9:T87e,## Overview

In testing passing in calldata, we noticed that the `data` field was always `null` even though we were including it. When adding the changes to the `transferTemplate` to look for data, and also including it in the XML, we no longer saw it coming through as `null`. 

The template now properly extracts and passes through any provided data/calldata, and the extended type guard in `transfer.ts` addresses an edge case where data was sometimes sent as `'null'` which didn't trigger the initial default to `0x`.

## Changes

### Template Updates
Added support for data/calldata in the transfer template by adding:
- Instruction to extract "Additional data/calldata (if any is included)"
- XML response field `<data>string | null</data>`

Previously,  the `TransferParams` interface supported an optional data parameter but it seemed that not being included in the template meant it was always `null`, even when provided in the request.

These changes enable proper handling of transaction data in transfers while protecting against LLM response variations. The template now properly extracts and passes through any provided data/calldata, and the code safely normalizes edge cases to ensure valid transaction data.

The `bun.lock` change is from a fresh install of the repo.

**Note**: I tested this on version `1.0.6` but haven't been able to run `1.0.7` due to the character issue I filed on the main repo. Wanted to put up the PR in the meantime! Thank you -- greatly appreciate all the work ya'll are doing to transition!

### Type Guard Change to Handle Edge Case

Added additional defensive handling in `TransferAction` for LLM response edge cases:
```typescript
// Normalize empty or invalid data field to '0x'
if (!params.data || params.data === '0x') {
  params.data = '0x';
} else {
  // Handle case where template returns 'null' string
  params.data = (params.data as string) === 'null' ? '0x' : params.data;
}
```
This handles cases where the LLM returns 'null' as a string instead of a null value, ensuring the transaction data is always properly formatted.

This PR implements the backend portions of the Runs Tracking and Interface plan described in `docs/runs-tracking-interface.md`. It adds structured logging and server aggregation endpoints enabling the client to render a per-run timeline.

### Context / Problem Statement
- We lacked a consistent way to observe an agent run end-to-end (start, actions, model calls, evaluators, end/timeout).
- Existing logs were unstructured for run-level aggregation, making it hard to build a timeline UI or debug long chains.

### What’s Implemented (Non-Frontend)
- Core & Bootstrap logging:
  - Log `RUN_*` lifecycle events as `type: 'run_event'` with `runId`, status, timing, and context.
  - Log `ACTION_STARTED` as `type: 'action_event'` with `runId`, `actionId`, `actionName`, and plan step.
  - Ensure evaluator logs include `body.runId`.
  - Propagate `runId` through embedding generation requests; emit `embedding_event` logs on completion/failure with `runId`.
  - For multi-action plans, include `parentRunId` on action logs for nesting.
- Server API (`packages/server`):
  - New routes under `/api/agents/:agentId/runs`:
    - `GET /runs` — lists recent runs with counts and status.
    - `GET /runs/:runId` — returns a detailed, chronological timeline for a single run.
  - Efficient aggregation (bulk queries; avoid N+1) and stable response shapes per the plan.
  - Tests added for grouping and timeline shaping.
- API Client (`packages/api-client`):
  - New types: `RunSummary`, `RunDetail`, `RunEvent`, `ListRunsParams`.
  - New service: `runs.listRuns(agentId, params)` and `runs.getRun(agentId, runId, roomId?)`.

### Not Included (Frontend)
- Client hooks and UI (Runs list and Run detail timeline) will follow in a separate PR.

### How to Test
- Run server tests for the runs router; verify grouping, counts, and event shaping.
- Exercise the endpoints manually with Postman or curl:
  - `GET /api/agents/:agentId/runs?roomId=&status=&limit=20`
  - `GET /api/agents/:agentId/runs/:runId?roomId=`

### Notes
- No new DB tables; leverages existing `logs` storage with structured bodies.
- Future: consider JSONB indexes and specialized adapter queries for large datasets.

## Summary

The fix ensures that all logs, including those from agent runtimes with namespaces like `#Eliza (Default)`, are properly captured and displayed with correct log levels (warn=40, error=50, info=30, etc.).

## Problem

The original issue had several components:

1. **Undefined Logger Destination**: The logging API was trying to access a Pino-style destination (`Symbol.for('pino-destination')`) but ElizaOS uses Adze logger, causing `undefined` errors.

2. **Missing Namespaced Logs**: Agent-specific logs with namespaces (e.g., `#Eliza (Default)`) were not being captured in the in-memory destination because sealed Adze instances don't trigger the global `adzeStore` listener.

3. **Incorrect Log Levels**: All logs were showing as level 30 (info) instead of their actual levels (warn=40, error=50) due to missing level information in the string output.

4. **ANSI Escape Sequence Issues**: Log parsing was failing due to ANSI color codes in terminal output.

## Solution

### 1. Core Logger Fix (`packages/core/src/logger.ts` & `logger.browser.ts`)

- **Fixed Namespaced Log Capture**: Modified the `invoke` function to manually write all log messages (including namespaced ones) to the `globalInMemoryDestination`
- **Preserved Log Levels**: Ensured that log entries maintain their correct numeric levels (40 for warn, 50 for error, etc.)
- **Enhanced String Output**: Updated `recentLogs()` to include level information in the format "TIMESTAMP LEVEL MESSAGE"

```typescript
// Key fix: Capture all logs in invoke function
const entry: LogEntry = {
  time: Date.now(),
  level: LOG_LEVEL_PRIORITY[method.toLowerCase()] || LOG_LEVEL_PRIORITY.info,
  msg,
};
globalInMemoryDestination.write(entry);
```

### 2. Logging API Fix (`packages/server/src/api/runtime/logging.ts`)

- **Removed Pino Dependencies**: Replaced Pino-specific destination access with ElizaOS `recentLogs()` function
- **Added ANSI Parsing**: Implemented regex to strip ANSI escape sequences before parsing log strings
- **Fixed Level Parsing**: Added proper mapping from level strings to numeric values
- **Improved Error Handling**: Added robust fallback parsing for malformed log lines

```

## Executive Summary
This week, the ElizaOS project balanced immediate progress with long-term strategic planning. We enhanced the framework's capabilities in the Web3 space and improved developer tooling, all while laying the groundwork for a major architectural evolution designed to increase the system's scalability and robustness.

### Key Strategic Initiatives & Outcomes

**Expanding Agent Capabilities in Web2 and Web3**
*Strategic Importance: To fulfill our mission, agents must be able to interact with a growing number of external systems and services, reflecting our commitment to modularity and open collaboration.*
-   The framework's Web3 capabilities were significantly enhanced by adding support for optional calldata in EVM transfers, allowing for more complex and powerful on-chain transactions in [elizaos-plugins/plugin-evm](https://github.com/elizaos-plugins/plugin-evm).
-   Our plugin ecosystem grew with the addition of a new community-contributed plugin (`@standujar/plugin-composio`), demonstrating the success of our open, modular architecture in the [elizaos-plugins/registry](https://github.com/elizaos-plugins/registry).

**Improving Developer Experience and System Stability**
*Strategic Importance: A smooth and reliable development environment empowers our community to build, test, and innovate more effectively.*
-   System observability was improved in [elizaos/eliza](https://github.com/elizaos/eliza) through enhanced Sentry integrations and logging, making it easier for developers to debug and maintain the core platform.
-   Key developer workflow issues were resolved across multiple plugins, including fixing CI test failures and containerizing the project starter, which simplifies setup and ensures code quality.
-   The agent's actions are now more transparent, with UI enhancements in [elizaos-plugins/plugin-evm](https://github.com/elizaos-plugins/plugin-evm) and [elizaos-plugins/plugin-knowledge](https://github.com/elizaos-plugins/plugin-knowledge) that display action calls and results directly in the chat interface.

**Planning for a More Scalable and Modular Future**
*Strategic Importance: We are proactively redesigning core components to ensure the framework can support future growth, complexity, and our vision for decentralized intelligence.*
-   A major strategic planning initiative was launched in [elizaos/eliza](https://github.com/elizaos/eliza), resulting in a comprehensive set of issues that outline a roadmap for refactoring the core API and message bus.
-   Discussions around integrating new AI providers like Venice AI reinforced our commitment to modularity, with a preference for leveraging existing plugins over adding redundant native support.

### Cross-Repository Coordination

**Shared Developer Infrastructure Improvements**
*Initiative: To streamline the development and testing process across multiple plugins by improving shared tooling and UI components.*
-   Work was completed to containerize the project starter ([#5842](https://github.com/elizaos-plugins/plugin-evm/issues/5842)), fix CI test failures ([#5714](https://github.com/elizaos-plugins/plugin-evm/issues/5714)), and enhance UI visibility ([#5831](https://github.comcom/elizaos-plugins/plugin-evm/issues/5831)). This coordinated effort benefits developers working on both the `plugin-evm` and `plugin-knowledge` repositories, ensuring a more consistent and reliable development experience.

28:T87e,## Overview

In testing passing in calldata, we noticed that the `data` field was always `null` even though we were including it. When adding the changes to the `transferTemplate` to look for data, and also including it in the XML, we no longer saw it coming through as `null`. 

The template now properly extracts and passes through any provided data/calldata, and the extended type guard in `transfer.ts` addresses an edge case where data was sometimes sent as `'null'` which didn't trigger the initial default to `0x`.

## Changes

### Template Updates
Added support for data/calldata in the transfer template by adding:
- Instruction to extract "Additional data/calldata (if any is included)"
- XML response field `<data>string | null</data>`

Previously,  the `TransferParams` interface supported an optional data parameter but it seemed that not being included in the template meant it was always `null`, even when provided in the request.

These changes enable proper handling of transaction data in transfers while protecting against LLM response variations. The template now properly extracts and passes through any provided data/calldata, and the code safely normalizes edge cases to ensure valid transaction data.

The `bun.lock` change is from a fresh install of the repo.

**Note**: I tested this on version `1.0.6` but haven't been able to run `1.0.7` due to the character issue I filed on the main repo. Wanted to put up the PR in the meantime! Thank you -- greatly appreciate all the work ya'll are doing to transition!

### Type Guard Change to Handle Edge Case

Added additional defensive handling in `TransferAction` for LLM response edge cases:
```typescript
// Normalize empty or invalid data field to '0x'
if (!params.data || params.data === '0x') {
  params.data = '0x';
} else {
  // Handle case where template returns 'null' string
  params.data = (params.data as string) === 'null' ? '0x' : params.data;
}
```
This handles cases where the LLM returns 'null' as a string instead of a null value, ensuring the transaction data is always properly formatted.

This PR implements the backend portions of the Runs Tracking and Interface plan described in `docs/runs-tracking-interface.md`. It adds structured logging and server aggregation endpoints enabling the client to render a per-run timeline.

### Context / Problem Statement
- We lacked a consistent way to observe an agent run end-to-end (start, actions, model calls, evaluators, end/timeout).
- Existing logs were unstructured for run-level aggregation, making it hard to build a timeline UI or debug long chains.

### What’s Implemented (Non-Frontend)
- Core & Bootstrap logging:
  - Log `RUN_*` lifecycle events as `type: 'run_event'` with `runId`, status, timing, and context.
  - Log `ACTION_STARTED` as `type: 'action_event'` with `runId`, `actionId`, `actionName`, and plan step.
  - Ensure evaluator logs include `body.runId`.
  - Propagate `runId` through embedding generation requests; emit `embedding_event` logs on completion/failure with `runId`.
  - For multi-action plans, include `parentRunId` on action logs for nesting.
- Server API (`packages/server`):
  - New routes under `/api/agents/:agentId/runs`:
    - `GET /runs` — lists recent runs with counts and status.
    - `GET /runs/:runId` — returns a detailed, chronological timeline for a single run.
  - Efficient aggregation (bulk queries; avoid N+1) and stable response shapes per the plan.
  - Tests added for grouping and timeline shaping.
- API Client (`packages/api-client`):
  - New types: `RunSummary`, `RunDetail`, `RunEvent`, `ListRunsParams`.
  - New service: `runs.listRuns(agentId, params)` and `runs.getRun(agentId, runId, roomId?)`.

### Not Included (Frontend)
- Client hooks and UI (Runs list and Run detail timeline) will follow in a separate PR.

### How to Test
- Run server tests for the runs router; verify grouping, counts, and event shaping.
- Exercise the endpoints manually with Postman or curl:
  - `GET /api/agents/:agentId/runs?roomId=&status=&limit=20`
  - `GET /api/agents/:agentId/runs/:runId?roomId=`

### Notes
- No new DB tables; leverages existing `logs` storage with structured bodies.
- Future: consider JSONB indexes and specialized adapter queries for large datasets.

3. **Incorrect Log Levels**: All logs were showing as level 30 (info) instead of their actual levels (warn=40, error=50) due to missing level information in the string output.
