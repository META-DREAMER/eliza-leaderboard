14:T27f4,## Summary

This PR implements a **Jobs API** for one-off messaging functionality, enabling external systems to send single messages to agents and poll for responses without maintaining persistent sessions. This is ideal for stateless integrations similar to SDK patterns.

Additionally, this PR **refactors the middleware architecture** into a modular structure for better maintainability and reusability.

## 🚀 Core Features

### Jobs API Implementation
- **Server Router** (`packages/server/src/api/messaging/jobs.ts` - 681 lines)
  - `POST /api/messaging/jobs` - Create a new job (send message to agent)
  - `GET /api/messaging/jobs/:jobId` - Poll job status and retrieve result  
  - `GET /api/messaging/jobs` - List all jobs (admin/debugging)
  - `GET /api/messaging/jobs/health` - Health check endpoint

- **API Client Service** (`packages/api-client/src/services/jobs.ts` - 423 lines)
  - Full TypeScript client with type-safe methods
  - Integrated into `ElizaClient` as `client.jobs`
  - Built-in polling and retry logic

### Key Capabilities
✅ **Automatic agent selection** - Uses first available agent if not specified  
✅ **Configurable timeouts** - Default: 30s, Max: 5 minutes  
✅ **In-memory job storage** - With automatic cleanup to prevent memory leaks  
✅ **Job status tracking** - `pending → processing → completed/failed/timeout`  
✅ **Metadata support** - Custom tracking fields  
✅ **Intelligent message handling** - Filters intermediate action messages, waits for final result  
✅ **Memory leak prevention** - Max 10k jobs with automatic cleanup  

### Message Flow
1. Client creates job via POST request
2. System creates temporary channel for job isolation
3. User message is sent to channel and emitted to internal message bus
4. Agent processes message via normal flow and responds
5. Response is captured and stored in job result (filters out "Executing action..." intermediate messages)
6. Client polls GET endpoint to retrieve result
7. Job auto-expires and cleans up after timeout

## 🔧 Technical Implementation Details

### Memory Management
- Jobs expire after configured timeout (default 30s, max 5 minutes)
- Cleanup runs every 60 seconds to remove completed/expired jobs
- Emergency cleanup at 10k jobs (removes oldest 10%)
- Message bus listeners auto-cleanup after timeout + 5s buffer
- Metrics tracking for job counts and cleanup operations

### Integration Points
- Integrated with existing messaging router
- Uses internal message bus for agent communication
- Creates temporary channels for job isolation
- Filters out intermediate "Executing action..." messages
- Captures only final agent responses

- ✅ Minimal maintenance surface area

- ✅ Maximum reuse of existing infrastructure

# Background

## What does this PR do?

This PR adds PostgreSQL Row-Level Security (RLS) to enable secure multi-tenant isolation in ElizaOS. Key features:

1. **Database-level isolation**: Uses PostgreSQL RLS policies to enforce tenant boundaries at the database layer
2. **Dynamic server ID assignment**: Each server uses its `owner_id` (derived from auth token) as its `serverId` when RLS is enabled
3. **Automatic RLS management**: Installs/uninstalls RLS functions and policies based on configuration
4. **Complete tenant isolation**: All tables with `owner_id` column are protected by RLS policies
5. **Backward compatible**: Existing deployments continue to work without changes

## What kind of change is this?

**Features** (non-breaking change which adds functionality)

## Why are we doing this?

### Problem
Currently, running multiple ElizaOS servers requires either:
- Multiple separate PostgreSQL databases (expensive, complex to manage)
- Sharing a database without isolation (security risk, data leakage possible)

### Solution
Row-Level Security provides:
- **Cost efficiency**: One PostgreSQL database for multiple tenants
- **Security**: Database-enforced isolation (not application-level)
- **Simplicity**: No complex application logic for tenant filtering
- **Performance**: RLS policies are optimized by PostgreSQL query planner

Implements lazy loading for wallet keys to support dynamic wallet creation after agent initialization. This allows agents to start without a wallet and have one created later by another plugin or external source - **no manual reload needed, just `setSetting()` and it works!**

## Problem Solved

**Use Case**: An agent starts without a Solana wallet. Later, another plugin or an external API creates a wallet for the agent and adds it to the runtime settings.

**Before**: The Solana plugin eagerly loaded wallet keys in the constructor. If no wallet existed at startup, the plugin would fail or throw errors. There was no way to add a wallet after the agent was already running.

**After**: The Solana plugin can start without a wallet. When a wallet is created and added via `runtime.setSetting()`, the next wallet access **automatically picks up the new wallet** - no restart, no manual reload needed!

## Real-World Scenario

```typescript
// Agent starts - no wallet yet
const agent = createAgent({ plugins: [solanaPlugin, another-plugin] });

// Later:
The other plugin:
  → runtime.setSetting('WALLET_PRIVATE_KEY', privateKey)
  → runtime.setSetting('WALLET_PUBLIC_KEY', publicKey)
  // That's it! ✅

// Next swap/transfer action automatically loads the wallet!
// No manual reload, no restart needed! 🎉
```

## How It Works

The lazy loading implementation uses a smart caching strategy:

```typescript
private async ensurePublicKey(): Promise<PublicKey | null> {
  if (this._publicKey) return this._publicKey;  // ← Only caches if wallet exists!

  // _publicKey is null → Try to load from settings
  const result = await getWalletKey(this.runtime, false);
  if (!result.publicKey) return null;  // ← Returns null, doesn't cache it

  this._publicKey = result.publicKey;  // ← Caches only on success
  return this._publicKey;
}
```

**Key insight**: `null` is **not** cached! Every call when `_publicKey = null` will re-check `runtime.getSetting()`. So once you call `setSetting()`, the next access automatically finds it!

**`reloadKeys()` is only needed** if you want to replace an existing wallet with a new one.

### Core Implementation

- **Renamed private fields** to indicate lazy loading:
  - `publicKey` → `_publicKey`
  - `keypair` → `_keypair`

- **Added promise caching** (anti-thundering herd pattern):
  - `_publicKeyPromise` and `_keypairPromise` to prevent duplicate concurrent loads
  - Load attempt counters for debugging

- **Implemented lazy load methods**:
  - `ensurePublicKey()`: Loads public key on-demand, caches only on success
  - `ensureKeypair()`: Loads keypair on-demand, caches only on success
