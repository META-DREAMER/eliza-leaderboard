14:T1529,## Summary

A live prod-fleet audit (2026-07-24) found **44 dedicated agents stuck in a terminal `error` state**, spread across **42 distinct organizations** — and **37 of those orgs have no other running agent** (their *only* agent has been dead for ~11 days). This is not accumulated cruft: all 44 were healthy agents killed by a single event.

## What happened (root cause)

**All 44 errored on the same day — 2026-07-13, in a rolling window 04:00–18:00 UTC** (2–5/hour), even though they were *created* across 2026-07-07…13. The trigger was a **bad image: `ghcr.io/elizaos/eliza:sha-226a22e`**:

- **41 of 44** were on `sha-226a22e` (23/25 of the upgrade failures targeted it; 18/19 of the provisioning failures carried it).
- The reconciler moved agents onto `sha-226a22e` over ~14h and the image **never came up serving** (`agent not serving` / `Agent not running`).
- Two terminal outcomes resulted:
  - **25 × `Upgrade permanently failed after 3 attempts (agent not serving)`** — the AGENT_UPGRADE exhausted its retries.
  - **19 × `Agent was stuck in provisioning state with no active provisioning job`** — these were mid-provision onto `sha-226a22e` when their provisioning job died (consistent with the provisioning-worker heap abort fixed in #17154).
- `error_count = 0` and `database_error = ∅` on all 44 → no active retry loop, not a DB-level fault.

**Why they were never recovered:** the existing rollback/re-arm path (`buildUpgradeFailureMarker` / the `upgrade-failed-target` trailer in `packages/cloud/shared/src/lib/services/provisioning-jobs.ts`) only covers a **rollback-safe** failure — *the new image fails but the OLD container still serves*, so the agent is re-armed on the next published target. These 44 hit a **different** class: **`agent not serving` with `previous_docker_image = ∅`** (no recorded prior image to fall back to). That case is marked permanent-`error` and then **stranded forever** — nothing rolls it back, nothing re-provisions a permanent-error agent, and (for the 19) the provisioning job that would have finished it was already dead.

## Blast radius / containment

- **Contained.** No error rows are newer than ~7 days; the current 91 running dedicated agents are healthy on a good image; nothing is still landing on `sha-226a22e`.
- **Customer impact is real and ongoing (availability):** 42 orgs affected, **37 with their sole agent dead for 11 days** — many owners likely haven't noticed, because a dead agent produces silence, not an error surface.

## The gap to fix (durable)

An upgrade/provision that ends **`not serving` with no rollback target** must not silently strand the agent in permanent `error`. It should do one of:

1. **Roll back** to a known-good digest — but `previous_docker_image` was not recorded for these, so the recovery path had nothing to fall back to (record it on every upgrade so rollback is always possible), or
2. **Re-provision / re-arm onto the current fleet target** (a permanent-`error` agent whose failed target is now superseded is exactly the row the fleet reconciler should re-attempt), or
3. at minimum **surface it for operator recovery** (a fleet health signal for `error`-state agents older than N with no active job), instead of a silent permanent death.

The 19 provisioning-stuck agents also argue for the #17154 fix to include a **sweep that re-drives (or fails cleanly) agents left in `provisioning`/`error` with no owning job** after a worker crash, rather than leaving them terminal.

## Immediate remediation (separate from the code fix)

- **Recover** the 37 sole-agent orgs by re-provisioning onto the current good image — these are live customers whose only agent is down.
- **Triage for deletion** only the 5 orgs that already have another healthy running agent (the dead one is redundant) plus any genuinely dormant org. There is **no `delete-agent`/`reap` admin script** today — deletion must go through the real agent-deletion flow (a raw SQL delete would orphan containers, node slots, and the per-room `SharedRuntimeConversation` Durable Objects, cf. #17006).

## Acceptance criteria

- [ ] A failed upgrade/provision that leaves the container `not serving` records enough state (prior digest / fleet target) to **auto-recover or be re-driven**, never a silent permanent `error`.
- [ ] `previous_docker_image` / `previous_image_digest` is populated on every upgrade so rollback is always possible.
- [ ] A reconciler sweep re-attempts (or cleanly closes) `error`/`provisioning` rows with no active job older than N.
- [ ] The 37 sole-agent-down orgs from 2026-07-13 are recovered; the redundant/dormant ones are cleaned via the real deletion flow.
