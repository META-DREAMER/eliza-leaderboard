- Validation happens before `existsSync` and `mkdir` calls

## Benefits

## Related Issues

<h2>Greptile Overview</h2>

### Greptile Summary

This PR updates `@types/node` from 22.10.5 to 25.0.6, a major version jump spanning 3 major versions. While this is a standard Dependabot update, it introduces a significant concern:

**Primary Issue: Runtime/Types Version Mismatch**

The `@types/node` package v25 provides TypeScript type definitions for Node.js 25.x APIs and features. However, this project:
- Uses Next.js 15.4.10, which officially supports Node.js 18.18+ or 20.x (not 25.x)
- Runs CI/CD on ubuntu-latest with Bun, which typically uses Node.js 18 or 20
- Has no explicit Node.js version constraint in package.json

This mismatch means the TypeScript compiler will assume Node.js 25 APIs are available, potentially allowing code that references newer APIs to pass type checking but fail at runtime.

**Impact Assessment**

Current usage of Node.js types in the codebase:
- `NodeJS.ErrnoException` type in error handling (src/lib/fsHelpers.ts)
- `process.env` for environment variables (throughout)  
- Node.js core modules: crypto, fs, path (drizzle/migrate.ts)

These common APIs are stable across versions, so immediate breakage is unlikely. However, future development might inadvertently use Node.js 25-specific features that won't work in the actual runtime.

**Recommendation**

Align `@types/node` version with your actual Node.js runtime version to ensure type safety matches runtime capabilities. If running Node.js 20.x, downgrade to `@types/node@^20.x.x`. If running Node.js 18.x, use `@types/node@^18.x.x`.

### Confidence Score: 3/5

- This PR introduces a runtime/types version mismatch that could cause subtle issues
- Score of 3 reflects moderate risk: the version jump skips 3 major versions and creates a mismatch between type definitions (Node.js 25) and likely runtime (Node.js 18/20). While existing code uses stable APIs that won't break immediately, this mismatch could allow future code to pass type checking but fail at runtime. The PR will likely work but goes against TypeScript best practices of matching types to runtime.
- package.json requires attention to align @types/node version with actual Node.js runtime version
