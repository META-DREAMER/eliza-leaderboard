7:Tc88,## 🐛 Fix: NPM CLI Package Runtime Path Resolution Issue

### Problem
The published NPM package `@elizaos/cli@1.4.3-alpha.0` was failing with the following error when users tried to run `elizaos create` or `elizaos start`:

```
Error: Cannot find module '/home/runner/work/eliza/eliza/packages/cli/package.json' 
from '/home/cjft/.bun/install/global/node_modules/@elizaos/cli/dist/index.js'
```

This occurred because the CLI was attempting to read its own `package.json` at runtime using `import.meta.url` path resolution, which embedded the GitHub Actions build machine's absolute paths during the bundling process.

### Root Cause
Three files were attempting to read `package.json` at runtime:
- `src/utils/user-environment.ts` - Used `import.meta.url` to resolve package.json path
- `src/utils/display-banner.ts` - Read package.json to display version
- `src/utils/copy-template.ts` - Used `require.resolve()` to find package.json

When Bun bundled the code on GitHub Actions, these dynamic path resolutions were evaluated and hardcoded to `/home/runner/work/eliza/eliza/...`, making the package unusable on users' machines.

### Solution: Build-Time Version Embedding
Implemented **Option 1: Embed Version at Build Time** to eliminate runtime package.json reads entirely.

### Changes Made

#### 1. **Created Version Generation Script** (`src/scripts/generate-version.ts`)
- Reads package.json at build time
- Generates a TypeScript module (`src/version.ts`) with embedded version info
- Exports constants: `CLI_VERSION`, `CLI_NAME`, `CLI_DESCRIPTION`

#### 2. **Updated Build Process** (`build.ts`)
- Now runs version generation before building
- Ensures version information is compiled into the JavaScript bundle

#### 3. **Refactored Runtime Code**
- **`user-environment.ts`**: Now imports from generated version file instead of reading package.json
- **`display-banner.ts`**: Uses embedded `CLI_VERSION` constant
- **`copy-template.ts`**: Falls back to 'latest' if version file is unavailable

#### 4. **Updated `.gitignore`**
- Added `src/version.ts` and `src/version.js` to prevent committing generated files

### Testing
- Created `test-build.sh` script to verify the build process
- Documented the solution in `BUILD-TIME-VERSION.md` and `BUILD-TIME-VERSION-SOLUTION.md`
- The solution ensures the CLI works correctly regardless of where it's installed

### Impact
- ✅ Fixes the critical runtime error preventing users from using the published NPM package
- ✅ Eliminates dependency on runtime file system operations for version info
- ✅ Makes the package truly portable and installable via NPM/Bun
- ✅ No breaking changes to the public API

### Verification Steps
1. Build the package locally: `cd packages/cli && bun run build`
2. Check that `src/version.ts` is generated with correct version info
3. Install and test the package globally
4. Verify `elizaos create` and `elizaos start` work without path errors

This fix ensures that the CLI package published to NPM will work correctly on all users' machines, regardless of their file system structure.

# Fix Discord Image Generation

## Problem

When users requested image generation in Discord, the bot would generate images but fail to send them to Discord at all. The `files` parameter was undefined in the callback chain, resulting in no images being displayed in Discord channels despite successful generation.

## Solution

This PR fixes the image generation functionality for Discord by ensuring generated images are sent as proper Discord file attachments that display inline.

### Changes Made

#### 1. **Updated Image Generation Action** (`packages/plugin-bootstrap/src/actions/imageGeneration.ts`)
- Modified the image generation callback to include file attachments
- Now sends generated images as proper Discord attachments with metadata:
  ```typescript
  await callback(responseContent, [
    {
      id: v4(),
      attachment: imageUrl,
      name: 'Generated_Image.png',
      contentType: ContentType.IMAGE,
    },
  ]);
  ```

#### 2. **Enhanced Action Processing System** (`packages/plugin-bootstrap/src/index.ts`)
- Updated action callback handling to properly pass file attachments:
  ```typescript
  await runtime.processActions(message, responseMessages, state, async (content, files) => {
    runtime.logger.debug({ content, files }, 'action callback');
    responseContent!.actionCallbacks = content;
    return callback(content, files);
  });
  ```

## Impact

❌ **Before**: Image generation requests resulted in no images being sent to Discord  
✅ **After**: Generated images display as proper inline Discord attachments

This enables image generation functionality in Discord for the first time, allowing users to request and view AI-generated images directly in Discord channels.

## Technical Details

The Discord plugin infrastructure already supported file attachments via:
- `sendMessageInChunks()` function with `files` parameter
- `HandlerCallback` interface accepting file attachments

However, the image generation action was not passing the `files` parameter, causing it to be undefined throughout the callback chain. This fix connects the image generation action to the existing Discord attachment infrastructure.

- [x] Image generation works in Discord channels
- [x] Generated images display as inline attachments
- [x] Existing functionality remains unaffected
- [x] File attachment handling works correctly

17:Tc88,## 🐛 Fix: NPM CLI Package Runtime Path Resolution Issue

### Problem
The published NPM package `@elizaos/cli@1.4.3-alpha.0` was failing with the following error when users tried to run `elizaos create` or `elizaos start`:

```
Error: Cannot find module '/home/runner/work/eliza/eliza/packages/cli/package.json' 
from '/home/cjft/.bun/install/global/node_modules/@elizaos/cli/dist/index.js'
```

This occurred because the CLI was attempting to read its own `package.json` at runtime using `import.meta.url` path resolution, which embedded the GitHub Actions build machine's absolute paths during the bundling process.

### Root Cause
Three files were attempting to read `package.json` at runtime:
- `src/utils/user-environment.ts` - Used `import.meta.url` to resolve package.json path
- `src/utils/display-banner.ts` - Read package.json to display version
- `src/utils/copy-template.ts` - Used `require.resolve()` to find package.json

When Bun bundled the code on GitHub Actions, these dynamic path resolutions were evaluated and hardcoded to `/home/runner/work/eliza/eliza/...`, making the package unusable on users' machines.

### Solution: Build-Time Version Embedding
Implemented **Option 1: Embed Version at Build Time** to eliminate runtime package.json reads entirely.

### Changes Made

#### 1. **Created Version Generation Script** (`src/scripts/generate-version.ts`)

## Problem

## Solution

This PR fixes the image generation functionality for Discord by ensuring generated images are sent as proper Discord file attachments that display inline.

### Changes Made

#### 1. **Updated Image Generation Action** (`packages/plugin-bootstrap/src/actions/imageGeneration.ts`)
- Modified the image generation callback to include file attachments
- Now sends generated images as proper Discord attachments with metadata:
  ```typescript
  await callback(responseContent, [
    {
      id: v4(),
      attachment: imageUrl,
      name: 'Generated_Image.png',
      contentType: ContentType.IMAGE,
    },
  ]);
  ```

#### 2. **Enhanced Action Processing System** (`packages/plugin-bootstrap/src/index.ts`)
- Updated action callback handling to properly pass file attachments:
  ```typescript
  await runtime.processActions(message, responseMessages, state, async (content, files) => {
    runtime.logger.debug({ content, files }, 'action callback');
    responseContent!.actionCallbacks = content;
    return callback(content, files);
  });
  ```

## Impact

✅ **After**: Generated images display as proper inline Discord attachments

This enables image generation functionality in Discord for the first time, allowing users to request and view AI-generated images directly in Discord channels.

## Technical Details

The Discord plugin infrastructure already supported file attachments via:
- `sendMessageInChunks()` function with `files` parameter
- `HandlerCallback` interface accepting file attachments

However, the image generation action was not passing the `files` parameter, causing it to be undefined throughout the callback chain. This fix connects the image generation action to the existing Discord attachment infrastructure.
