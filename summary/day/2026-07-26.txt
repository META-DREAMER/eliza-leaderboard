14:T190f,## Goal

Ship a trustworthy LifeOps parent-assistant suite that materially reduces the
anticipation, planning, coordination, monitoring, and recovery work carried by
a busy world-traveling mother coordinating children with a co-parent and
caregivers.

The completed system must ingest authoritative household sources, reason over
multiple calendars without leaking private event details, distinguish proposals
from agreements, obtain the right approvals, monitor material changes, execute
typed transactions exactly once, and verify closure. It must expose source
freshness and errors instead of presenting unavailable data as a healthy empty
state.

## Design doc

`packages/docs/ongoing-development/research/11-agentic-parent-suite.md`

## Scope

- Calendar source registry, sync health, multi-account aggregation, guest
  free/busy, ICS/webcal, and Microsoft Graph calendar support.
- Deterministic conflict/availability evaluation for time, people, custody,
  caregivers, transport, locations, resources, travel, recurrence, time zones,
  DST, and all-day events.
- Typed schedule proposals, per-party agreements, material-change
  invalidation, approval-gated messaging, and provider materialization.
- Household roles, scoped/expiring caregiver access, private-busy projection,
  append-only audit, and scoped export.
- School/activity ingestion and correction monitoring; action bundles,
  responsibility ownership, seasonal opportunities, household items, and
  external-source adapters.
- Food constraints, inventory confidence, cart/order idempotency, delivery
  exception recovery, childcare/work modeling, and source-grounded parenting
  guidance with human handoff.
- A composite world-traveling co-parent persona plus G1-G48 capability
  scenarios, real-provider tests, live-model trajectories, and manually
  reviewed evidence.

## Non-goals

- A second scheduler, household graph, connector abstraction, or file store.
- Behavior keyed from prompt text or demographic runtime modes.
- Autonomous sensitive messages, custody changes, medical/legal decisions, or
  purchases without typed policy and required approval.
- Scraping private guest calendars or fabricating availability, inventory,
  costs, source health, transactions, or completion.

15:T1807,## Problem

The production admin-canary upgrade for the demo agent failed safely before cutover because the mandatory pre-upgrade snapshot exceeded the Cloud raw hydration budget:

- production deploy: `main@054fc9feff4f95dc97409cc7b703e2e45600ebcc`
- canary workflow: `30183809168`
- canary job: `771bc989-3244-41d7-bb03-c9ff565be8c6`
- sanitized actor-bound cause: `Pre-upgrade snapshot failed: Snapshot payload exceeds the raw hydration budget (268435456 bytes) — refusing to retain it`

The current v1 agent snapshot eagerly materializes one JSON document containing every agent-owned shared-Postgres row, including derived embeddings, plus base64 local files. Cloud accepts up to 256 MiB, while `/api/restore` and backup-chain reconstruction cap at 128 MiB, so a 128–256 MiB snapshot can authorize a cutover but be impossible to restore. R2 offload happens only after the whole payload has already been downloaded, parsed, reserialized, encrypted, and retained.

For managed Cloud agents, old and new containers use the same external Postgres database. Copying that database into the container snapshot is both wasteful and semantically dangerous: the current rollback restore deletes/reinserts live shared rows while the current image may still be serving.

This extends #16639; it is the rollout-blocking correctness closure discovered by the exact production canary.

## Required architecture

### 1. Immediate v1 safety alignment

- Define one canonical v1 maximum restorable wire size shared by agent restore, Cloud fetch, backup reconstruction, and verification; it must not exceed 128 MiB.
- Add source-side aggregate/raw/expanded budgeting so the agent aborts before eagerly retaining every component.
- Budget failures are typed, observable, privacy-safe, non-retryable, and occur before cutover.
- Keep manual/auto v1 behavior for genuinely small backups; do not raise heap or body limits.

### 2. Legacy-to-v2 standby bridge

The first rollout crosses an image-protocol boundary: the old image emits only v1 and rejects a v2 database reference. A projected v1 payload cannot make old restore safe because an empty/partial `postgres-rows` restore deletes data.

- Add a distinct durable legacy-standby lifecycle; do not reuse `replacement_cleanup_*`, whose reconciler semantics mean “garbage to destroy.”
- After the new image is provisioned and healthy, stop-preserve the exact old container, volume, VPN identity, image digest, environment generation, and capacity ownership.
- Atomically cut traffic to the new placement while retaining the old stopped container as rollback authority.
- Any failed acceptance CAS-switches back to that exact standby without calling old `/api/restore`.
- Standby retirement requires a verified v2 restore point and explicit acceptance; time alone may never retire it.
- Recovery/reconciliation must be crash-safe and generation/CAS fenced.

### 3. Additive v2 backup protocol

- `POST /api/snapshot` accepts a bounded purpose/capability contract.
- Shared/BYO Postgres is represented by a credential-free, agent-bound connection-identity fingerprint/reference; restore requires an exact match and performs zero SQL deletes/inserts.
- PGlite remains a real captured/restored database component.
- Local media, vault, character/config, and state are streamed as deterministic bounded archive chunks.
- Reuse `agent_sandbox_backups` and the existing tenant-scoped backup namespace. Store an encrypted descriptor plus chunk objects; do not introduce a second backup store.
- Each fixed-size chunk uses authenticated encryption with AAD binding organization, sandbox, backup, schema, index, and size. Hashes/nonces/tags live in the descriptor; commit the descriptor only after every chunk verifies.
- Restore streams, decrypts, verifies, and stages all components before destructive apply. Reject traversal, symlinks, malformed/truncated streams, wrong tenant/agent/database identity, and partial data.
- Reconcile the required R2 bindings into the provisioning daemon. Existing whole-string object helpers must not carry v2.

### 4. Rollout

- Prefer a narrow bridge image first, then the feature image, so rollback-protocol risk is isolated.
- The first legacy→v2 canary retains the old standby through real v2 restore proof.
- After the v2 image becomes the declared rollback floor, subsequent blue/green upgrades use v2 backups and the ordinary cleanup path.
- Never bypass the mandatory restore point, silently drop local state, or treat the external-Postgres reference as a disaster backup.

## Acceptance and evidence

- [ ] Exact-limit v1 passes; limit+1 fails before cutover; Cloud and restore limits cannot diverge.
- [ ] Source-side snapshot collection stays bounded and cancels promptly.
- [ ] A >256 MiB legacy fixture crosses the protocol boundary with bounded worker memory while the old standby remains rollback-capable.
- [ ] Crash/retry at every standby phase converges exactly once without destroying the serving or rollback placement.
- [ ] Failed acceptance CAS-restores the exact old standby without `/api/restore`.
- [ ] v2 shared-Postgres restore validates identity, issues zero SQL, and preserves rows written after snapshot.
- [ ] PGlite, media, vault, character/config, and state round-trip exactly, including corrupt/truncated/adversarial cases.
- [ ] No backup descriptor becomes visible until every encrypted chunk is durable and verified; orphan chunks are reconciled safely.
- [ ] Existing small v1 manual backup/restore remains green.

1b:Tca6,## Problem

A read-only audit prompted by staging recovery canary run 30224564063 found a deterministic capacity-accounting bug independent of that run's still-redacted leaf failure.

`DockerSandboxProvider.stopWithPolicy()` decrements `docker_nodes.allocated_count` after both a fresh container removal and canonical “No such container.” The durable agent row retains the same sandbox/node/container locator until credential cleanup and row deletion complete. If credential revocation, the row-delete CAS, process completion, or job status persistence fails after the first stop, a retry rehydrates the same locator, accepts the already-absent container, and decrements the same slot again. `GREATEST(count - 1, 0)` masks underflow but can free a live sibling's slot. Suspend also stops/decrements while retaining the locator, so a later delete can repeat the decrement without any retry.

The app-container path already solves this class with an atomic durable slot-release stamp; managed agent sandboxes lack an equivalent.

## Required invariant

One logical managed Docker allocation releases exactly one node slot across retries, crashes, already-absent responses, suspend/delete sequences, and late provider completion. Remote teardown remains retryable, while local capacity arithmetic is transactionally idempotent.

## Proposed narrow repair

Add durable deletion allocation ownership (for example `deletion_allocation_counted: boolean | null`):

- `true`: this exact deletion generation still owns one counted node slot;
- `false`: it had no counted slot or the slot was already released;
- `null`: no deletion intent / explicitly unresolved pre-migration intent.

Initialize it from the pre-delete lifecycle state, preserve it on recovery re-enqueue, and cover both queued and direct delete entrypoints. Make ordinary provider stop remote-teardown-only. After an accepted stop outcome, atomically CAS the exact deletion generation `true -> false` and decrement the exact node in the same DB transaction. Reconciliation counts deletion-pending/failed rows only while ownership remains true. Pre-migration deletion intents must be reconciled explicitly rather than guessed.

## Acceptance / real tests

Use real PGlite transactions and the real Docker provider with only SSH transport scripted:

- node count 2 with target + live sibling;
- first stop releases 2→1, downstream credential failure retains the row;
- retry receives “No such container,” completes delete, count remains 1;
- crash before release, crash after release, concurrent release, and stale attempt/locator/node/environment CAS cases;
- stopped/suspended agent with retained locator never decrements a sibling;
- reachable stop failure preserves ownership/count;

# Background

## What does this PR do?

The production canary failed because Cloud **retained** a snapshot larger than anything on the restore path can **consume**:

| Side | Constant | Before | After |
|---|---|---|---|
| retain | `SNAPSHOT_MAX_RAW_BYTES` (`eliza-sandbox.ts`) | **256 MiB** | canonical (128 MiB), env-clamped |
| restore | `MAX_BACKUP_BODY_BYTES` (`packages/agent/src/api/server.ts`) | 128 MiB | canonical |
| reconstruct | `MAX_RECONSTRUCTED_BACKUP_CHAIN_BYTES` (`agent-sandboxes.ts`) | 128 MiB | canonical |

A 128–256 MiB snapshot was therefore retained, authorized a cutover, and could never be restored.

- New `packages/shared/src/agent-backup-limits.ts` holds **`MAX_RESTORABLE_AGENT_BACKUP_BYTES` (128 MiB)** — the one canonical v1 restorable wire size. `@elizaos/shared` is already a dependency of **both** `packages/agent` and `packages/cloud/shared`, so retain, restore and reconstruction import one source of truth with no import cycle. This mirrors the existing `chat-upload-limits.ts` precedent (a leaf limits module both sides import so they cannot drift).
- `resolveRetainableAgentBackupBytes()` resolves the `ELIZA_SNAPSHOT_MAX_RAW_BYTES` operator override **clamped to the canonical limit**. The override keeps its real purpose (lowering the budget for a staging soak or a constrained worker) but can no longer re-open the divergence by configuration alone — which it could before.
- The breach still fails exactly where it already did: **while streaming, before retention** (`readBodyWithinBudget`), so a too-large snapshot is never persisted and never authorizes a cutover.

## Deliberately NOT changed: the verifier's decrypt budget

`DEFAULT_MAX_DECRYPT_BYTES` (256 MiB, `agent-backup-verifier.ts`) is left alone on purpose. It is a **per-cycle aggregate** budget spanning a batch of backups, not a per-backup wire size — a different axis. Lowering it to 128 MiB would be a *regression*: one max-size backup would consume an entire cycle, so the sweep would verify a single backup per cycle. At 256 MiB a max-size (128 MiB) backup always fits with room to spare, and `chargeBudget` already distinguishes `payload-exceeds-cycle-budget` (permanent, stop sampling) from `cycle-budget-exhausted` (transient, defer) — so the "can never verify" case is already handled correctly.
