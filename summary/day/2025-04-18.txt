15:T77f,# ElizaOS Twitter Plugin: Redundant Tweet Interaction Checks

## Description
The Twitter plugin is repeatedly checking the same tweets and mentions in a loop, even after they've been processed. This creates unnecessary API calls and log spam.

## Current Behavior
The system continuously checks the same tweets over and over, as shown in the logs:

```log
[2025-03-31 16:21:29] LOG: Checking Twitter interactions
[2025-03-31 16:21:30] LOG: Completed checking mentioned tweets:
[2025-03-31 16:21:30] LOG: Already responded to tweet 1906195114227020237, skipping
[2025-03-31 16:21:30] LOG: Already responded to tweet 1906195395497091521, skipping
[2025-03-31 16:21:30] LOG: Already responded to tweet 1906209067460137240, skipping
...
[2025-03-31 16:21:59] LOG: Checking Twitter interactions
[2025-03-31 16:22:00] LOG: Already responded to tweet 1906195114227020237, skipping
[2025-03-31 16:22:00] LOG: Already responded to tweet 1906195395497091521, skipping
[2025-03-31 16:22:00] LOG: Already responded to tweet 1906209067460137240, skipping
```

## Expected Behavior
- The system should only check new interactions since the last check
- Previously processed tweets should be filtered out before logging
- The interaction check should maintain a cursor or timestamp of the last checked tweet

## Impact
1. Unnecessary Twitter API calls that could lead to rate limiting
2. Excessive log entries making it difficult to debug actual issues
3. Increased system load from repeated processing of the same data

## Possible Solutions
1. Implement a cursor-based pagination system to only fetch new tweets
2. Store the last checked tweet ID and only process tweets newer than that
3. Add a proper caching mechanism for processed tweets with TTL

## Environment
- ElizaOS Version: 1.0.0-beta.7
- Bun install && bun run build && bun start

- Previous issue about duplicate key errors in Twitter mentions #4115 16:T954,# ElizaOS Twitter Plugin Bugs

## Issue 1: Duplicate Key Error When Receiving Twitter Mentions

**Describe the bug**
When someone mentions the bot on Twitter, the system tries to create a memory record twice with the same ID, resulting in database errors:

```
error: duplicate key value violates unique constraint "memories_pkey"
detail: "Key (id)=(d79a6e52-7b78-0c8b-941d-fd9c0e353f7a) already exists."
```

Logs show the same memory ID being processed twice:
```
[2025-03-30 05:29:29] DEBUG: DrizzleAdapter createMemory:
    memoryId: "d79a6e52-7b78-0c8b-941d-fd9c0e353f7a"
    contentLength: 26
[2025-03-30 05:29:29] LOG: Processing Tweet: 1906217138978697554
[2025-03-30 05:29:29] DEBUG: DrizzleAdapter createMemory:
    memoryId: "d79a6e52-7b78-0c8b-941d-fd9c0e353f7a"
    contentLength: 26
```

**To Reproduce**
1. Configure Twitter plugin with valid credentials
2. Have someone mention your Twitter bot
3. Check logs for duplicate key errors

**Expected behavior**
The bot should create only one memory record per tweet mention and handle all interactions without database errors.

**Root cause**
The issue occurs because `handleTwitterInteractions()` creates a memory record and then calls `handleTweet()` which tries to create the same memory again:
1. First creation in `handleTwitterInteractions()` around line 227
2. Second creation in `handleTweet()` around line 642

## Issue 2: Null Post Interval Configuration

**Describe the bug**
The Twitter post interval configuration is not being properly read, resulting in null values in the logs:

```
[2025-03-30 05:31:09] LOG: - Post Interval: null-null minutes
```

**To Reproduce**
1. Configure Twitter plugin with a valid post interval setting
2. Check logs to see that the interval is showing as null-null minutes

**Expected behavior**
The logs should correctly show the configured post interval, such as "Post Interval: 30-60 minutes" if configured with those values.

**Additional context**
The post interval configuration appears to be properly set in the config files, but the system is not reading or applying these values correctly. This may affect the bot's posting schedule.
