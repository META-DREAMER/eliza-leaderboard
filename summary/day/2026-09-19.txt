15:T891,## Summary

The Twilio and Blooio inbound webhooks use check-then-mark idempotency: `packages/cloud/api/webhooks/twilio/[orgId]/route.ts` calls `isAlreadyProcessed(idempotencyKey)` (~line 147), then `handleIncomingMessage` (~166), then `markAsProcessed` (~167); `webhooks/blooio/[orgId]/route.ts` has the same shape (~107-112, ~168). `handleIncomingMessage` runs agent inference, sends the reply through `messageRouterService.sendMessage`, and records a `twilio_sms` usage row keyed by `MessageSid`, so it routinely exceeds Twilio's 15 s webhook timeout. Any second delivery of the same `MessageSid` / message id that arrives before the first finishes (a fallback URL pointed at the same endpoint, an operator replay, a duplicate POST with a valid signature, or a non-production deployment with `SKIP_WEBHOOK_VERIFICATION=true`) passes the check and is processed in full again: two outbound SMS (real provider spend), two inference runs, two usage rows. `isAlreadyProcessed` also fails open on a DB error. The atomic primitive already exists and is what the WhatsApp webhook uses: `tryClaimForProcessing` (`INSERT ... ON CONFLICT DO NOTHING`) with `releaseProcessingClaim` on failure (`packages/cloud/shared/src/lib/utils/idempotency.ts`, `webhooks/whatsapp/[orgId]/route.ts:110-133`).

## Reproduction (develop `1eba34ba95`, real primitives on PGlite with `idempotency_keys` pushed)

Two concurrent Twilio-style sequences (`isAlreadyProcessed` -> 50 ms work -> `markAsProcessed`) on key `twilio:SM_probe`, versus two concurrent `tryClaimForProcessing("whatsapp:probe")`:

```
check-then-mark results [ "processed", "processed" ]  handled 2
tryClaim results        [ true, false ]
```

The route-level consequence follows from the code order above; the full route was not stood up (it needs an org, a phone gateway and a routed agent).

## Fix direction

Claim before processing in both routes exactly as WhatsApp does: `tryClaimForProcessing(key, "twilio")`; on `false` return the empty TwiML 200; on handler failure `releaseProcessingClaim(key)` so a genuine retry can proceed. Open PR #27661 touches `tryClaimForProcessing` (expired-key reclaim) but does not move these two routes onto it.

# Risks

Low to medium; the change is confined to how "today" is derived for bill dueness.

- New `packages/shared/src/lifeops-normalize/calendar-time-zone.ts` is the single owner: `registerCalendarTimeZoneResolver(runtime, resolver)` stores one owner-zone resolver on the runtime (a global-symbol property, so a dist and a source copy of the module see the same registration), `resolveCalendarTimeZone(runtime, now)` resolves owner zone → agent `TIMEZONE` setting → host zone and reports the `source`, and `calendarDateKey(now, timeZone)` produces the owner-day key.
- Fail-closed: a resolver that throws is a `LifeOpsServiceError` 503 `CALENDAR_TIME_ZONE_UNAVAILABLE` (cause preserved); an invalid zone from the owner or the setting is 422 `CALENDAR_TIME_ZONE_INVALID`. No step falls through to another zone. A `null` owner zone is "not configured" and continues to the setting; that is the only fallthrough.
- `FinancesService.getUpcomingBills` derives `todayIso` from `calendarDateKey(now, (await this.resolveCalendarTimeZone(now)).timeZone)`; the wrapper rethrows the shared error as `FinancesServiceError` with the same status and code, which `runPaymentsHandler` already turns into `success:false` and `runFinancesRoute` into `ctx.error(res, message, status)`. The action constructs `new FinancesService(runtime)` and the route `new FinancesService(runtime, {ownerEntityId})` exactly as before; neither needs injection because the owner lives on the runtime.
- The personal-assistant plugin registers `resolveConfiguredOwnerTimeZone` in `init`, next to the other first-turn registries. It reads the owner facts through `ownerFactsToView`, so the active-travel destination override is honoured like every other owner-zone consumer, and it propagates a store read failure instead of substituting the host zone (the lenient `resolveOwnerTimeZone` used by reminders is unchanged).
- Behavioral change for operators: an invalid owner or `TIMEZONE` zone now surfaces as an error on the bills route and the dashboard action instead of a silently UTC-classified list. Documented in `plugins/plugin-finances/README.md`.

# Background and change

`FormService.registerControlType` owned a per-runtime registry, but top-level validation, parsing, formatting, and both extraction prompts consulted only the separate legacy `registerTypeHandler` map. A registered custom type therefore did not govern a top-level field; the built-in date parser also serialized host-local midnight as a UTC instant and could shift a stated day.

The service now passes its registered `ControlType` to top-level validation and display. The evaluator, single-field extractor, and correction detector resolve the same type at their model/parse boundaries; standalone helpers take an additive, explicit type or resolver argument so one agent's custom registry cannot bleed into another's. An explicit legacy `TypeHandler` still overrides a built-in, while a per-runtime custom `ControlType` wins over that global legacy handler. Date-only answers normalize to a validated `YYYY-MM-DD` calendar day; explicit-year ISO, numeric, and English month-name formats are supported, while yearless or impossible dates remain invalid for re-asking. Sensitive display masking still precedes a type's formatter.

# Risks and documentation

Moderate compatibility risk at the date boundary. Unsupported time-bearing, yearless, and locale-ambiguous input is now invalid rather than silently changed into a plausible saved date. Existing persisted timestamp-shaped values have no reliable original calendar-day provenance; this PR does not invent a migration or silently reinterpret them. Owners should assess those legacy sessions before release. No UI or route was changed. The plugin's existing README registration contract is implemented without a new global registry.

# Risks

Medium (core contract + adapters), mitigated by an explicit fallback:

- New `TaskMetadataPatch { set, unset }` and optional `IDatabaseAdapter.patchTaskMetadata`. `IAgentRuntime.patchTaskMetadata` returns `"patched" | "missing" | "unsupported"` (the adapter member is excluded from the runtime's adapter-surface type). Adapters that do not implement it keep working: `TaskService.persistTaskMetadata` falls back to merging the change over the freshest snapshot and calling `updateTask`, exactly the previous behavior.
- plugin-sql implements the patch as one `UPDATE`: `(COALESCE(metadata,'{}'::jsonb) || $set::jsonb) - 'k1' - 'k2'`, so a concurrent whole-object writer cannot slip between a read and this write. `JSON.stringify` drops `undefined` values, which is why key removal is explicit via `unset` (`lastError` on success, `baseInterval` when a worker returns `nextInterval`) instead of the old `lastError: undefined` / `delete` on the snapshot.
- The core in-memory adapter and `plugin-inmemorydb` merge in place (the latter on its serialized task-mutation tail).
- Semantics of what the run writes are unchanged (same keys, same values); only the write shape changed from replace-all to patch. `dueAt`/`scheduledAt` handling in `updateTask` is untouched.

One additional check, `isNat64LocalUsePrefix`, in `isPrivateIpv6` in `packages/core/src/network/ssrf.ts` and its parity copy `packages/cloud/shared/src/lib/security/outbound-url.ts`: every address whose first three hextets are `64:ff9b:1` (the RFC 8215 local-use block `64:ff9b:1::/48`) is classified as internal before any embedded-IPv4 decoding runs. The block is reserved for site-local translators, is not globally reachable, and a translator may carve its network-specific prefix at any length from /48 to /96, so decoding one layout would still miss the others; failing closed on the whole /48 is the only classification that covers them all. The well-known prefix `64:ff9b::/96` keeps its existing embedding-based rule (a public embedding stays public), and every other IPv6 range is untouched. One existing test asserted `64:ff9b:1::a9fe:a9fe` was public "because it is not /96"; that case now uses `64:ff9b:2::a9fe:a9fe`, which is outside both NAT64 prefixes.

# Background

## What does this PR do?

RFC 8215 reserves `64:ff9b:1::/48` for local-use NAT64 translators. A network running such a translator could previously reach an embedded loopback, link-local or RFC 1918 target through a literal IPv6 URL that both guards classified as public; the DNS-pinned path still screened resolved addresses, so the literal form was the residual. The first commit unwrapped the low 32 bits of `64:ff9b:1::/96` like the well-known prefix; review pointed out that RFC 6052 allows the IPv4 address to sit at other offsets inside a /48 or /64 network-specific prefix, which that decode missed. The second commit replaces the decode with a fail-closed rule on the whole /48 in both guards.

Bug fix (security hardening, non-breaking).
