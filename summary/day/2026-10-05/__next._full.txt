14:T8f0,## Problem

`AgentRuntime.useModel` checks both a caller-supplied `params.signal` and the owning streaming context's `abortSignal` before and after dispatch, but forwards only the explicit signal to the provider when both exist. Cancelling the turn while a cooperative provider is waiting on a response body therefore leaves the transport running. Runtime cancellation is only noticed after that handler eventually settles.

Reproduced against `develop` at `4039228dfdd965354cb61a9da0e26774de21ae02`, through the real runtime and a real local HTTP response body. This is transport/lifecycle evidence with a deterministic registered model handler, not a live LLM call.

## Reproduction

1. Register a `TEXT_LARGE` handler that calls `fetch(url, { signal: params.signal })` and awaits `response.text()`.
2. Have the local HTTP server flush a partial body and hold the response open.
3. Call `runtime.useModel` with an explicit caller controller inside `runWithStreamingContext({ abortSignal: turnController.signal }, ...)`.
4. After the server receives the request, abort only `turnController`.

The handler's signal remains un-aborted and the pending response is not cancelled. Aborting the explicit caller controller subsequently allows cleanup. Caller-only, turn-only, shared-signal, and pre-aborted controls behave correctly.

## Expected behavior

The provider transport should observe cancellation from either owner, without mutating the caller's request or aborting the other owner's controller. Cancellation must retain its reason and must not trigger provider fallback.

## Proposed scope

Compose the two distinct signals once at the dispatch boundary and use the same signal for provider parameters, runtime checks, downstream delivery, and embedding validation. Preserve signal identity when there is only one signal or both references are the same. Add real-runtime HTTP regressions and document the cancellation contract; no provider plugin API or dependency changes.

The new cancellation suite on the unchanged baseline is **1 failed / 6 passed**; after the implementation it is **7 passed**. The existing provider fallback suite also passes (**18 tests combined**). Full package and repository verification are being recorded separately, including any Windows limitations.

16:T6ee,### What happens

`buildSelfControlBlockPolicy` in `plugins/plugin-blocker/src/services/website-blocker/engine.ts` only adds a `www.` entry when the requested host has exactly two labels (`shouldAddWwwVariant`, line 1010). It also looks up the per-site policy group by the literal requested host (line 260). As a result the block silently leaves the site reachable in three common cases:

1. **Country-code registrable domains.** Blocking `bbc.co.uk`, `amazon.co.uk` or `abc.net.au` adds no `www.` entry, but these sites serve from `www.`.
2. **Requests that name the www host.** Blocking `www.example.com` (or a pasted `https://www.example.com/`) never blocks `example.com`.
3. **www requests for a site with a policy group.** Blocking `www.twitter.com` blocks only that host. The Twitter/X group that a `twitter.com` request gets (x.com, t.co, twimg hosts and others) is skipped, and twitter.com redirects to x.com, so the block has no practical effect.

In each case the block reports itself as active while the site stays open.

### Repro

```ts
import { buildSelfControlBlockPolicy } from "./engine";

buildSelfControlBlockPolicy(["example.co.uk"]).blockedWebsites;
// ["example.co.uk"]     (no www.example.co.uk)

buildSelfControlBlockPolicy(["www.example.com"]).blockedWebsites;
// ["www.example.com"]   (no example.com)

buildSelfControlBlockPolicy(["www.twitter.com"]).blockedWebsites;
// ["www.twitter.com"]   (a "twitter.com" request yields 13 hosts, including x.com and t.co)
```

### Expected

A registrable domain and its `www.` host should be treated as one site. Both should be blocked whichever one was named, and the site's policy group should apply. Other subdomains such as `news.example.co.uk` or `sub.example.org` should keep blocking only themselves.

In `plugins/plugin-wallet/src/sdk/x402/client.ts`, a payment is checked with `this.budget.checkBudget(service, amount)` (sync), then `await this.executePayment(selected)` (an on-chain transfer), and only afterwards recorded with `this.budget.recordPayment(log)`. `X402BudgetTracker` keeps `dailySpend` in memory and only updates it in `recordPayment`. So concurrent x402 requests to the same service can all pass the per-service `dailyLimit` check before any of them is recorded, and the agent spends past the configured service cap.

Scope, to be precise: the AgentWallet contract's on-chain spend policy (`setSpendPolicy` / `remainingBudget`) still bounds global spend when it's configured. What can be exceeded is the client-side per-service caps (`serviceBudgets[].dailyLimit`) and `globalDailyLimit` when no on-chain policy is set.

A minimal script against the real `budget.ts` (at `f7a6b0fea5`) that mirrors the client's check → await → record order:

  serviceBudgets: [{ service: "api.example.com", maxPerRequest: 1_000_000n, dailyLimit: 5_000_000n }], // $5/day
});
const executePayment = () => new Promise<void>((r) => setTimeout(r, 50)); // stands in for the transfer
async function pay(i: number) {
  if (!tracker.checkBudget("api.example.com", 1_000_000n).allowed) return "blocked";
  await executePayment();
  tracker.recordPayment({ timestamp: Date.now(), service: "api.example.com", url: `https://api.example.com/${i}`,
    amount: 1_000_000n, token: "0x00…00", recipient: "0x00…01", success: true } as any);
  return "paid";
}
const outcomes = await Promise.all(Array.from({ length: 10 }, (_, i) => pay(i)));
```

```

**Expected behavior**

At most 5 of the 10 payments proceed, and the rest are blocked before `executePayment` runs.
