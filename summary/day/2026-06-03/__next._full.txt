14:Tfed,## Summary

Two release-orchestration workflows hit `startup_failure` on every tag push (most recently on `v2.0.3`):

- [Release All Platforms](https://github.com/elizaOS/eliza/actions/runs/26156834072) — `.github/workflows/release-all.yml`, triggered by `push: tags: [v*.*.*]`
- [elizaOS Full OS Release](https://github.com/elizaOS/eliza/actions/runs/26156833438) — `.github/workflows/elizaos-os-full-release.yml`, triggered by `release: types: [created]`

Both fail before any job runs (`This run likely failed because of a workflow file issue.`). YAML parses cleanly locally; all referenced reusable workflows exist at the tag.

## Root cause

Both orchestrators call reusable workflows whose `secrets:` blocks declare `required: true` for repo secrets that don't exist in `elizaOS/eliza`. When `secrets: inherit` can't supply a `required: true` secret, GitHub fails the parent at startup.

Confirmed via `gh secret list -R elizaOS/eliza` that these are missing:

| Secret | Required by | Purpose |
|---|---|---|
| `DEBIAN_GPG_PRIVATE_KEY` | `publish-apt-repo.yml` | sign apt repo |
| `DEBIAN_GPG_KEY_ID` | `publish-apt-repo.yml` | sign apt repo |
| `DEBIAN_GPG_PASSPHRASE` | `publish-apt-repo.yml` | sign apt repo |
| `CSC_LINK` | `release-electrobun.yml` (macOS sign) | Developer ID .p12 (base64) |
| `CSC_KEY_PASSWORD` | `release-electrobun.yml` | .p12 password |
| `APPLE_ID` | `release-electrobun.yml`, `apple-store-release.yml` | notarization Apple ID |
| `APPLE_APP_SPECIFIC_PASSWORD` | `release-electrobun.yml`, `apple-store-release.yml` | notarization |
| `APPLE_TEAM_ID` | `release-electrobun.yml`, `apple-store-release.yml` | Apple Developer Team ID |
| `ITC_TEAM_ID` | `apple-store-release.yml` | App Store Connect team ID |
| `APP_STORE_APP_ID` | `apple-store-release.yml` | numeric app ID |
| `MATCH_PASSWORD` | `apple-store-release.yml` | Fastlane Match passphrase |
| `MATCH_GIT_URL` | `apple-store-release.yml` | Fastlane Match repo |
| `WINDOWS_SIGN_CERT_BASE64` | `windows-store-release.yml` | Windows code-signing cert |
| `WINDOWS_SIGN_CERT_PASSWORD` | `windows-store-release.yml` | cert password |
| `WINDOWS_SIGN_TIMESTAMP_URL` | `windows-store-release.yml` | RFC 3161 timestamp server |
| `FLATHUB_TOKEN` | `flatpak-publish.yml` | declared `required: false`, not blocking |

The full secret list expected is documented in the header comment of `.github/workflows/release-all.yml`.

## Why the other release workflows worked

`NPM Release`, `Build Agent Image`, `Build elizaOS Linux ISO`, `Build elizaOS Debian Package` (build-only, not publish), `Release AOSP Flasher`, `Release Orchestrator`, `Snap Build & Test`, `Build & Release (Electrobun)`, `Release USB Installer` all started fine — their workflows don't `require: true` any missing secret. (USB Installer separately failed mid-run on a now-fixed `electrobun` PATH issue.)

## Resolution options

1. **Add the missing secrets** to `elizaOS/eliza` → Settings → Secrets and variables → Actions. This is the intended end state per the workflow header docs.
2. **Downgrade `required: true` → `required: false`** in the reusable workflows for platforms we don't intend to ship yet (e.g. if Windows Store / Apple Store / signed apt repo aren't in scope for v2.0.x). The leaf workflows already self-guard most calls.
3. **Stop calling unconfigured publish workflows** from `release-all.yml` until their secrets exist.

Probably want a mix: add Debian GPG (lowest-risk, internal-only) and Apple signing (highest-value), and gate Windows Store + Flathub behind explicit opt-in until those credentials are arranged.

## Context

- Tag for `v2.0.3` is live on `main` (`fa240156ed`). All other release workflows (NPM, Linux ISO, Android, Snap, Electrobun, etc.) ran or are running normally.
- Failed runs are also reproducible on the prior `v2.0.2` attempt — this is the pre-existing block, not a new regression.

The multi-agent orchestrator surface (`/orchestrator`, `@elizaos/plugin-task-coordinator`) is functional but minimal. A richer, full-window **chat-shell UX** — labeled session sidebar, a real composer, theme engine, memory/skills/notes/settings panels, and per-task tool views — would make driving and observing multi-agent runs far nicer, and would give the orchestrator a first-class home in the app shell.

The [odysseus](https://github.com/pewdiepie-archdaemon/odysseus) frontend (MIT) already has a polished, well-considered design for exactly this kind of agent chat workbench.

## Proposal

Port the odysseus **frontend** 1:1 into `plugin-task-coordinator`, **rebuilt in React on `@elizaos/ui`** and wired to elizaOS's **existing runtime** — no new backend, no odysseus Python. Surface it as a new full-bleed `/odysseus` app-shell page (and apply the same full-bleed treatment to `/orchestrator`).

To support a view owning its whole window with no host chrome, add an opt-in `fullBleed` flag to `AppShellPageRegistration` (backward-compatible).

## Scope

- **Frontend only.** All task/session state stays in `@elizaos/plugin-agent-orchestrator`; this is the display/control layer.
- Where elizaOS has no client method for a surface yet (email IMAP/SMTP, calendar CalDAV, gallery backend, voice TTS/STT, …), the view renders an **honest empty/disabled state** rather than fabricated data or dead controls.
- **Credit:** original UI/UX design from odysseus (MIT).

`develop` CI is currently red on **Server Tests** / **Plugin Tests** / **Zero-Key E2E** / **Build production Docker image** because vite-based tests fail to resolve the new `@elizaos/logger` package:

```

The package may have incorrect main/module/exports specified in its package.json.
 ❯ packageEntryFailure node_modules/.bun/vite@.../vite/dist/node/chunks/config.js
FAIL packages/agent/src/__tests__/views-system-smoke.test.ts
FAIL packages/agent/src/__tests__/views-registry-integration.test.ts
FAIL packages/agent/src/__tests__/plugin-tui-view-coverage.test.ts
```

(This blocks every open PR against `develop`, since they all inherit it.)

## Root cause

`packages/logger/package.json` resolves `.` to **`./dist/index.js`** by default, with a non-default `eliza-source` condition pointing at `./src/index.ts`:

```jsonc
"exports": {
  ".": {
    "types": "./dist/index.d.ts",
    "eliza-source": { "import": "./src/index.ts", "default": "./src/index.ts" },
    "import": "./dist/index.js",
    "default": "./dist/index.js"
  }
}
```

`@elizaos/core` depends on it (`"@elizaos/logger": "workspace:*"`, imported in `packages/core/src/logger.ts`). Local/dev setups resolve fine because they run with `--conditions eliza-source` (→ `src`). But the CI vite test runner uses the **`default`** condition → `./dist/index.js`, and **`packages/logger/dist` is not built** before these tests run — so resolution fails.

The test build steps (e.g. Plugin Tests' `run build --filter=@elizaos/core …`) don't build `@elizaos/logger`, and it doesn't get built as a transitive dep in that path either.

## Suggested fixes (pick one)

1. **Build `@elizaos/logger` before the agent/server vite tests** — add it to the build filter list in the test scripts (or ensure turbo builds it as a `^build` dep of `@elizaos/core`).
2. **Resolve `@elizaos/logger` to `src` in the vite test config** — set `resolve.conditions: ['eliza-source', …]` in the agent test vite/vitest config, matching how the runtime resolves it.

Happy to PR whichever direction maintainers prefer.

  resize) + collapsible 48px `IconRail` (mutually exclusive with the sidebar)

In strict / mention-only mode, a user could post a substantive question with **no** `@-mention`, then point the bot at it a few seconds later with a bare `@bot ^^`. Instead of answering, the bot replied with a generic greeting ("Hey there! How can I help you today?"). Re-sending the full question *with* the mention answered correctly. This carries recent unaddressed messages forward so the addressed pointer arrives with the question already folded into `[Recent channel context]`, matching the behavior users already get when both messages share one debounce window.

## Root cause

The Discord `channelDebouncer` bundles rapid messages into a `[Recent channel context]` block prepended to the addressed anchor, but only *within a single debounce batch* (default `DISCORD_CHANNEL_DEBOUNCE_MS=3000`). When the question and the `^^` pointer land more than ~3s apart they fall into separate batches:

- the question flushes record-only into memory (a `prior_message`) and
- the `^^` flushes alone with an empty `[Recent channel context]`.

The model then treats the content-light `^^` as the current message and emits a generic greeting rather than answering the question. A second, compounding issue: a purely-unaddressed batch was arming the 30s response cooldown, which could drop the next unaddressed message before it was even recorded.

## Fix

Two source files, structural only — driven by recency and addressing, with **no** content / intent / regex classification:

- **`debouncer.ts`** — a recency-based per-channel rolling buffer (`recentUnaddressed`, `bufferTtlMs` default 10s and clamped to `>= debounceMs`) of recent unaddressed messages. The next addressed batch drains this buffer and prepends it, so the existing bundler folds it into `[Recent channel context]`. Gated to strict / mention-only mode (`shouldRespondOnlyToMentions`), skipped when message coalescing is enabled, and cleared on `markResponded` and `destroy` so handled chatter never re-bundles into a later unrelated reply.
- **`discord-events.ts`** — arm the response cooldown (`markResponded`) only when the bot actually engages (`botAddressed || !shouldRespondOnlyToMentions`), so a purely-unaddressed batch does not start the 30s cooldown that would otherwise drop the next unaddressed message before it is recorded. Also threads `shouldRespondOnlyToMentions` through to the debouncer options.

Scope and cost:
- **Strict-mode-scoped** — respond-to-all, DM, and coalesce paths are unchanged.
- **No added model / planner cost** — unaddressed messages still hit the persist-only return before the planner; this only changes what context an *already-addressed* turn carries.
- Respects the core runtime `RoomHandlerQueue` "Wave 0" no-coalesce contract — all merging stays plugin-side.

The dashboard app (`packages/app`) renders a **blank screen** when a route pulls in `recharts` (e.g. via the `@elizaos/ui` chart wrapper). The console shows one of two errors depending on whether Vite pre-bundles recharts on that boot:

- pre-bundled: `Uncaught (in promise) TypeError: require_isUnsafeProperty is not a function` at `recharts.js`
- served raw: `SyntaxError: The requested module '.../es-toolkit/compat/get.js' does not provide an export named 'default'`

## Root cause

`recharts@3.8.1` default-imports 11 `es-toolkit/compat/<name>` subpaths (`get`, `omit`, `sortBy`, `throttle`, `last`, `maxBy`, `minBy`, `range`, `sumBy`, `uniqBy`, `isPlainObject`).

`es-toolkit@1.47`'s `package.json` `exports` map gives `./compat/*` **only a CJS condition** (no `import`/ESM):

```jsonc
"./compat/*": { "default": { "types": "./compat/*.d.ts", "default": "./compat/*.js" } }
```

So Vite resolves those imports to es-toolkit's CJS `compat/<name>.js`. Two failure modes:

1. **Pre-bundled** — the dep optimizer bundles the transitive CJS `dist/compat/**/<name>.js`, whose source declares a local `const require_isUnsafeProperty = require(...)`. That name collides with the optimizer's own CJS-interop init helper, emitting a self-shadowing `var require_isUnsafeProperty = require_isUnsafeProperty()` → TDZ → "is not a function".
2. **Served raw** — the CJS shim has no ESM `default` export Vite can surface → "does not provide an export named 'default'".

The real root cause is the es-toolkit packaging (`./compat/*` should also offer an `import` condition pointing at the `.mjs` output). This PR is a consumer-side workaround until that lands.

## Fix

Add a small resolver on **both** serve paths Vite may use:

- the top-level `plugins` array (raw-serve path), and
- `optimizeDeps.rolldownOptions.plugins` (optimizer path),

that rewrites each `es-toolkit/compat/<name>` to its real ESM `dist/compat/**/<name>.mjs` (located relative to the **importer**, so the es-toolkit version recharts actually depends on is used) and emits a tiny virtual module re-exporting the named binding as `default` (+ `export *`), matching how recharts consumes it. Covering both paths keeps it correct whether or not Vite pre-bundles recharts on a given boot.
