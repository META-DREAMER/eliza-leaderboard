14:T3411,## Summary

12 commits that ship connector capability detection (Sprint A), orchestrator self-healing + security gates, and a moltbot-inspired UX redesign for sub-agent narration that prevents conversation-memory pollution from poisoning future planner turns.

## What changed

**Core (Sprint A — connector capability detection)**
- New `MessageConnectorCapability` enum + 4 handler types (`typingHandler`, `stopTypingHandler`, `createThreadHandler`, `postToThreadHandler`).
- 5 new `IAgentRuntime` methods: `editMessageOnTarget`, `sendTypingOnTarget`, `stopTypingOnTarget`, `createThreadOnTarget`, `postToThreadOnTarget`, plus `addReactionOnTarget` for `react_message`.
- `requireConnectorHook<K>` DRY helper (4 call sites would otherwise repeat the same lookup + guard).
- Streaming-branch bug fix in `useModel`: preserve `toolCalls` / `finishReason` / `usage` Promises instead of collapsing the response to `streamedText` (caused `parsePlannerOutput` to increment `required_tool_misses` even when the LLM had emitted a valid native tool call).

**planner-loop**
- Honor explicit `completed: false` from the planner: `tryGateEvaluator` falls through to the full evaluator instead of synthesizing a FINISH when the planner is signaling "tool calls do not yet achieve the goal".
- Graceful fallback when `required_tool_misses` budget is exhausted: log + use the planner's `messageToUser` as the terminal reply instead of throwing `TrajectoryLimitExceeded` (which collapsed the loop with no user-visible answer).

**plugin-discord**
- Declares 7 capabilities incl. `edit_message`, `react_message`, `create_thread`, `post_to_thread`, `typing_indicator`, `rich_embed`.
- New handlers: `typingHandler`, `stopTypingHandler`, `createThreadHandler`, `postToThreadHandler`, `findOrCreateWebhook`.
- `handleSendMessage` now returns a `Memory` carrying `metadata.platformMessageId` so callers can edit/react later.

**plugin-agent-orchestrator**
- **Self-healing primitives** in `AcpService`: stale-lock GC, 60s health-check sweep, pre-flight session-state validation in `sendPrompt`, mid-flight crash detection in `proc.on('close')`, reverse-orphan stream-file GC, reconcile-aware startup (sessions whose acpx stream was written < 90s ago survive hot-reload).
- **Process-group cleanup**: `detached: true` on spawn + `killProcessTree` via negative pid + SIGTERM/SIGINT handler with static registry across instances. No more `claude-agent-acp` zombies after parent exit.
- **Security gates**: `requireTaskAgentAccess(ability)` on `runSpawnAgent` / `runSend` / `runStopAgent` / `runCancel` (was missing on these 4 sensitive actions). `ELIZA_ADMIN_ENTITY_ID` already supported by core roles.
- **TASK_AUDIT NDJSON** at `~/.eliza/plugin-acp/audit.ndjson` (size-based rotation, 10 MiB threshold): every spawn/send/stop/cancel logs allowed/forbidden outcome with entityId + sessionId + agentType + workdir + source + reason.
- **Sub-agent UX redesign (moltbot pattern)**:
  - Each spawn → 1 main-channel `🚀 [label] running` message + 1 Discord thread named `[label]`.
  - Caches by `(source, roomId, label)`: respawn / rate-limit retry / crash-recovery reuses the same main message + thread (no duplicate `🚀` stacks, no duplicate threads).
  - LRU eviction with `LABEL_CACHE_LIMIT = 200` bounds runtime growth.
  - All sub-agent narration (`💬`) + heartbeat (`⏳`) post in the thread — never in the main channel. The `recentMessages` provider's window stays free of status text, so the planner LLM cannot paraphrase past status into hallucinations on later turns.
  - `runtime.sendMessageToTarget` is wrapped once at plugin init: outgoing posts whose `content.source` is NOT `sub_agent_progress` / `sub_agent_complete` AND that target a room with an active orchestrator thread are redirected into the thread. Cross-platform — capability-gated on `post_to_thread`.
  - Capability fallback ladder: thread → edit-in-place → fresh send. Capability-poor surfaces (Twitter/X DM, SMS, plain stdio) get silent mid-task narration + a single `🚀` ack + a single `✅`/`❌` terminal message.
  - Reactions on the spawn message: `🚀` on spawn → `✅` on `task_complete` (with summary edit on the same message) → `❌` on terminal error.
  - Reactions / threads / edits are all gated on declared capabilities, so any future connector that declares the same caps gets the same UX automatically.
- **Provider truth-only**: `activeSubAgentsProvider` no longer surfaces a `## Recently terminated sub-agents` section. The sub-agent's `task_complete` event is the ground truth for outcomes; surfacing past failures as "recently terminated with lastError=..." was letting the planner generalize them as predictors for new spawns.
- **Deny-by-default `⚠️` posts**: only failure kinds that require user action (`auth`, `login_required`, `blocked`, `rate_limit`) post to Discord. Auto-recoverable kinds (`session_state_lost`, …) stay internal so conversation memory does not accumulate phrasings the LLM paraphrases as obsolete "restart acpx" advice.

**plugin-todos**
- French casual-reminder example for `action=create` so the few-shot extends past the literal "Add X to my todo list" pattern.

## Known follow-ups (out of scope for this PR)

- `suppressPlannerReply` flag on `TASKS_SPAWN_AGENT.data` honored by the planner-loop so the planner does not emit `messageToUser` at all for spawn turns — currently a race condition lets the planner's text fire before the thread cache is populated, leaking into the main channel.
- `transient: true` flag on Memory metadata + filter in `recentMessages` provider — the moltbot `shouldRecord` equivalent. Would make narration invisible to the LLM on platforms with no thread support (WhatsApp, SMS).

Adds `packages/benchmarks/swe_bench/harness/comparison.py` — a side-by-side comparison runner that grades the **same** SWE-bench Lite instance through two paths and produces a single JSON report with per-instance patches, resolve status, time, and a winner field.

- **Path A (elizaOS)**: reuses `swe_bench.cli._run_instance` — same TS bridge, same prompt, same diff extractor. Number changes there carry over automatically.
- **Path B (opencode)**: clones `<repo>.git`, `git checkout <base_commit>`, runs `opencode run "<task>"` in the workdir, captures `git diff`. Both paths feed the same `SWEBenchEvaluator.evaluate_patch` so grading is identical.

## Why

Closes the "is elizaOS on par at coding with opencode?" question with measurable apples-to-apples. The orchestrator's `buildOpencodeSpawnConfig` only adds routing wiring, so Path B bypasses the orchestrator to keep variance attributable to opencode itself (not routing).

## Schema (`comparison_<ts>.json`)

```jsonc
{
  "schema_version": 1,
  "totals": { "instances", "elizaos_resolved", "opencode_resolved",
              "elizaos_wins", "opencode_wins", "ties_resolved", "ties_failed" },
  "records": [{
    "instance_id", "repo", "base_commit",
    "path_a": { "path": "elizaos", "status", "patch", "resolved", "time_s",
                "patch_status", "tests_passed", "tests_failed", "error" },
    "path_b": { "path": "opencode", ... same shape ... },
    "winner": "elizaos | opencode | tie_resolved | tie_failed"
  }]
}
```

`status` ∈ `resolved | failed | no_patch | error | skipped_opencode_missing | not_run_yet`.

<!-- /greptile_comment -->19:T19b0,## Root cause

Fresh sandboxes provisioned with `:develop` consistently failed health check at 180s. The container started, Node ran, but never reached the HTTP listen.

Container logs:
```
[wallet][os-store] boot hydrate skipped: Cannot find package 'jose' imported from /app/plugins/plugin-elizacloud/dist/node/index.node.js
[eliza-autonomous] Failed to start: Error [ERR_MODULE_NOT_FOUND]: Cannot find package 'jose' ...
```

Inspecting the image:

```
/app/node_modules/jose -> /app/packages/app-core/node_modules/jose
/app/packages/app-core/node_modules/jose -> ../../../node_modules/jose
```

Two-hop circular symlink. Node's ESM resolver can't traverse it → import fails → process never finishes boot → container hangs in `ep_poll` until daemon kills it.

## How the loop was formed

`link-docker-local-app-packages.mjs` links app-core's owned root deps (`jose`, `@node-rs/argon2`) in two passes:
1. `packages/app-core/node_modules/<dep>` (for app-core's local resolution)
2. `/app/node_modules/<dep>` (for transitive imports from other plugins)

Each pass calls `resolveDependencyPackageDir` with `[packageDir, repoRoot]`. After the first pass linked `app-core/node_modules/jose → /app/node_modules/jose`, the second pass's resolver searched packageDir first, saw the freshly-created symlink's target had `package.json` (`fs.existsSync` follows symlinks), and returned the symlink path verbatim.

`linkDependencyPackage`'s equality check `path.resolve(packageDir) === path.resolve(target)` compared the symlink path against the target — different strings, so the function proceeded:
1. `removePath(target)` — **deleted the real npm-installed jose at `/app/node_modules/jose`**
2. symlinked target → packageDir (the now-broken intermediate symlink)

End state: circular symlink. Real npm install gone.

## Fix

`resolveDependencyPackageDir` now returns `fs.realpathSync(dir)` instead of the raw join path. The realpath collapses any prior symlink, so when the second-pass call resolves jose it returns `/app/node_modules/jose` (the actual install). `linkDependencyPackage`'s equality check then correctly detects `target === packageDir` and skips — preserving the real npm install at root.

## How this was missed

The first `:develop` builds without Shaw's `baseDirs` patch resolved only at root, so this couldn't happen. The bug was introduced in `06dc596` ("fix(docker): resolve app-core owned dependencies") which added `baseDirs: [packageDir, repoRoot]` so the resolver searches both. Once that landed, every subsequent `:develop` build had the circular symlink baked in.

- [ ] In the resulting image, `ls -la /app/packages/app-core/node_modules/jose` is a symlink → `/app/node_modules/jose` (one hop, not circular)
- [ ] Manual provision of a fresh sandbox via the dashboard transitions from `pending` → `running` (not stuck in health timeout)
