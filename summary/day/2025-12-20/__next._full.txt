14:T1582,## Overview

This RFC documents our current data pipeline architecture and proposes improvements across several data engineering domains. Looking for team input on priorities and approach.

## Current Architecture

Our pipeline follows a **4-stage modular design**:

```
GitHub API → [Ingest] → SQLite (raw tables)
                ↓
           [Process] → SQLite (scores, tags, badges)
                ↓
            [Export] → JSON APIs (leaderboards, stats)
                ↓
          [Summarize] → AI summaries (repo, contributor, overall)
                ↓
           _data branch → GitHub Pages (static deployment)
```

### Strengths ✅
- **Modular design** - Each stage independent, can run in isolation
- **Sophisticated rate limiting** - Adaptive concurrency, token bucket, primary/secondary limit handling
- **Data lineage via git** - `_data` branch with sqlite-diffable provides full audit trail
- **Type safety** - TypeScript strict mode, Zod schemas, Drizzle ORM
- **Configurable scoring** - Multi-dimensional metrics, per-type caps, tagging system
- **Fork-friendly** - No hardcoded org values, env var overrides

### Gaps & Risks ⚠️

| Area | Gap | Risk Level |
|------|-----|------------|
| Idempotency | Partial updates possible if export fails mid-way | Medium |
| Data Quality | No freshness alerts, anomaly detection, or reconciliation checks | Medium |
| Observability | Limited visibility into pipeline health beyond logs | Low |
| Error Recovery | No dead-letter queue, failures silently skipped in mapStep | Medium |
| AI Summaries | Silent fallback if OpenRouter API down, no alerts | Low |
| Scaling | Fixed concurrency, no pagination for large contributor lists | Low (for now) |

---

## Proposed Improvements

### 1. Orchestration

**Current:** GitHub Actions + CLI commands

| Option | Fit | Effort | Notes |
|--------|-----|--------|-------|
| **Stay with GitHub Actions** | Good | - | Works, but limited DAG visibility and retry logic |
| **Dagster** | Excellent | Medium | Asset-based model fits our pipeline, great UI, built-in lineage |
| **Prefect** | Good | Medium | Python-native, good observability |
| **Temporal** | Good | High | Best for durable long-running workflows (AI summaries) |

**Recommendation:** Dagster aligns well with our "assets" mental model (raw tables → scores → summaries → JSON APIs). Provides lineage visualization, partial re-execution, and better failure handling.

### 2. Data Quality & Integrity

**Current:** Zod validation, uniqueness constraints, bot filtering

**Proposed additions:**
- [ ] Add `validate` pipeline stage with assertions:
  - Row counts shouldn't decrease unexpectedly
  - Scores within expected ranges (0-1000?)
  - Freshness check (last ingest < 48 hours)
  - Raw vs processed count reconciliation
- [ ] Consider **Great Expectations** or **Soda** for declarative data contracts
- [ ] Add anomaly detection (unusual spikes in contributors, scores)

### 3. Data Governance

**Current:** Git versioning via sqlite-diffable

**Proposed additions:**
- [ ] PII scrubbing - Hash or remove emails from commits table
- [ ] Config versioning - Store scoring config snapshot with each pipeline run
- [ ] Data catalog - Document table schemas, relationships, refresh cadence
- [ ] Consider **DataHub** or **OpenMetadata** for lineage visualization (if we scale)

### 4. Observability & Monitoring

**Current:** Console logs only

**Proposed additions:**
- [ ] Pipeline metrics dashboard showing:
  - Last successful run timestamp
  - Duration per stage
  - Record counts over time
  - Error rate trends
- [ ] Alerting on:
  - Pipeline failures
  - Data freshness violations (no ingest in 48h)
  - Anomalous record count changes
- [ ] GitHub Actions job summary with run statistics

### 5. Architecture Evolution Paths

**Path A: Incremental (Recommended for now)**
```
Current → Add data quality checks → Better logging/metrics → Dagster (later)
```

**Path B: Modern Data Stack**
```
SQLite → DuckDB → dbt for transforms → Dagster orchestration
```

**Path C: Event-Driven (Future, if needed for scale)**
```
GitHub Webhooks → Event queue → Real-time processing → Time-series DB
```

- [ ] Migrate one pipeline stage as proof of concept
- [ ] Build observability dashboard
