This is the most technically complex part of the matrix runner, as it requires deep object manipulation, array indexing, and robust error handling. The implementation must be flexible enough to handle various scenario structures while being safe and predictable.

The parameter override system will be used by the run orchestration logic (ticket 1.4) to generate the modified scenario configurations for each matrix execution.

#### **3. Acceptance Criteria**

1. **Core Override Function:**
   * Implement `applyParameterOverride(scenario: any, path: string, value: any): any` that:
     * Takes a scenario object (parsed from YAML)
     * Accepts a dot-notation path (e.g., `character.llm.model`, `run[0].input`)
     * Applies the specified value at that path
     * Returns a deep clone of the scenario with the override applied
     * Does not mutate the original scenario object
2. **Dot-Notation Path Parsing:**
   * Support nested object access: `character.llm.model`
   * Support array indexing: `run[0].input`, `plugins[2].enabled`
   * Support mixed paths: `run[0].evaluations[1].value`
   * Handle edge cases like empty arrays, null values, and missing intermediate objects
   * Provide clear error messages for invalid paths
3. **Batch Override Application:**
   * Implement `applyMatrixOverrides(baseScenario: any, overrides: Record<string, any>): any` that:
     * Takes a base scenario and a set of parameter overrides
     * Applies all overrides in sequence
     * Returns the final modified scenario object
     * Handles conflicts gracefully (later overrides take precedence)
4. **Path Validation:**
   * Implement `validateParameterPath(scenario: any, path: string): ValidationResult` that:
     * Checks if a given path exists in the scenario structure
     * Returns detailed information about path validity
     * Suggests corrections for common mistakes (e.g., `run.0.input` → `run[0].input`)
     * Warns about potentially dangerous overrides (e.g., overwriting entire objects)
5. **Type Safety and Deep Cloning:**
   * All operations must work with deep clones to prevent accidental mutations
   * Preserve the original data types when possible
   * Handle special cases like Date objects, RegExp, and other non-plain objects
   * Maintain array ordering and object key ordering where possible
6. **Error Handling:**
   * Clear error messages for invalid paths: `"Path 'run[5].input' is invalid: array 'run' has only 2 elements"`
   * Type mismatch warnings: `"Warning: Setting 'plugins[0]' to string value, but existing value is object"`
   * Path creation for missing intermediate objects: `"Created missing object at path 'character.llm'"`
7. **Performance Optimization:**
   * Efficient path parsing that doesn't recompute for similar paths
   * Minimal object copying - only clone what needs to be modified
   * Caching of parsed paths for repeated operations

#### **2. Description**

To enable advanced, multi-variable testing of agent performance, we need a robust way to define a "matrix" of test configurations. This ticket covers the creation of the YAML configuration file that will drive the new Scenario Matrix Runner.

The goal is to design a schema that is both powerful and easy for developers to understand. This configuration will specify a base scenario and a set of parameters to vary, allowing the system to automatically generate and run all possible combinations.

This work is foundational for the entire Scenario Testing and Reporting Framework and does not include the logic for actually running the scenarios, only for defining and validating their configuration.

#### **3. Acceptance Criteria**

1. **YAML Schema Definition:**
   * A formal YAML schema is defined and documented. The configuration file (e.g., `matrix.scenario.yaml`) must support the following top-level keys:
     * `name` (string, required): A human-readable name for the test matrix (e.g., "GitHub Issue Prompt Robustness").
     * `description` (string, optional): A longer description of the test's goals.
     * `base_scenario` (string, required): The file path (relative to the project root) to the base `.scenario.yaml` file to be used in each run.
     * `runs_per_combination` (integer, optional, default: `1`): The number of times to execute each unique combination of parameters to check for consistency.
     * `matrix` (array, required): An array of objects defining the axes of variation. Each object must contain:
       * `parameter` (string, required): The target field in the base scenario to override, specified using dot-notation (e.g., `character.llm.model`, `run[0].input`).
       * `values` (array, required): A list of the values to be substituted for the specified `parameter`.
2. **TypeScript Interfaces:**
   * A new file, `packages/cli/src/commands/scenario/src/matrix-schema.ts`, will be created.
   * This file will contain exported TypeScript interfaces (`MatrixConfig`, `MatrixAxis`, etc.) that precisely match the defined YAML schema, ensuring strong type safety for the rest of the feature.
3. **Configuration Validation:**
   * The `matrix-schema.ts` file will also contain an exported validation function, e.g., `validateMatrixConfig(config: unknown): MatrixConfig`.
   * This function will use a library like **Zod** to rigorously validate the parsed YAML object against the schema.
   * Validation errors must be user-friendly and clearly indicate the specific problem in the configuration file (e.g., `Validation Error: "matrix[1].values" must be a non-empty array.`).
4. **Documentation:**
   * A new documentation file, `packages/cli/src/commands/scenario/docs/matrix-testing.md`, will be created.
   * This document will explain the purpose of matrix testing and provide a detailed guide on how to create the `matrix.scenario.yaml` file, with clear explanations for each field.
