14:T965,## Summary
Steward login is broken in production — **both** email and Google OAuth fail with 400 — which blocks "Sign in with Eliza Cloud" for **every** app (the cli-login flow bounces all third-party apps + the dashboard through this same login).

Reproduces with plain `curl` (no browser, no extensions), so it's a server-side prod issue, not a client environment.

## Symptoms (prod, `api.elizacloud.ai`)
**Google/OAuth** — `GET /steward/auth/oauth/google/authorize?...&response_type=code`:
```
{"ok":false,"error":"code_challenge is required for response_type=code"}
```
Adding `code_challenge` + `code_challenge_method=S256` still returns **400**.

**Email** — `POST /steward/auth/email/send` → **400 Bad Request** (from `steward-login-section.tsx` → `signInWithEmail`).

## Root cause (the OAuth half)
The Steward `/authorize` endpoint now **requires PKCE** (`code_challenge`), but:
- `packages/cloud-frontend/src/pages/login/steward-oauth-url.ts` → `buildStewardOAuthAuthorizeUrl()` builds the URL with `response_type: "code"` and **no** `code_challenge` / `code_challenge_method`.
- The exchange flow is **nonce-based with no verifier**: `packages/cloud-api/auth/steward-nonce-exchange/route.ts` documents *"The Steward API authenticates the exchange purely by possession of the one-time `code` — there is no client [verifier]."*

So the authorize service (PKCE-required) and the cloud login flow (nonce-based, no PKCE) are out of sync — and even a hand-added `code_challenge` still 400s, suggesting a deeper Steward auth misconfig/regression in prod.

## Impact
No one can sign in via Eliza Cloud right now — dashboard, edad, and every third-party app using the cli-login "Sign in with Eliza Cloud" bounce here and dead-end at this login.

## Fix options
- **A (restore parity):** make Steward `/authorize` accept the nonce flow **without** `code_challenge` (matches the existing nonce-exchange contract). Simplest if PKCE was enabled unintentionally.
- **B (full PKCE):** frontend generates a `code_verifier` + S256 `code_challenge`, sends `code_challenge` at `/authorize` and stores the verifier; `steward-nonce-exchange` forwards `code_verifier` to `/auth/oauth/exchange`.

The `email/send` 400 handler isn't in this monorepo (Steward service) — flag for that team too; it may share the same prod regression.

Found via the cli-login flow from a third-party browser app.

In `plugin-local-inference`'s voice pipeline, the plumbing to tie a recognized voice to an elizaOS `Entity` is fully present, but the **bind step appears to be unreachable at runtime** — `VoiceProfileStore.bindEntity` / `unbindEntity` have no caller outside tests. As a result a profile's `entityId` stays `null` in practice: attribution can resolve *which voice* is speaking, but the agent never persists *who that is* into the relationship graph.

> Grep-level finding on current `develop` — happy to be corrected if there's a dynamic/registered path I missed.

## What already works (so this isn't a rebuild)

- Voice profiles carry and persist an `entityId` — `plugins/plugin-local-inference/src/services/voice/profile-store.ts` (`bindEntity` L605, `unbindEntity` L627).
- Attribution resolves the entity on recognition — `src/services/voice/speaker/attribution-pipeline.ts:199` (`entityId: refined?.entityId ?? match.profile.entityId ?? null`).
- The UI already crowns the OWNER when the speaking voice's entity matches the owner — `packages/ui/.../ChatVoiceStatusBar` (`speakerEntityId === ownerEntityId`).

## The gap

`grep -rn bindEntity` across `plugins/` + `packages/` returns only the definitions in `profile-store.ts` and references in `__tests__/voice-profile-store.test.ts`. The voice-profile routes (`src/services/voice/voice-profile-routes.ts`) expose `activate` / list / soft-delete, but **no bind/claim endpoint**, and there is no agent action that binds. 2. An agent action so the agent can bind by voice ("this is &lt;name&gt;"), mirroring how `GENERATE_MEDIA` is wired.
3. On bind, route through `EntityStore` / `RelationshipStore` + the identity merge engine (per the root `CLAUDE.md` rule — don't bypass it), so the bound voice becomes a first-class relationship node.

App-credits purchases and inference spend use **two different ledgers**, so credits a user buys for a monetized app can't be spent — and a user with cloud/org credits is blocked from a monetized app unless they separately top up the app pool. This blocks third-party browser apps monetizing via `X-App-Id` end-to-end.

This looks like a half-finished migration (see the `// Switched from app_credit_balances ... to the org balance` comment), so flagging rather than unilaterally changing billing.

## Details (origin/develop)
- **Purchase funds the per-app pool.** `processPurchase` credits `app_credit_balances` via `appCreditBalancesRepository.addCredits(...)` — `packages/cloud-shared/src/lib/services/app-credits.ts:~307`.
- **Balance check reads the per-app pool.** `checkBalance` → `appCreditBalancesRepository.findByAppAndUser(...)` — `app-credits.ts:~193`.
- **Spend debits the ORG balance.** The spend path was switched to `creditsService.reserveAndDeductCredits({ organizationId })` — `app-credits.ts:~408` (the "Switched from app_credit_balances ... to the org balance" comment). The `X-App-Id` completions path also reserves against the org: `reserveCredits({ organizationId })` — `packages/cloud-api/v1/chat/completions/route.ts:~934`.

## Impact
1. A user buys app-credits → funds land in `app_credit_balances` → inference debits the **org** balance → "Insufficient credits" against an empty org balance. **Money paid, credits never spendable.**
2. `checkBalance` gates on the app pool, so a user who *does* have org/cloud credits is rejected from a monetized app unless they top up the app pool too.
3. The `/api/v1/apps/[id]/chat` 402 says "Insufficient app credits" but deducts from the org balance (`route.ts:~295-333`), so the error misdirects users.

## Suggested fix (pick one ledger)
- **A — org-only (matches the "Switched" comment's intent):** make `processPurchase` credit the **org** balance (and have `/api/v1/app-credits/balance` + `checkBalance` report/read org). App-credits checkout becomes "top up cloud credits for this app"; creator still earns markup via `recordCreatorEarnings()`. Simplest if the per-app pool is being retired.
- **B — app-pool-only:** make the `X-App-Id` spend path read+debit `app_credit_balances` instead of the org balance.

Happy to open the PR once you confirm the direction (A or B) — A looks consistent with the existing comment + `recordCreatorEarnings`. Also a one-line follow-up: word the `/apps/[id]/chat` 402 to match whichever ledger is checked.

24:T7cb,## Problem

The global CORS middleware (`app.use("*", corsMiddleware)` in `cloud-api/src/bootstrap-app.ts`) reflects `Access-Control-Allow-Origin` **only** for first-party origins (`elizacloud.ai` + localhost + pages previews) with `credentials: true`, and omits the header for everyone else.

So registered third-party browser apps — e.g. `supakan.nubs.site`, `*.apps.elizacloud.ai` — are blocked by CORS on the **public, token-authed** API (`/api/v1/chat/completions`, `/api/v1/app-credits/*`, `/api/v1/models`, …), even though they authenticate with a `Bearer eliza_*` key. This defeats the model documented in `lib/middleware/cors-apps.ts` ("CORS open for the API; security is enforced by auth tokens, not origin").

Verified live: own origin gets `ACAO`; `milady.nubs.site` (a registered app origin) and `supakan.nubs.site` get **none** → browser blocks every request.

## Fix

Split CORS by origin class in the global middleware:

- **First-party origins** → reflect origin + `credentials: true` (unchanged; cookie/session auth keeps working).
- **Any other browser origin** → reflect origin **without** credentials, so token-authed apps can call the API from the browser.
