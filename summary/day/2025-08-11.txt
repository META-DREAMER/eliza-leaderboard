- **Issue**: The package scope `@elizaos` doesn't exist on npm, preventing publishing
- **Impact**: Package cannot be published to npm, but CLI reports success

### 2. False Success Reporting
- **Issue**: CLI reports `[√] Successfully published @elizaos/plugin-polygon@1.0.0 to npm`
- **Reality**: npm publish failed with 404 error
- **Impact**: Developers believe their plugin is published when it's not

### 3. Registry Repository Mismatch
- **Expected**: Should create PR against `https://github.com/elizaos-plugins/registry`
- **Actual**: Still references old registry `https://github.com/elizaos/registry`
- **Impact**: Plugin won't appear in the official ElizaOS registry

```bash

# Ensure you're on the correct branch with the changes
git checkout polygon

# Run the publish command
elizaos publish --npm

# Verify the success message appears
# [√] Successfully published @elizaos/plugin-polygon@1.0.0 to npm

# Check if package actually exists on npm
npm view @elizaos/plugin-polygon@1.0.0
# Result: 404 Not Found - '@elizaos/plugin-polygon@1.0.0' is not in this registry
```

The npm logs show the root cause:
```

error 404 Not Found - PUT https://registry.npmjs.org/@elizaos%2fplugin-polygon - Not found
```

This indicates that the `@elizaos` scope doesn't exist on npm, which is required for publishing scoped packages.

### CLI Error Handling Failure
The ElizaOS CLI is not properly parsing npm error codes:
- npm returns exit code 1 (failure)
- CLI ignores the error and reports success
- No validation that the package actually exists on npm

## Expected Behavior
1. CLI should detect npm publish failures (exit code 1)
2. CLI should fail with clear error message when package scope doesn't exist
3. CLI should validate that package actually exists on npm after publishing
4. CLI should create PRs against the correct registry repository

```typescript
// Before publishing, check if scope exists
const scopeExists = await checkNpmScope('@elizaos');
```

15:Te73,### Problem Statement
Currently, ElizaOS scenario testing lacks the ability to mock internal agent runtime calls (particularly LLM interactions) when testing via the API client. This makes it difficult to create deterministic tests for agent behavior and workflows.

### Current Limitations
- Global function mocks only work for code executed in the same process
- No way to intercept `runtime.useModel` calls from the bootstrap plugin
- Agent behavior is non-deterministic due to real LLM calls
- Difficult to test specific agent decision paths and responses

### Why Different Approach Was Needed

The existing mocking system was designed for **code execution environments** (E2B sandbox and local `node -e` processes), where mocks are applied to the execution context. However, **agent testing** works differently:

- **E2B/Local Execution**: Code runs in isolated processes/sandboxes where global mocks can be applied
- **Agent Testing**: Agent runs as a service with API client interaction, requiring direct runtime method interception
- **Architecture Gap**: The bootstrap plugin calls `runtime.useModel` internally, which can't be mocked through the execution environment approach

This architectural difference necessitated a new approach that directly intercepts runtime methods rather than relying on execution context mocking.

### Proposed Solution: Runtime Method Mocking

We've implemented a new mocking approach that directly intercepts `IAgentRuntime` method calls:

#### Key Components

1. **MockEngine Enhancement**
   - Added `runtimeMethodMocks` to support mocking runtime methods
   - Priority system: `runtimeMethod` > `service` > `globalFunction`
   - Direct method replacement on the runtime instance

2. **Schema Updates**
   - Extended `MockSchema` to include `runtimeMethod: z.string().optional()`
   - Supports mocking any `IAgentRuntime` method (e.g., `useModel`, `getService`)

3. **Conditional Matching**
   - Matcher functions can inspect method arguments
   - Example: `"return args[1] && args[1].prompt && args[1].prompt.includes('should respond')"`
   - Supports complex conditional logic for when to apply mocks

#### Usage Example

```yaml
setup:
  mocks:
    - runtimeMethod: "useModel"
      method: "useModel"
      when:
        matcher: "return args[1] && args[1].prompt && args[1].prompt.includes('should respond')"
      response: "<response><name>agent</name><reasoning>Mocked response</reasoning><action>RESPOND</action></response>"
```

#### Benefits

1. **Deterministic Testing**: Replace LLM calls with static responses
2. **Full Workflow Testing**: Test complete agent decision flows
3. **Conditional Mocking**: Apply mocks based on specific conditions
4. **Runtime Integration**: Works seamlessly with existing agent architecture
5. **Backward Compatibility**: Existing mocks continue to work

#### Implementation Steps

- MockEngine runtime method support
- Schema updates for runtimeMethod mocks
- Conditional matching with matcher functions
- Integration with scenario runner
- Basic useModel mocking working
- Add support for mocking other runtime methods (getService, etc.)
- Create comprehensive test scenarios
- Add documentation and examples
- Consider adding mock recording/replay capabilities

### Technical Details

The implementation works by:
1. Creating the `IAgentRuntime` instance in the scenario runner
2. Applying mocks directly to the runtime object before agent initialization
3. The bootstrap plugin receives the mocked runtime and uses the mocked methods
4. Mocks are reverted after scenario completion
