14:Tda8,## Symptom
`bun run --cwd packages/app build:android` from a clean tree produces an APK with `assets/agent` but **zero `assets/public`, no `capacitor.config.json`** → on device the WebView shows `https://localhost/ net::ERR_CONNECTION_REFUSED` forever (no Capacitor `errorPath` is configured, so there's no retry). Verified on a Solana Seeker tonight.

## Root cause
`7ac0e1fb96` (fix(rv64-pipeline), May 20) moved `androidDir` in `packages/app-core/scripts/run-mobile-build.mjs:89` from `packages/app/android` → `packages/app-core/platforms/android` (gradle, native patches, agent staging) — but `runCapacitor(["sync","android"])` still runs with cwd `packages/app` and `capacitor.config.ts` has **no `android.path`**, so the Capacitor CLI keeps delivering the web layer to `packages/app/android`. Nothing bridges the two trees: `capacitor-platform-templates.mjs:27-43` explicitly skips `assets/public`, `assets/agent`, and the generated capacitor JSONs when materializing templates.

Evidence it used to be one project: the tracked `packages/app-core/platforms/android/capacitor.settings.gradle` projectDirs (`../../../app/node_modules/…`) are only producible with the platform dir at `app-core/platforms/android` — i.e. an `android.path` override existed and was lost. A pre-May-20 develop worktree (`bb69a3642e`) has all five asset trees together under `packages/app/android`. Same asymmetry: `iosDir` lives in the host app (`packages/app/ios/App`), android was left behind.

## Why CI doesn't catch it
- `build-android.yml` / `mobile-build-smoke.yml` only assert the APK **file exists** (smoke: lines 255-262); the artifact audits (`auditAndroidCloudArtifact`) check banned entries only, never that `assets/public/index.html` is present.
- No workflow boots the app; `mobile-local-chat-smoke.mjs` isn't wired into any workflow.
- Builds on machines with stale untracked `assets/public` leftovers in the platforms tree appear to work — clean checkouts never do.

## Verified workaround (tonight, on-device confirmed)
After `build:android`: copy `packages/app/android/app/src/main/assets/{public,capacitor.config.json,capacitor.plugins.json}` + `res/xml/config.xml` into `packages/app-core/platforms/android/app/src/main/...`, re-run `./gradlew :app:assembleDebug` there → complete APK (282→336MB), app boots to onboarding on a real device. Caveat: the tracked canonical `capacitor.settings.gradle` lags the synced one (missing background-runner, barcode-scanner, browser, device, haptics, network plugin projects → runtime "plugin not implemented" degradation).

## Proposed fix (either)
1. Restore the lost wiring: `android: { path: "../app-core/platforms/android" }` in `packages/app/capacitor.config.ts` (and teach `ensure-capacitor-platform.mjs`/`isCapacitorPlatformReady` to probe that dir), so sync/copy/update land directly in the gradle tree; or
2. Add a `stageAndroidWebAssets()` step after every `runCapacitor(["sync","android"])` call (4 android targets) copying the web payload + regenerated capacitor gradle files (with path rewrite) into `androidDir`.

Plus, regardless: a **positive APK audit** for sideload targets (assert `assets/public/index.html` + `assets/capacitor.config.json` + `assets/agent/` via `jar tf`) and the same one-liner in CI after assembleDebug, so a web-less APK can never ship silently again.

## State migration plan — operator runs ONCE, manually

There's existing state in `hetzner/apps-data-plane/staging.tfstate` (the tenant DB was deployed on staging before this refactor). Move it to the new shared backend before any new apply.

Order of operations:

1. **Pause both workflows on develop** so nobody apply-races the move:
   ```
   gh workflow disable terraform-apps-data-plane.yml
   gh workflow disable terraform-apps-shared.yml
   ```

2. **Pull both state files locally**:
   ```bash
   export AWS_ACCESS_KEY_ID=...    # R2_STATE_ACCESS_KEY_ID
   export AWS_SECRET_ACCESS_KEY=...
   export HCLOUD_TOKEN=...         # HCLOUD_APPS_TOKEN

   # source: staging apps-data-plane (pre-refactor layout)
   cd packages/cloud-infra/cloud/terraform/hetzner/apps-data-plane
   git checkout develop  # the OLD code path, with tenant_db in this module
   terraform init -backend-config=backend-staging.hcl
   terraform state pull > /tmp/staging-old.tfstate

   # destination: brand-new apps-shared backend (empty)
   cd ../apps-shared
   git checkout refactor/apps-shared-module
   terraform init -backend-config=backend.hcl
   ```

3. **Move the tenant DB + deps from the old staging state into the new shared state**. Run these from the `apps-shared/` working directory (`-state` reads source from disk, `-state-out` writes destination):
   ```bash
   terraform state mv -state=/tmp/staging-old.tfstate -state-out=/tmp/shared-new.tfstate \
     hcloud_network.apps                   hcloud_network.apps
   terraform state mv -state=/tmp/staging-old.tfstate -state-out=/tmp/shared-new.tfstate \
     hcloud_network_subnet.apps            hcloud_network_subnet.apps
   terraform state mv -state=/tmp/staging-old.tfstate -state-out=/tmp/shared-new.tfstate \
     hcloud_firewall.tenant_db             hcloud_firewall.tenant_db
   terraform state mv -state=/tmp/staging-old.tfstate -state-out=/tmp/shared-new.tfstate \
     hcloud_volume.tenant_db_data          hcloud_volume.tenant_db_data
   terraform state mv -state=/tmp/staging-old.tfstate -state-out=/tmp/shared-new.tfstate \
     hcloud_server.tenant_db               hcloud_server.tenant_db
   terraform state mv -state=/tmp/staging-old.tfstate -state-out=/tmp/shared-new.tfstate \
     hcloud_server_network.tenant_db       hcloud_server_network.tenant_db
   terraform state mv -state=/tmp/staging-old.tfstate -state-out=/tmp/shared-new.tfstate \
     hcloud_volume_attachment.tenant_db_data hcloud_volume_attachment.tenant_db_data
   terraform state mv -state=/tmp/staging-old.tfstate -state-out=/tmp/shared-new.tfstate \
     random_password.tenant_db_admin       random_password.tenant_db_admin
   ```

4. **Push both updated state files**:
   ```bash
   # write the new shared state
   cd packages/cloud-infra/cloud/terraform/hetzner/apps-shared
   terraform state push /tmp/shared-new.tfstate

   # write the slimmed-down staging state back
   cd ../apps-data-plane
   terraform state push /tmp/staging-old.tfstate
   ```

5. **Verify both modules plan against reality**:
   ```bash
   cd ../apps-shared && terraform plan -var-file=shared.tfvars
   # EXPECTED (apply this — these are the intended renames + label updates):
   #   ~ hcloud_network.apps        — labels: tier "apps-data-plane" -> "apps-shared",
   #                                  drop environment key (NAME rename suppressed via
   #                                  lifecycle.ignore_changes=[name])
   #   ~ hcloud_volume.tenant_db_data   — same labels diff; name rename suppressed
   #   ~ hcloud_firewall.tenant_db      — same labels diff; name rename suppressed
   #   ~ hcloud_server.tenant_db        — same labels diff; name + user_data +
   #                                       image + ssh_keys all suppressed
   # All four diffs are IN-PLACE (Hetzner PATCH on labels), no destroy, volume +
   # data + private IP all stable. Run `terraform apply` once to converge.
   #
   # NOT EXPECTED (abort + rollback if you see any of these):
   #   - hcloud_server.tenant_db destroyed / replaced
   #   - hcloud_volume.tenant_db_data destroyed / replaced
   #   - any "+ -> destroy" line

   cd ../apps-data-plane && terraform plan -var-file=staging.tfvars
   # expected: no changes — app_node + firewall + DNS already in this state,
   # the new data source just reads the (now shared) network id.
   ```

6. **Re-enable workflows**:
   ```
   gh workflow enable terraform-apps-data-plane.yml
   gh workflow enable terraform-apps-shared.yml
   ```

7. **Done.** Future applies of `apps-data-plane` for staging and production both consume the same shared state.

### About the Hetzner-side name (`eliza-apps-tenantdb-staging` → `eliza-app-tenant`)

The existing tenant DB Hetzner server is named `eliza-apps-tenantdb-staging`. After the state move, TF wants the resource called `eliza-app-tenant` — but `hcloud_server.tenant_db.lifecycle.ignore_changes` already includes `name`, so **TF will NOT rename the server Hetzner-side**. The operator can rename it via the Hetzner Console (cosmetic only — labels, IPs, volumes are all stable).

## Rollback plan

If anything goes wrong after the state move but before reality changes:

1. Revert this PR (`git revert` on develop).
2. Restore the staging state from the R2 versioned bucket (R2 keeps prior object versions — the pre-move tfstate is still there as the previous version).
3. Or push `/tmp/staging-old.tfstate.bak` back (`terraform state push -force` from the backup we kept locally before step 4).

The tenant DB itself is never destroyed during this migration — `terraform state mv` only edits the state graph, no apply runs against the cloud. Worst case after a botched revert is "state thinks the tenant DB is in one module, reality has it; next apply tries to recreate it" → operator rolls back state instead, no DB loss.

Three latent failures the previous tenant-db cloud-init template hits the moment a fresh server boots — all caught the hard way during the staging apply this evening. PR #8384 baked the systemd-oneshot approach; this PR makes the apt install + the script itself + the systemd unit actually survive contact with reality.

## What this fixes

### 1. apt install postgresql hangs forever
Cloud-init races `unattended-upgrades.service` for the dpkg lock. Postgres' postinst then hits a `needrestart` interactive prompt, no tty, no askpass → stuck. Result: `/etc/postgresql/` stays empty, `tenant-db-init` loops `"postgresql package not installed yet; deferring"` on every boot, nothing ever recovers.

Fixes:
- `bootcmd:` disables `unattended-upgrades.service` BEFORE the apt phase
- `/etc/apt/apt.conf.d/99-cloud-init-noninteractive`: `--force-confnew --force-confdef`
- `/etc/needrestart/conf.d/50-cloud-init-noninteractive.conf`: `$nrconf{restart}='a'`
- `package_upgrade: false` — `package_update` is enough; no need to dist-upgrade during install

### 2. `sudo -u postgres ...` fails inside systemd
The Hetzner Ubuntu cloud image ships with root's password marked **expired** (`chage -l root`). Even with `NOPASSWD: ALL` in sudoers, sudo refuses to run from a tty-less service until the password is reset. The journal showed:
```
sudo: Account or password is expired, reset your password and try again
pam_unix(sudo:account): expired password for user root (root enforced)
```
Swapped every `sudo -u postgres CMD` → `runuser -u postgres -- CMD`. `runuser` only uses PAM session, no password auth step.

### 3. systemd ordering cycle with cloud-final
The previous `After=cloud-final.service` was wrong: cloud-final runs runcmd → runcmd enables tenant-db-init → cycle. systemd printed:
```
cloud-final.service: Found ordering cycle on tenant-db-init.service/stop
Job tenant-db-init.service/stop deleted to break ordering cycle
```
Service still ran but with a race window when restarted manually. Dropped `cloud-final.service` from `After=`; `network-online.target` is sufficient.

<h2>Hardhat v3.8.0</h2>
<p>This release includes two improvements: a warning is now printed if a plugin is imported in <code>hardhat.config.ts</code> but not included in the plugins array and <code>node:test</code> now more cleanly displays Solidity errors.</p>
<h3>Changes</h3>
<ul>
<li>
<p><a href="https://redirect.github.com/NomicFoundation/hardhat/pull/8339">#8339</a> <a href="https://github.com/NomicFoundation/hardhat/commit/f21390fe78773d8ba514cd4a64954220437293e3"><code>f21390f</code></a> Thanks <a href="https://github.com/alcuadrado"><code>@​alcuadrado</code></a>! - Added <code>definePlugin</code>, a new helper exported from <code>hardhat/plugins</code>. Plugin authors should wrap their plugin literal with it so the default export of their <code>index</code> module becomes:</p>
<pre lang="ts"><code>import type { HardhatPlugin } from &quot;hardhat/types/plugins&quot;;
<p>import { definePlugin } from &quot;hardhat/plugins&quot;;</p>
<p>const hardhatPlugin: HardhatPlugin = definePlugin({<br />
id: &quot;my-plugin&quot;,<br />
// ...<br />
});</p>
<p>export default hardhatPlugin;<br />
</code></pre></p>
<p><code>definePlugin</code> returns its argument unchanged and, as a side effect, registers the plugin's id in a process-wide registry of loaded plugins. Hardhat's CLI uses that registry to warn when a plugin is imported but missing from the user's <code>plugins</code> array.</p>
</li>
<li>
<p><a href="https://redirect.github.com/NomicFoundation/hardhat/pull/8339">#8339</a> <a href="https://github.com/NomicFoundation/hardhat/commit/19c6927372fb39c4c4f0afe37895c738abbde237"><code>19c6927</code></a> Thanks <a href="https://github.com/alcuadrado"><code>@​alcuadrado</code></a>! - Hardhat now warns when a plugin is imported in your Hardhat config file but missing from the <code>plugins</code> array. The warning is printed to stderr after the runtime environment is created, listing the offending plugins and pointing the user at the fix.</p>
<p>If your Hardhat config file is written in TypeScript, for the warning to be reliable your project's <code>tsconfig.json</code> must enable <code>verbatimModuleSyntax: true</code>. Without it, TypeScript deletes unused default-value imports, so an unused plugin can't be detected.</p>

<pre lang="ts"><code>import type { HardhatPlugin } from &quot;hardhat/types/plugins&quot;;
<p>import { definePlugin } from &quot;hardhat/plugins&quot;;</p>
<p>const hardhatPlugin: HardhatPlugin = definePlugin({<br />
id: &quot;my-plugin&quot;,<br />
// ...<br />
});</p>
<p>export default hardhatPlugin;<br />
</code></pre></p>
<p><code>definePlugin</code> returns its argument unchanged and, as a side effect, registers the plugin's id in a process-wide registry of loaded plugins. Hardhat's CLI uses that registry to warn when a plugin is imported but missing from the user's <code>plugins</code> array.</p>
</li>
<li>
<p><a href="https://redirect.github.com/NomicFoundation/hardhat/pull/8339">#8339</a> <a href="https://github.com/NomicFoundation/hardhat/commit/19c6927372fb39c4c4f0afe37895c738abbde237"><code>19c6927</code></a> Thanks <a href="https://github.com/alcuadrado"><code>@​alcuadrado</code></a>! - Hardhat now warns when a plugin is imported in your Hardhat config file but missing from the <code>plugins</code> array. The warning is printed to stderr after the runtime environment is created, listing the offending plugins and pointing the user at the fix.</p>
<p>If your Hardhat config file is written in TypeScript, for the warning to be reliable your project's <code>tsconfig.json</code> must enable <code>verbatimModuleSyntax: true</code>. Without it, TypeScript deletes unused default-value imports, so an unused plugin can't be detected.</p>
</li>
</ul>

<p><em>Sourced from <a href="https://github.com/evanw/esbuild/releases">esbuild's releases</a>.</em></p>
<blockquote>
<h2>v0.28.0</h2>
<ul>
<li>
<p>Add support for <code>with { type: 'text' }</code> imports (<a href="https://redirect.github.com/evanw/esbuild/issues/4435">#4435</a>)</p>
<p>The <a href="https://github.com/tc39/proposal-import-text">import text</a> proposal has reached stage 3 in the TC39 process, which means that it's recommended for implementation. It has also already been implemented by <a href="https://docs.deno.com/examples/importing_text/">Deno</a> and <a href="https://bun.com/docs/guides/runtime/import-html">Bun</a>. So with this release, esbuild also adds support for it. This behaves exactly the same as esbuild's existing <a href="https://esbuild.github.io/content-types/#text"><code>text</code> loader</a>. Here's an example:</p>
<pre lang="js"><code>import string from './example.txt' with { type: 'text' }
console.log(string)
</code></pre>
</li>
<li>
<p>Add integrity checks to fallback download path (<a href="https://redirect.github.com/evanw/esbuild/issues/4343">#4343</a>)</p>
<p>Installing esbuild via npm is somewhat complicated with several different edge cases (see <a href="https://esbuild.github.io/getting-started/#additional-npm-flags">esbuild's documentation</a> for details). If the regular installation of esbuild's platform-specific package fails, esbuild's install script attempts to download the platform-specific package itself (first with the <code>npm</code> command, and then with a HTTP request to <code>registry.npmjs.org</code> as a last resort).</p>
<p>This last resort path previously didn't have any integrity checks. With this release, esbuild will now verify that the hash of the downloaded binary matches the expected hash for the current release. This means the hashes for all of esbuild's platform-specific binary packages will now be embedded in the top-level <code>esbuild</code> package. Hopefully this should work without any problems. But just in case, this change is being done as a breaking change release.</p>
</li>
<li>
<p>Update the Go compiler from 1.25.7 to 1.26.1</p>
<p>This upgrade should not affect anything. However, there have been some significant internal changes to the Go compiler, so esbuild could potentially behave differently in certain edge cases:</p>
<ul>
<li>It now uses the <a href="https://go.dev/doc/go1.26#new-garbage-collector">new garbage collector</a> that comes with Go 1.26.</li>
<li>The Go compiler is now more aggressive with allocating memory on the stack.</li>
<li>The executable format that the Go linker uses has undergone several changes.</li>
<li>The WebAssembly build now unconditionally makes use of the sign extension and non-trapping floating-point to integer conversion instructions.</li>
</ul>
<p>You can read the <a href="https://go.dev/doc/go1.26">Go 1.26 release notes</a> for more information.</p>
</li>
</ul>
<h2>v0.27.7</h2>
<ul>
<li>
<p>Fix lowering of define semantics for TypeScript parameter properties (<a href="https://redirect.github.com/evanw/esbuild/issues/4421">#4421</a>)</p>
<p>The previous release incorrectly generated class fields for TypeScript parameter properties even when the configured target environment does not support class fields. With this release, the generated class fields will now be correctly lowered in this case:</p>
<pre lang="ts"><code>// Original code
class Foo {
  constructor(public x = 1) {}
  y = 2
}
<p>// Old output (with --loader=ts --target=es2021)<br />
class Foo {<br />
constructor(x = 1) {<br />
this.x = x;<br />
__publicField(this, &quot;y&quot;, 2);<br />
}<br />
x;<br />
}</p>
<p>// New output (with --loader=ts --target=es2021)<br />
class Foo {<br />
</code></pre></p>
</li>
</ul>

<blockquote>
<h1>Changelog: 2025</h1>
<p>This changelog documents all esbuild versions published in the year 2025 (versions 0.25.0 through 0.27.2).</p>
<h2>0.27.2</h2>
<ul>
<li>
<p>Allow import path specifiers starting with <code>#/</code> (<a href="https://redirect.github.com/evanw/esbuild/pull/4361">#4361</a>)</p>
<p>Previously the specification for <code>package.json</code> disallowed import path specifiers starting with <code>#/</code>, but this restriction <a href="https://redirect.github.com/nodejs/node/pull/60864">has recently been relaxed</a> and support for it is being added across the JavaScript ecosystem. One use case is using it for a wildcard pattern such as mapping <code>#/*</code> to <code>./src/*</code> (previously you had to use another character such as <code>#_*</code> instead, which was more confusing). There is some more context in <a href="https://redirect.github.com/nodejs/node/issues/49182">nodejs/node#49182</a>.</p>
<p>This change was contributed by <a href="https://github.com/hybrist"><code>@​hybrist</code></a>.</p>
</li>
<li>
<p>Automatically add the <code>-webkit-mask</code> prefix (<a href="https://redirect.github.com/evanw/esbuild/issues/4357">#4357</a>, <a href="https://redirect.github.com/evanw/esbuild/issues/4358">#4358</a>)</p>
<p>This release automatically adds the <code>-webkit-</code> vendor prefix for the <a href="https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/mask"><code>mask</code></a> CSS shorthand property:</p>
<pre lang="css"><code>/* Original code */
main {
  mask: url(x.png) center/5rem no-repeat
}
<p>/* Old output (with --target=chrome110) */<br />
main {<br />
mask: url(x.png) center/5rem no-repeat;<br />
}</p>
<p>/* New output (with --target=chrome110) */<br />
main {<br />
-webkit-mask: url(x.png) center/5rem no-repeat;<br />
mask: url(x.png) center/5rem no-repeat;<br />
}<br />
</code></pre></p>
<p>This change was contributed by <a href="https://github.com/BPJEnnova"><code>@​BPJEnnova</code></a>.</p>
</li>
<li>
<p>Additional minification of <code>switch</code> statements (<a href="https://redirect.github.com/evanw/esbuild/issues/4176">#4176</a>, <a href="https://redirect.github.com/evanw/esbuild/issues/4359">#4359</a>)</p>
<p>This release contains additional minification patterns for reducing <code>switch</code> statements. Here is an example:</p>
<pre lang="js"><code>// Original code
switch (x) {
  case 0:
    foo()
    break
  case 1:
  default:
    bar()
}
</code></pre>
</li>
