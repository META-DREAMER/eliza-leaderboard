## Background

### What does this PR do?

This PR fixes environment variable loading to work correctly with exported shell variables, not just `.env` files:

1. **Changes `loadSecretsNodeImpl()`** to read directly from `process.env` instead of re-reading the `.env` file
2. **Creates centralized `loadEnvFile()`** function in `core/utils/environment.ts` for consistent `.env` file loading
3. **Updates CLI and Server** to use the centralized function
4. **Updates all tests** to reflect the new behavior

### What kind of change is this?

- ✅ **Bug fixes** (non-breaking change which fixes an issue)
- ✅ **Improvements** (misc. changes to existing features)

### Why are we doing this?

#### Problem Discovered

When running agents in environments where variables are exported directly on the host system (e.g., `export POSTGRES_URL=postgresql://...`), the variables were not accessible via `runtime.getSetting()`, even though they were correctly set in the environment.

**Testing confirmed the issue**:
- ✅ With `.env` file: Works
- ❌ With `export POSTGRES_URL=...`: **Doesn't work**
- ❌ With system environment variables: **Doesn't work**

This is problematic for:
- Production deployments where secrets are managed via exported environment variables
- Container orchestration systems (Docker, ECS, Kubernetes) that inject env vars
- CI/CD pipelines that set variables programmatically
- Development workflows that prefer `export` over `.env` files

#### Root Cause

The `loadSecretsNodeImpl()` function in `packages/core/src/secrets.ts` was:
1. **Only** reading the `.env` FILE directly using `fs.readFileSync()`
2. Parsing it with `dotenv.parse()`
3. Merging those parsed values into `character.settings`

This approach **completely ignored** `process.env`, which contains:
- Variables loaded from `.env` by the CLI (via `dotenv.config()`)
- **Exported shell variables** (`export FOO=bar`) ← **Main issue**
- Container-injected environment variables
- System environment variables

**Why was this a problem?**

When you run:
```bash
export POSTGRES_URL=postgresql://production:5432/eliza
bunx elizaos start --character=./characters/sample.json
```

The variable is in `process.env`, but `loadSecretsNodeImpl()` was looking for a `.env` file instead. If no `.env` file existed, it would fail to load ANY environment variables, even though they were available in `process.env`.

#### Solution

The fix reads `process.env` directly instead of re-reading the `.env` file

**Why this works:**

1. **When using `.env` files**: The CLI calls `dotenv.config()` which loads `.env` → `process.env`
2. **When using exported variables**: Shell already puts them in `process.env`
3. **When using container env vars**: Runtime injects them into `process.env`
4. **Result**: `loadSecretsNodeImpl()` now sees ALL variables, regardless of source

## Documentation changes needed?

- ✅ My changes do not require a change to the project documentation.

The behavior is now more intuitive - environment variables work as expected from any source. No user-facing documentation changes needed.

## Why are we doing this?
