4:T1578,# Enhancement: Add API cost estimation to ingestion pipeline

## Context
Running `bun run pipeline ingest` with large date ranges can unexpectedly consume thousands of GitHub API calls, potentially hitting rate limits:
- **Authenticated users**: 5,000 requests/hour
- **GitHub Apps**: 15,000 requests/hour

This is especially problematic for:
- Historical data ingestion (e.g., `--after 2024-01-01` on 20+ repos)
- First-time project setup
- Large active repositories with thousands of PRs/issues

### Real-world example:
- **23 repositories** × **52 weeks** × **~6 API calls per week** = **~7,176 API calls**
- **Outcome**: Rate limit exhaustion, 1-2 hour wait, failed ingestion

Users need visibility into API cost before committing to large ingestions.

## Proposal
Add `--estimate-only` flag and automatic pre-flight cost estimation that shows:
- Estimated API call count
- Risk level (LOW/MEDIUM/HIGH)
- Estimated duration
- Warning for HIGH risk operations

## Implementation

### Add cost estimation function to `cli/analyze-pipeline.ts`:

```typescript
// Simple API cost estimation helper
function estimateApiCalls(
  repositories: { owner: string; name: string }[],
  intervalCount: number,
): { total: number; risk: string; duration: number } {
  const baseCallsPerRepo = intervalCount * 6; // ~6 calls per interval (PRs, issues, commits)
  const total = repositories.length * baseCallsPerRepo;

  const risk = total > 2000 ? "HIGH" : total > 500 ? "MEDIUM" : "LOW";
  const duration = Math.ceil(total / 60); // ~60 calls per minute with rate limiting

  return { total, risk, duration };
}
```

### Add CLI flag to ingest command:

```typescript
program
  .command("ingest")
  // ... existing options
  .option(
    "--estimate-only",
    "Show API cost estimation without executing ingestion",
    false,
  )
```

### Add estimation logic before execution:

```typescript
// Calculate date range and intervals
const repositories = options.repository
  ? pipelineConfig.repositories.filter(
      (r) => `${r.owner}/${r.name}` === options.repository,
    )
  : pipelineConfig.repositories;

const daysDiff =
  dateRange.endDate && dateRange.startDate
    ? Math.ceil(
        (new Date(dateRange.endDate).getTime() -
          new Date(dateRange.startDate).getTime()) /
          (1000 * 60 * 60 * 24),
      )
    : parseInt(options.days || "7");
const intervalCount = Math.ceil(daysDiff / 7); // Weekly intervals

const estimate = estimateApiCalls(repositories, intervalCount);

rootLogger.info(`📊 Cost Estimation:`, {
  repositories: repositories.length,
  intervals: intervalCount,
  estimatedApiCalls: estimate.total,
  riskLevel: estimate.risk,
  estimatedDuration: `${estimate.duration} minutes`,
});

// Handle estimate-only mode
if (options.estimateOnly) {
  console.log(`\n📋 INGESTION ESTIMATE`);
  console.log(`Repositories: ${repositories.length}`);
  console.log(`Time intervals: ${intervalCount}`);
  console.log(`Estimated API calls: ${estimate.total}`);
  console.log(`Risk level: ${estimate.risk}`);
  console.log(`Estimated duration: ${estimate.duration} minutes`);

  if (estimate.risk === "HIGH") {
    console.log(
      `\n⚠️  HIGH RISK: Consider using smaller date ranges or --repository flag`,
    );
  }
  return;
}

// Warn on high-risk operations
if (estimate.risk === "HIGH") {
  rootLogger.warn(
    `⚠️  High API usage detected (${estimate.total} calls). Monitor rate limits closely.`,
  );
}
```

## Benefits
- ✅ Prevents accidental rate limit exhaustion
- ✅ Better planning for large ingestions
- ✅ User can test with `--estimate-only` before committing
- ✅ Helpful for debugging and capacity planning
- ✅ No behavior change for existing commands (estimation is informational)

## Trade-offs
- Estimation is approximate (actual calls may vary by ±20%)
- Adds ~65 lines of code total (11-line function + 1-line option + ~50 lines logic)
- Risk thresholds are somewhat arbitrary (can be tuned based on team preferences)

5:T1264,# Enhancement: Add graceful shutdown to CLI pipeline

## Context
Long-running ingestion pipelines (historical data ingestion spanning months) can take hours, especially for large active repositories. Currently, pressing Ctrl+C immediately terminates the process, losing all in-progress work.

This is common when:
- Ingesting historical data for the first time
- Running large date range imports (e.g., `--after 2024-01-01`)
- Processing multiple large repositories
- Debugging or testing ingestion locally

## Proposal
Add graceful shutdown handling that:
1. **First Ctrl+C**: Completes current operation, saves progress, then exits cleanly
2. **Second Ctrl+C**: Force exits immediately if user needs to stop now
3. Shows clear messaging about shutdown state
4. Allows resuming with same command (pipeline skips already-processed data)

## Implementation

### Add to `cli/analyze-pipeline.ts` (before program definition):

```typescript
// Graceful shutdown handler
let gracefulShutdown = false;
process.on("SIGINT", () => {
  if (!gracefulShutdown) {
    gracefulShutdown = true;
    (global.process as { gracefulShutdown?: boolean }).gracefulShutdown = true;
    console.log(
      "\n⚠️  Graceful shutdown initiated... Current operations will complete.",
    );
    console.log("Press Ctrl+C again to force exit.");
  } else {
    console.log("\n🔴 Force exit requested.");
    process.exit(1);
  }
});
```

### Update ingest command execution (in ingest action handler):

```typescript
try {
  await ingestPipeline(undefined, context);

  if (gracefulShutdown) {
    rootLogger.warn(
      "⚠️  Ingestion interrupted but current operations completed successfully!",
    );
    rootLogger.info(
      "💡 You can resume by running the same command again - the pipeline will skip already processed data.",
    );
  } else {
    rootLogger.info("✅ Ingestion completed successfully!");
  }
} catch (error: unknown) {
  if (String(error).includes("GRACEFUL_SHUTDOWN")) {
    rootLogger.warn(
      "⚠️  Ingestion gracefully interrupted. Progress has been saved.",
    );
    rootLogger.info("💡 Resume by running the same command again.");
    return;
  }
  throw error;
}
```

### Update `src/lib/pipelines/types.ts` mapStep to respect shutdown:

```typescript
const results = await pMap(
  inputs,
  async (item, index) => {
    // Check for graceful shutdown before processing each item
    if (
      global.process &&
      (global.process as { gracefulShutdown?: boolean }).gracefulShutdown
    ) {
      context.logger?.warn(
        `Graceful shutdown requested. Skipping remaining items after ${index}/${inputs.length}`,
      );
      throw new Error("GRACEFUL_SHUTDOWN");
    }
    return await operation(item, context);
  },
  {
    concurrency: Math.max(1, concurrency),
    stopOnError: false, // Continue processing other items even if one fails
  },
);

return results.filter((r) => r !== null); // Filter out any null results from interrupted operations
```

## Benefits
- ✅ Better UX for long-running operations (common in this project)
- ✅ No lost work on interruption - current operation completes
- ✅ Clear user feedback about shutdown state
- ✅ Resume capability - just re-run the same command
- ✅ Safety valve with double Ctrl+C for immediate exit

## Trade-offs
- Uses global state (`gracefulShutdown` flag on process object)
- Adds ~30-40 lines of code
- Slight complexity in pipeline execution flow

## User Experience

### Before (current behavior):
```bash
$ bun run pipeline ingest --after 2024-01-01
Fetching data for ethereum-optimism/optimism...
^C [Process killed immediately, no progress saved]
```

### After (with graceful shutdown):
```bash
$ bun run pipeline ingest --after 2024-01-01
Fetching data for ethereum-optimism/optimism...
^C
⚠️  Graceful shutdown initiated... Current operations will complete.
Press Ctrl+C again to force exit.
⚠️  Ingestion interrupted but current operations completed successfully!
💡 You can resume by running the same command again - the pipeline will skip already processed data.

$ bun run pipeline ingest --after 2024-01-01
[Resumes from where it left off]
```

10:T1578,# Enhancement: Add API cost estimation to ingestion pipeline

## Context
Running `bun run pipeline ingest` with large date ranges can unexpectedly consume thousands of GitHub API calls, potentially hitting rate limits:
- **Authenticated users**: 5,000 requests/hour
- **GitHub Apps**: 15,000 requests/hour

This is especially problematic for:
- Historical data ingestion (e.g., `--after 2024-01-01` on 20+ repos)
- First-time project setup
- Large active repositories with thousands of PRs/issues

### Real-world example:
- **23 repositories** × **52 weeks** × **~6 API calls per week** = **~7,176 API calls**
- **Outcome**: Rate limit exhaustion, 1-2 hour wait, failed ingestion

Users need visibility into API cost before committing to large ingestions.

## Proposal
Add `--estimate-only` flag and automatic pre-flight cost estimation that shows:
- Estimated API call count
- Risk level (LOW/MEDIUM/HIGH)
- Estimated duration
- Warning for HIGH risk operations

## Implementation

### Add cost estimation function to `cli/analyze-pipeline.ts`:

```typescript
// Simple API cost estimation helper
function estimateApiCalls(
  repositories: { owner: string; name: string }[],
  intervalCount: number,
): { total: number; risk: string; duration: number } {
  const baseCallsPerRepo = intervalCount * 6; // ~6 calls per interval (PRs, issues, commits)
  const total = repositories.length * baseCallsPerRepo;

  const risk = total > 2000 ? "HIGH" : total > 500 ? "MEDIUM" : "LOW";
  const duration = Math.ceil(total / 60); // ~60 calls per minute with rate limiting

  return { total, risk, duration };
}
```

### Add CLI flag to ingest command:

```typescript
program
  .command("ingest")
  // ... existing options
  .option(
    "--estimate-only",
    "Show API cost estimation without executing ingestion",
    false,
  )
```

### Add estimation logic before execution:

```typescript
// Calculate date range and intervals
const repositories = options.repository
  ? pipelineConfig.repositories.filter(
      (r) => `${r.owner}/${r.name}` === options.repository,
    )
  : pipelineConfig.repositories;

  dateRange.endDate && dateRange.startDate
    ? Math.ceil(
        (new Date(dateRange.endDate).getTime() -
          new Date(dateRange.startDate).getTime()) /
          (1000 * 60 * 60 * 24),
      )
    : parseInt(options.days || "7");

  repositories: repositories.length,
  intervals: intervalCount,
  estimatedApiCalls: estimate.total,

});

  console.log(`\n📋 INGESTION ESTIMATE`);
  console.log(`Repositories: ${repositories.length}`);
  console.log(`Time intervals: ${intervalCount}`);
  console.log(`Estimated API calls: ${estimate.total}`);
  console.log(`Risk level: ${estimate.risk}`);
  console.log(`Estimated duration: ${estimate.duration} minutes`);

  if (estimate.risk === "HIGH") {
    console.log(
      `\n⚠️  HIGH RISK: Consider using smaller date ranges or --repository flag`,
    );
  }

  rootLogger.warn(
    `⚠️  High API usage detected (${estimate.total} calls). Monitor rate limits closely.`,
  );
}
```

11:T1264,# Enhancement: Add graceful shutdown to CLI pipeline

## Context
Long-running ingestion pipelines (historical data ingestion spanning months) can take hours, especially for large active repositories. Currently, pressing Ctrl+C immediately terminates the process, losing all in-progress work.

This is common when:
- Ingesting historical data for the first time
- Running large date range imports (e.g., `--after 2024-01-01`)
- Processing multiple large repositories
- Debugging or testing ingestion locally

## Proposal
Add graceful shutdown handling that:
1. **First Ctrl+C**: Completes current operation, saves progress, then exits cleanly
2. **Second Ctrl+C**: Force exits immediately if user needs to stop now
3. Shows clear messaging about shutdown state
4. Allows resuming with same command (pipeline skips already-processed data)

## Implementation

### Add to `cli/analyze-pipeline.ts` (before program definition):

```typescript
// Graceful shutdown handler
let gracefulShutdown = false;
process.on("SIGINT", () => {
  if (!gracefulShutdown) {
    gracefulShutdown = true;
    (global.process as { gracefulShutdown?: boolean }).gracefulShutdown = true;
    console.log(
      "\n⚠️  Graceful shutdown initiated... Current operations will complete.",
    );
    console.log("Press Ctrl+C again to force exit.");
  } else {
    console.log("\n🔴 Force exit requested.");
    process.exit(1);
  }
});
```

### Update ingest command execution (in ingest action handler):

```typescript
try {
  await ingestPipeline(undefined, context);

  if (gracefulShutdown) {
    rootLogger.warn(
      "⚠️  Ingestion interrupted but current operations completed successfully!",
    );
    rootLogger.info(
      "💡 You can resume by running the same command again - the pipeline will skip already processed data.",
    );
  } else {
    rootLogger.info("✅ Ingestion completed successfully!");
  }
} catch (error: unknown) {
  if (String(error).includes("GRACEFUL_SHUTDOWN")) {
    rootLogger.warn(
      "⚠️  Ingestion gracefully interrupted. Progress has been saved.",
    );
    rootLogger.info("💡 Resume by running the same command again.");
    return;
  }
  throw error;
}
```

### Update `src/lib/pipelines/types.ts` mapStep to respect shutdown:

```typescript
const results = await pMap(
  inputs,
  async (item, index) => {
    // Check for graceful shutdown before processing each item
    if (
      global.process &&
      (global.process as { gracefulShutdown?: boolean }).gracefulShutdown
    ) {
      context.logger?.warn(
        `Graceful shutdown requested. Skipping remaining items after ${index}/${inputs.length}`,
      );
      throw new Error("GRACEFUL_SHUTDOWN");
    }
    return await operation(item, context);
  },
  {
    concurrency: Math.max(1, concurrency),
    stopOnError: false, // Continue processing other items even if one fails
  },
);

return results.filter((r) => r !== null); // Filter out any null results from interrupted operations
```

## Benefits
- ✅ Better UX for long-running operations (common in this project)
- ✅ No lost work on interruption - current operation completes
- ✅ Clear user feedback about shutdown state
- ✅ Resume capability - just re-run the same command
- ✅ Safety valve with double Ctrl+C for immediate exit

## Trade-offs
- Uses global state (`gracefulShutdown` flag on process object)
- Adds ~30-40 lines of code
- Slight complexity in pipeline execution flow
