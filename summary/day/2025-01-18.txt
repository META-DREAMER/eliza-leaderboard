}16:T28c0,**Is your feature request related to a problem? Please describe.**

Currently agents hosting twitter spaces can only start processing audio from other human speakers after the speakers are muted. This not only introduces delay in most situations but also makes the conversation flow feel less natural. On the other hand, agents sometimes have very long responses that basically become monologues and there is no way the human speakers can interrupt the agent to change the direction of conversation as needed.

**Describe the solution you'd like**

1. I propose that the agent should be always "listening" while others speak, so that the agent can already work on a prompt based on the context of the conversation and relevant knowledge to respond as soon as the others finish speaking or even jump into conversations if needed.

2. Allow the human speaker to use keywords such as stop, halt or anything else to the same effect to essentially tell the agentruntime to stop streaming the audio chunks from elevenlabs and start listening again straightaway.

**Additional context**

I took a first stab at my proposed solutions but didn't have any luck so far.

Some issues I faced
- I was not able to collect audio data, convert at fixed intervals and temporarily store as well as checking against RAG to get relevance scores which should be the trigger to send the prompt and generate response.
- The main issue with trying to get the agent to pick out "stop" and related keywords was that the audio capture came from both the human speaker and the agent which makes it difficult to recognise the stop request.

        // Log retrieved knowledge
        knowledgeData.forEach((k, index) => {
            elizaLogger.info(`[SttTtsPlugin] RAG Knowledge ${index + 1}:`, {
                text: k?.content?.text,
                score: k?.score,
                source: k?.source
            });
        });

        // Calculate relevance score with detailed logging
        let relevanceScore = 0;
        const scoreDetails: string[] = [];

        // Base score for any non-empty message
        if (text.length > 0) {
            relevanceScore += 0.2;
            scoreDetails.push("+0.2 (non-empty message)");
        }

        knowledgeData.forEach((k, index) => {
            if (!k?.content?.text) return;

            // Check for exact phrase matches
            if (k.content.text.toLowerCase().includes(text.toLowerCase())) {
                relevanceScore += 0.4;
                scoreDetails.push(`+0.4 (exact match in knowledge ${index + 1})`);
            }

            // Add base score for relevant knowledge
            relevanceScore += 0.2;
            scoreDetails.push(`+0.2 (relevant knowledge ${index + 1})`);
        });

        // Log final relevance calculation
        elizaLogger.info("[SttTtsPlugin] Relevance calculation complete:", {
            inputText: text,
            finalScore: relevanceScore,
            scoreBreakdown: scoreDetails,
            knowledgeCount: knowledgeData.length
        });

        return relevanceScore;
    } catch (error) {
        elizaLogger.error("[SttTtsPlugin] Error in checkRelevance:", error);
        return 0.5; // Default to 50% relevance on error
    }
}

private async shouldRespondToMessage(text: string): Promise<boolean> {
    const relevanceScore = await this.checkRelevance(text);
    const randomChance = Math.random();
    let shouldRespond = false;
    let reason = "";

    if (relevanceScore > 0.4) {
        shouldRespond = randomChance < 0.9;
        reason = "High relevance (>0.4), 90% chance to respond";
    } else if (relevanceScore > 0.2) {
        shouldRespond = randomChance < 0.7;
        reason = "Medium relevance (>0.2), 70% chance to respond";
    } else {
        shouldRespond = randomChance < 0.4;
        reason = "Low relevance, 40% chance to respond";
    }

    elizaLogger.info("[SttTtsPlugin] Response decision:", {
        inputText: text,
        relevanceScore,
        randomChance,
        shouldRespond,
        reason
    });

    return shouldRespond;
}

# Background

## What does this PR do?

It provides dependency injection-driven object management functions for Eliza's plugin system, enabling Providers, Actions, and Evaluators in the plugin to be initialized in a dynamic way. 
It also enables these objects to support multiple existence modes such as `Singleton` and `onRequest`, making instance management more flexible.
An abstract class of `BaseInjectableAction` is created at the same time. Through the `@property` decorator, the generation of ContentClass and its Template becomes more automated without the need for additional manual creation.

If you want to use this di plugin, your plugin exports will look like:

```
import { CreateResourceAction } from "./sampleAction";
import { SampleProvider } from "./sampleProvider";
import { SampleEvaluator } from "./sampleEvalutor";
import { PluginOptions } from "../types";

export const samplePlugin: PluginOptions = {
    name: "sample",
    description: "Enables creation and management of generic resources",
    actions: [CreateResourceAction],
    providers: [SampleProvider],
    evaluators: [SampleEvaluator],
    // separate examples will be added for services and clients
    services: [],
    clients: [],
};

export default samplePlugin;
```

**All the actions, providers, evaluators are `Class` instead of `Object`.**

So the normalization process is added to `agent/src/index.ts`'s `startAgents` method:

```typescript
import { normalizeCharacter } from "@elizaos/plugin-di";

const startAgents = async () => {
    // ... 

    if (charactersArg) {
        characters = await loadCharacters(charactersArg);
    }

    // Normalize characters for injectable plugins
    characters = await Promise.all(characters.map(normalizeCharacter));

    // ....
}
```

This `normalizeCharacter` method will normalize the plugin with dependency injection Class to the normal plugin.

## What kind of change is this?

Features (non-breaking change which adds functionality)

## Why are we doing this? Any context or related work?

1. The `Action` and `Provider` in some plugins hope to be initialized in a dynamic way rather than directly exporting an object.
2. Some `Provider`s may be shared among multiple `Plugin`s. They need to exist in a `Singleton` instance rather than creating an instance for each plugin.
3. There are many elements in `Action` that can be automated through decorator definitions, and this plugin provides a convenient abstract class.
