#32905 added the durable cutover hold (#22934), and it merged today. `drainCutoverHolds` promises that "a per-hold lease keeps replicas from running the same turn concurrently", but that only holds while a redelivery finishes within one lease period.

`packages/cloud/services/gateway-webhook/src/cutover-hold.ts` on develop does three things:

- It takes `SET NX EX 180` on `webhook:cutover-hold-lease:<dedupKey>`.
- It awaits `handlers.redeliver(held)`. That is `redeliverHeldWebhook` → `processMessage` → `sendPersonalSharedReply`, which runs a full Personal Shared turn: up to `PERSONAL_SHARED_TURN_TIMEOUT_MS = 15 * 60_000` per attempt (`webhook-handler.ts:78`), with up to `PERSONAL_SHARED_ATTEMPTS = 3` attempts.
- It always runs `finally { await redis.del(leaseKey) }`.

The hold stays due in `webhook:cutover-holds` while it is being redelivered, and every replica polls every 2 s (`index.ts:256`, `CUTOVER_HOLD_DRAIN_INTERVAL_MS = 2_000`). `draining` only stops new drains, so during a rolling deploy the old pod keeps its in-flight redelivery while the new pod polls. So:

1. **Duplicate turn:** once a redelivery runs past 180 s, another replica re-acquires the lease and delivers the same held turn again.
2. **Lease stolen on release:** the first drainer's unconditional `del` then deletes the second drainer's lease, so a third can join.

`redeliverHeldWebhook` calls `processMessage` directly, so the ingress-side processing claim does not protect this path. The user receives the reply twice. On private Blooio/Twilio replies the gateway has no egress lease.

# Change

`drainCutoverHolds` (`cutover-hold.ts`):

- The lease value is a per-drain `randomUUID()` token.
  - Before, it was `String(now)`, and the Redis adapters JSON-parse reads, so that value came back as a number.
- While the redelivery runs, the lease is renewed every third of its period. Renewal stops, with a warning, if the lease is no longer ours. A failed renewal is logged and retried on the next tick.
- The lease is released only if we still own it.
- `options.leaseSeconds` (default 180, unchanged) lets tests outlive a lease in real time.
- **Crash recovery is unchanged:** a dead drainer's lease still lapses within one period.
- Renewal and release are atomic compare-and-act operations: `GatewayRedis.expireIfEquals` / `delIfEquals`, each a single server-side Lua script on the ioredis, ioredis-mock and Upstash adapters.
  - A GET-then-act check (the first revision) left a one-round-trip gap in which the lease could change hands. Thanks @ss251.
  - The hand-written `MemoryRedis` fake in `personal-private-egress.test.ts` implements the two methods too.

  WEATHER ranks above ARCHIVE. Then it asserts the tiered order keeps that
  ranking.

  - the handoff times out;

# Change

`build-mobile-bundle.ts` resolves the six platform-neutral remote-control protocol modules to source: `crypto`, `controller`, `runtime-store`, `secure-store-contract`, `cloud-client`, `cloud-endpoints`.

- Their imports are only `node:crypto`, `@elizaos/core`, `@elizaos/core/contracts/remote-control` and `@elizaos/plugin-elizacloud/cloud-config/domain-contract`. I checked each file's imports.
- The longer alias wins over the `@elizaos/plugin-browser` stub.
- `remote-control/browser-controller` stays stubbed: it imports `../browser-service` and `../targets/remote-device-target`.
- The plugin root and all other subpaths are unchanged.

**Android Play cloud policy** (`packages/app/scripts/mobile/android/cloud-policy.ts`, `strip.ts`):

- `@elizaos/capacitor-network-policy` joins `ANDROID_CLOUD_STRIPPED_NATIVE_PLUGINS`.
  - It serves on-device model downloads: only `ElizaAgentService` and `ElizaBionicInferenceServer` use it natively, and both are already stripped.
  - The JS side is a bare side-effect import in `native-plugin-entrypoints.ts`, next to other stripped plugins (camera, canvas, appblocker, bun-runtime).
- `PasswordsActivity` and `BrowserNativeMessagingService` join `ANDROID_CLOUD_STRIPPED_COMPONENTS`, and their Java sources join `ANDROID_CLOUD_STRIPPED_JAVA_FILES`.
  - `CredentialManagerPlugin.java` is stripped too. Its only behavior is starting `PasswordsActivity`, and nothing in the cloud tree registers it.
- `ANDROID_CLOUD_STRIPPED_QUERY_PACKAGES` (Chromium placeholder, Bitwarden, 1Password, healthdata) replaces the one-off healthdata `<queries>` regex in `strip.ts`.
- `ANDROID_CLOUD_MANIFEST_MERGER_REMOVED_QUERY_PACKAGES` adds a `tools:node="remove"` marker for `${elizaChromiumPackageName}`, because the kept `plugin-native-browser-surface` library re-adds it through manifest merge (same pattern as `ANDROID_CLOUD_MANIFEST_MERGER_REMOVED_PERMISSIONS`).
- **Bug fix:** `ANDROID_CLOUD_STRIPPED_PERMISSIONS` listed `"android.permission.USE_FULL_SCREEN_INTENT"`, while `removeAndroidPermissionRequests` prepends `android.permission.`. The entry never matched, so the permission always leaked. It is now `"USE_FULL_SCREEN_INTENT"`.
- The Play allowlists themselves are unchanged (the manifest `queryPackages` allowlist is still `[]`).
  - Everything above makes the cloud build meet the existing policy.
  - Allowing the password-manager surface in the Play client would be a separate product/policy decision.

For the mobile bundle fix, I looked at two alternatives:
- **Un-stubbing plugin-browser subpaths wholesale** would pull desktop-only modules into the phone bundle.
- **Aliasing only `crypto`** fixed the first 6 errors and exposed the same failure for `cloud-endpoints` (`DEFAULT_DIRECT_CLOUD_BASE_URL`, `stripTrailingSlashes`, … imported by `packages/ui/src/api/client-cloud.ts:79-84`). So the fix covers the protocol-module class.
