14:Tc39,## Summary

Generated media that arrives as a `data:` URL (Google Imagen images, TTS audio, voice-first audio) is undeliverable on Discord and Telegram. Discord's SDK resolves the string as a filesystem path (ENOENT, caption lost with it); Telegram's `sendMedia` throws `File not found at path: data:image/png;base64,<whole blob>`, aborts the reply before the text is sent, and logs the full base64 payload twice.

## Where (develop `c2bb8860be`)

- Producers: `packages/agent/src/services/media-generation.ts:98-103` `bytesToAudioDataUrl` → `data:audio/mpeg;base64,…` (used at `:201` for TTS); `packages/core/src/features/advanced-capabilities/actions/generateMedia.ts:227` `data:image/png;base64,${result.imageBase64}` for base64-only image providers; `packages/core/src/services/message/delivery.ts:155` voice-first `data:audio/wav;base64,…`.
- The media-persist hook that would rewrite these into `/api/media/<sha>.<ext>` handles (`packages/agent/src/api/media-runtime.ts:127-151`, phase `outgoing_before_deliver`) runs from `processor.ts:713/1303/1500` and the autonomy execution facade; the action callback that delivers `GENERATE_MEDIA` output reaches the connector send handlers without passing through it.
- Discord: `plugins/plugin-discord/utils.ts:339-341` wraps the string in `AttachmentBuilder("data:…")`; for audio/video the guarded fetch rejects non-http and the catch at `:372-377` falls through to the same `AttachmentBuilder("data:…")`; discord.js 14.27.0 `DataResolver.resolveFile` then does `path.resolve` + `fs.stat` → ENOENT, and because files ride on the last text chunk (`utils.ts:690-700`) the caption in the same `channel.send` is lost too.
- Telegram: `plugins/plugin-telegram/src/messageManager.ts:1121-1160` sends attachments in a `Promise.all` before the text; `:1425-1428` throws `File not found at path: ${mediaPath}` with the whole data URL; `:1464-1476` `logger.error({ mediaPath, error: error.message })` logs the blob twice; the rethrow aborts `sendMessageInChunks`, and the turn's `delivery_started` marker (`:1575-1610`) refuses a replay.
- Slack: `plugins/plugin-slack/src/service.ts:2776-2793` rejects via the fetch guard and logs `{ url: media.url }`, i.e. the blob.

## Input → wrong output

`GENERATE_MEDIA` with the Google image provider (base64-only) or any TTS request → on Discord the caption and image are both lost (ENOENT); on Telegram nothing reaches the user, the log carries megabytes of base64, and the turn cannot be retried. Providers that return https URLs (OpenAI) work, which matches the live Discord evidence in PR #20460.

## Fix direction

Run the media-persist hook on action-callback deliveries too (so `data:` becomes a canonical media-store handle) and make Discord and Telegram resolve store handles to bytes; or decode `data:` URLs into a Buffer in `buildOutboundDiscordAttachment` and Telegram `sendMedia` (`{ source: buffer }` for Telegraf). Never put a `data:` payload into an error message or a log field (log a hash or length instead). Telegram should send text independently of attachments so one bad attachment cannot suppress the reply.
15:T5ee,## Summary

The agent export bundle contains the agent's decrypted `settings.secrets`, and the import path writes a bundle's `settings.secrets` straight into the new agent, although the export is documented as stripping secrets.

## Where (develop `c2bb8860be`)

- `packages/agent/src/services/agent-export.ts:743-747` reads the agent through `db.getAgentsByIds`; `plugins/plugin-sql/src/base.ts:645-663` `mapAgentRow` runs `transformAgentSettings(agent, decryptedCharacter)`, so `agent.settings.secrets` is plaintext.
- `agent-export.ts:921-923` strips only `runtime.character.secrets` into `characterConfig`; `:932` places the full `agent` record in the payload untouched.
- `agent-export.ts:995-1002` on import strips `secrets` from `characterConfig` but spreads `payload.agent` (including `settings.secrets`) into `agentData` before `createAgents`.

## Input → wrong output

`POST /api/agent/export` → the decrypted JSON inside the `.eliza-agent` bundle carries every provider key under `agent.settings.secrets`; the only barrier is the bundle password. `POST /api/agent/import` with a bundle whose `agent.settings.secrets` was edited plants those values (keys, endpoints) into the newly created agent.

## Fix direction

Delete `agent.secrets` and `agent.settings.secrets` (and vault-shaped keys) in `extractAgentData` before building the payload, strip the same fields from `payload.agent` in `restoreAgentData`, and add a test that decrypts the produced bundle and asserts no `settings.secrets` is present.
