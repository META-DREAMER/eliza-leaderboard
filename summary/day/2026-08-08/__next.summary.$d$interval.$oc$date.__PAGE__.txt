1. Query parsing yields only a *candidate* (`resolveAuthSuccessCandidate`). Known-provider `*_connected` markers or `connection_id` alone never claim success.
2. Success requires **one** of:
   - A **callback-minted short-lived HMAC proof** verified by public `GET /api/v1/oauth/success-proof/verify?proof=…` (covers Twitter/Discord and sessionless API-key OAuth returns to `/auth/success`), and when a `connection_id` is present a sessioned browser must also own that connection; or
   - An **authenticated ownership lookup** `GET /api/v1/oauth/connections/:id` returning an active connection for the current org/user (sessioned browsers without a proof).
3. Until verification succeeds the page stays **pending**, then **verified**, **unverified**, or **unavailable** (distinct UI for transport/5xx).

**Backend changes:**

- `mintOAuthSuccessProof` / `verifyOAuthSuccessProof` (HMAC, ~10 min TTL, nonce) in cloud shared OAuth services
- Generic OAuth2, Twitter (OAuth1a + OAuth2), and Discord callbacks attach `proof` only when the redirect path is exactly `/auth/success`
- Public path allowlist for `/api/v1/oauth/success-proof/verify`
- Reserved markers (`proof`, `platform`, `connection_id`, known `*_connected`) are cleared before rewriting so a prior success URL cannot retain a valid proof across an error redirect

**Provider contracts preserved:**

| Callback | Success query shape on `/auth/success` |
| --- | --- |
| Generic OAuth2 | `{platform}_connected=true&platform=…&connection_id=…&proof=…` |
| Twitter | `twitter_connected=true&platform=twitter&proof=…` (no connection_id) |
| Discord | `discord=connected&platform=discord&discord_connected=true&proof=…` |

Forged marker-only URLs stay **unverified**.

# Background

## What does this PR do?

Makes lean-chat Google Calendar connect/sync **workable and safe**:

1. **Scheduling** — Seeded in lean-chat because Calendar is already always selected and hard-depends on it.
2. **Google Workspace (gated)** — Loads only on explicit Google signals (entries enable, configured googlechat, or full `GOOGLE_CLIENT_ID`+`SECRET`+`REDIRECT_URI`). Empty `{}` googlechat does **not** load. **`enabled: false` is a final deny**.
3. **Mobile order** — Companion adds run **before** the mobile allow-list so Workspace cannot re-enter iOS/Android load sets.
4. **Trusted OAuth URLs only** — Verified handoffs require known Google/Microsoft authorize hosts/paths; untrusted hosts refused.
5. **CALENDAR_SOURCES** — Verified only for allowlisted handoff states; Google → `[CONFIG:google-workspace]`; Microsoft → `[CONFIG:calendar]` with `MICROSOFT_*` pluginParameters.
6. **CONNECTOR** — Rejects calendar-feed connect phrasing; sanitized config errors; no success without trusted auth URL.
7. **PLUGIN toggle test** — regression lock for cloud self-API auth headers (runtime already on develop).

16:T1a9b,# Problem

Live reminder acks read as machine output, twice over. Observed:

```
Created trigger "take vitamins" (once at 2026-08-09T08:00:00Z). on it. set for 8am every morning.
```

Three defects in one reply:

1. **Raw ISO timestamp (and cron / interval-ms) in chat.** `describeSchedule` in `packages/agent/src/actions/trigger.ts` rendered `once at ${scheduledAtIso}`, `cron ${cronExpression}`, and `every ${intervalMs}ms` straight into the user-facing ack.
2. **Double-speak.** The action returned `verifiedUserFacing` text without `turnComplete`, so the planner-loop's `combinedVerifiedToolTextAndProse` glued the mechanical line to the evaluator's restatement of the same fact — the same class #17975 fixed at the voice seam.
3. Sibling ops (update / delete / toggle / run) echoed the internal `Trigger: …` displayName convention back at the user.

Complementary to #18026 (recurrence correctness): that fixed WHAT gets scheduled; this fixes what the user READS.

# Fix

- **New `packages/agent/src/triggers/humanize.ts`** — schedule phrasing for chat: cron → human recurrence (`every morning at 8am` for `0 8 * * *`, `every Monday at 9am`, `every weekday at 9am`, `every 15 minutes`, `on the 1st of every month at 9am`); one-shots → countdown or friendly local time (`in 5 minutes`, `today at 3:30pm`, `tomorrow at 8am`, `on Wednesday at 8am`, `on Aug 20 at 8am`); intervals → largest evenly-dividing unit (`every 12 hours`). Unrecognized shapes degrade to a neutral phrase (`on a custom schedule`) — never the raw value. Clock times render process-local: the local-first deployment runs the agent on the user's own machine.
- **`TRIGGER` replies humanized** (`trigger.ts`): create / update / delete / toggle / run use those phrases and strip the `Trigger:` prefix. The machine detail moves into the ActionResult's structured `data` (`scheduledAtIso`, `cronExpression`, `intervalMs`) where the planner and telemetry can still read it.
- **One ack per turn.** Committed mutations (create / update / delete / toggle, including the idempotent already-exists replay) now set `turnComplete: true` — the same action-owned contract `LOGS` and `CONTACT` use, and the seam the #17975 voice dedupe keys on. Under the planner-loop's gated-FINISH contract the action's verified humanized ack is the turn's single user-facing message; the evaluator no longer restates it.

19:Te11,## Follow-up to #18085

#18085 made connector-account storage resolve lazily, but its review (on the pre-merge head) reproduced a real backend-transition race that the merged version still carries:

- **Masked boot-window write:** `upsertAccount` before the SQL adapter attaches lands in the in-memory fallback; after attachment every read resolves the fresh database wrapper, so `listAccounts` silently drops from 1 to 0 — the write is hidden, not durable.
- **OAuth split across `startOAuth`:** `createOAuthFlow` writes to the fallback, the provider attaches the adapter during the awaited `startOAuth`, and `updateOAuthFlow`/`completeOAuth` then target the database wrapper that has no flow — "Unknown, expired, or already used OAuth flow state".

## Fix

`packages/core/src/connectors/account-manager.ts`: the private storage getter now returns one stable facade. Every operation resolves the backend and, when a durable backend has appeared while the fallback still holds state, first drains the fallback into it (accounts + pending unexpired flows) on a serialized migration chain, then clears the fallback. Handoffs cannot interleave; a failed handoff rejects the awaiting operation and keeps the fallback state for the next attempt (no silent loss). `getStorage()` consumers (routes, providers, credential resolver) get the same facade, so external holders cannot straddle the transition either.

## Tests (`account-manager.test.ts`, new `fallback-to-durable state handoff` describe — all fail on develop)

26:T99e,## Symptom

Agent creation started failing on 2026-08-06, after eleven consecutive clean days, and has not recovered.

By job finalisation day (`jobs` where `type='agent_provision'`, production):

```
2026-07-29 → 2026-08-05     0 failures across 63 jobs
2026-08-06 onward           20 failed / 124 jobs over the trailing 7 days = 16.1% hard failure
```

This is a dated regression, not background noise. The eleven-day clean streak immediately before it is what makes the break legible.

## What the user experiences

The happy path is fast — **66 s p50** from message to a running container. The failure path is not: retries and the job watchdog mean roughly **52 minutes** elapse before the user is told anything went wrong, and what they are told then sends them to a control panel.

Worse, until #17924 lands, each of these failures converts into a *permanent* lockout: the resulting `error` row blocks that organization from ever provisioning again through the onboarding chat. That is the mechanism behind the population in that issue growing from 60 to 69 in fifteen hours.

## Where to start

Three candidate contributors are already known and measured; this issue is to establish which of them accounts for the 16%, and whether there is a fourth:

1. **Fleet capacity.** 193 counted slots against 168 declared, four nodes over their ceiling, and **3 free slots** across the whole fleet (#17866). Placement funnels onto whichever node has room, which is how the 2026-08-06/07 outage happened (#17880).
2. **The proactive autoscaler cannot add nodes.** `evaluateCapacity` gates scale-up on `enabled.length < maxNodes` with `maxNodes` hardcoded to **12** (`node-autoscaler.ts:65`, no env override) against **14 enabled** — so it can only drain. On-demand autoscale during a provision still works (a node cold-started in 58 s on 08-08), but nothing pre-warms.
3. **The replacement-cleanup fence deadlock** (#17924 comment): fences accrue 3 → 4 → 6 over 06/07/08 Aug and are never retired, and a stranded fence makes the enqueue refuse with 409.

Note the daemon running production provisioning is currently pinned well behind `main`, so fixes already merged for this area are not in effect there.

## Suggested acceptance

Failure rate back under 1% over a rolling 7 days, and the time-to-user-notification on the failure path brought down from ~52 minutes to something a person will wait through.

Related: #17866, #17880, #17924.

27:T8b5,## Symptom

On the sign-in screen — the first thing anyone sees — the page paints almost instantly but the user cannot act for up to **4.7 seconds on production**. "Loading sign-in options…" stays on screen the whole time.

## Measurement

Browser timing on `app-staging.elizacloud.ai/login`:

```
first-contentful-paint    92 ms
load complete            153 ms
/steward/auth/providers  1242 ms      <- the only resource over 400 ms
```

`curl`, five consecutive runs per environment:

```
/steward/auth/providers   staging: 3.53  0.78  0.79  0.74  2.75  s
                          PROD:    3.71  0.78  0.76  0.75  4.69  s

/api/health (same Worker) staging: 0.087 s        PROD: 0.065 s
```

So the endpoint is roughly **10× slower warm** and **up to 60× slower cold** than a neighbouring route on the same Worker. Production is consistently the worse of the two.

## Why this one endpoint gates everything

The sign-in buttons (passkey, magic link, Google/Discord/GitHub, EVM/Solana) are all rendered from this response, so its latency is the user's time-to-first-action. Everything else on the page is already there at 92 ms.

## What to look at

The shape of the numbers — a fast floor around 750 ms with occasional multi-second spikes — reads like a per-request upstream call with no caching, plus a cold-start path. Worth establishing before fixing:

1. Is this served by the cloud Worker directly or proxied to a Steward backend? If proxied, the 750 ms floor is probably the upstream round trip.
2. Is the provider list effectively static? The set of enabled auth providers changes at deploy/config time, not per request — if so it is cacheable with a generous TTL, and the spikes disappear with the cold path.
3. If a cache layer already exists here, check whether it is actually enabled in each environment before adding another.

Whatever the remedy, state explicitly what could go stale and how a provider change propagates — silently serving a removed provider on a login screen is worse than the latency.

## Suggested acceptance

Time-to-interactive on the login screen under ~300 ms at p95, in production, measured the same way as above.

Found during a QA pass of the app surfaces.

A lone surrogate in an Anthropic stop sequence, or in an OpenAI/Anthropic tool description/schema, therefore still reaches captured request JSON as a \ud8xx escape. This contradicts the merged comment that every outgoing string is forced well-formed.

At packages/core/src/runtime/planner-rendering.ts:79-90 and packages/core/src/runtime/planner-loop.ts:2279-2281, the marker count is computed from requested head/tail lengths before the helpers back off at surrogate boundaries. Exact repro:

33:T17ce,## Summary

Fixes #18054.

Anonymous navigation to `/auth/success` no longer renders a trusted "Connected" card from query parameters alone.

**Verification contract (this head `084b5512549b7d1a632dc00c8b8d786bfb199035`):**

1. Query parsing yields only a *candidate* (`resolveAuthSuccessCandidate`). Known-provider `*_connected` markers or `connection_id` alone never claim success.
2. Success requires **one** of:
   - A **callback-minted short-lived HMAC proof** verified by public `GET /api/v1/oauth/success-proof/verify?proof=…` (covers Twitter/Discord and sessionless API-key OAuth returns to `/auth/success`), and when a `connection_id` is present a sessioned browser must also own that connection; or
   - An **authenticated ownership lookup** `GET /api/v1/oauth/connections/:id` returning an active connection for the current org/user (sessioned browsers without a proof).
3. Until verification succeeds the page stays **pending**, then **verified**, **unverified**, or **unavailable** (distinct UI for transport/5xx).

**Backend changes:**

- `mintOAuthSuccessProof` / `verifyOAuthSuccessProof` (HMAC, ~10 min TTL, nonce) in cloud shared OAuth services
- Generic OAuth2, Twitter (OAuth1a + OAuth2), and Discord callbacks attach `proof` only when the redirect path is exactly `/auth/success`
- Public path allowlist for `/api/v1/oauth/success-proof/verify`
- Reserved markers (`proof`, `platform`, `connection_id`, known `*_connected`) are cleared before rewriting so a prior success URL cannot retain a valid proof across an error redirect

**Provider contracts preserved:**

| Callback | Success query shape on `/auth/success` |
| --- | --- |
| Generic OAuth2 | `{platform}_connected=true&platform=…&connection_id=…&proof=…` |
| Twitter | `twitter_connected=true&platform=twitter&proof=…` (no connection_id) |
| Discord | `discord=connected&platform=discord&discord_connected=true&proof=…` |

Forged marker-only URLs stay **unverified**.

Live reminder acks read as machine output, twice over. Observed:

```
Created trigger "take vitamins" (once at 2026-08-09T08:00:00Z). on it. set for 8am every morning.
```

Three defects in one reply:

1. **Raw ISO timestamp (and cron / interval-ms) in chat.** `describeSchedule` in `packages/agent/src/actions/trigger.ts` rendered `once at ${scheduledAtIso}`, `cron ${cronExpression}`, and `every ${intervalMs}ms` straight into the user-facing ack.
2. **Double-speak.** The action returned `verifiedUserFacing` text without `turnComplete`, so the planner-loop's `combinedVerifiedToolTextAndProse` glued the mechanical line to the evaluator's restatement of the same fact — the same class #17975 fixed at the voice seam.
3. Sibling ops (update / delete / toggle / run) echoed the internal `Trigger: …` displayName convention back at the user.

Complementary to #18026 (recurrence correctness): that fixed WHAT gets scheduled; this fixes what the user READS.

# Fix

- **New `packages/agent/src/triggers/humanize.ts`** — schedule phrasing for chat: cron → human recurrence (`every morning at 8am` for `0 8 * * *`, `every Monday at 9am`, `every weekday at 9am`, `every 15 minutes`, `on the 1st of every month at 9am`); one-shots → countdown or friendly local time (`in 5 minutes`, `today at 3:30pm`, `tomorrow at 8am`, `on Wednesday at 8am`, `on Aug 20 at 8am`); intervals → largest evenly-dividing unit (`every 12 hours`). Unrecognized shapes degrade to a neutral phrase (`on a custom schedule`) — never the raw value. Clock times render process-local: the local-first deployment runs the agent on the user's own machine.
- **`TRIGGER` replies humanized** (`trigger.ts`): create / update / delete / toggle / run use those phrases and strip the `Trigger:` prefix. The machine detail moves into the ActionResult's structured `data` (`scheduledAtIso`, `cronExpression`, `intervalMs`) where the planner and telemetry can still read it.
- **One ack per turn.** Committed mutations (create / update / delete / toggle, including the idempotent already-exists replay) now set `turnComplete: true` — the same action-owned contract `LOGS` and `CONTACT` use, and the seam the #17975 voice dedupe keys on. Under the planner-loop's gated-FINISH contract the action's verified humanized ack is the turn's single user-facing message; the evaluator no longer restates it.

3b:Te11,## Follow-up to #18085

#18085 made connector-account storage resolve lazily, but its review (on the pre-merge head) reproduced a real backend-transition race that the merged version still carries:

- **Masked boot-window write:** `upsertAccount` before the SQL adapter attaches lands in the in-memory fallback; after attachment every read resolves the fresh database wrapper, so `listAccounts` silently drops from 1 to 0 — the write is hidden, not durable.
- **OAuth split across `startOAuth`:** `createOAuthFlow` writes to the fallback, the provider attaches the adapter during the awaited `startOAuth`, and `updateOAuthFlow`/`completeOAuth` then target the database wrapper that has no flow — "Unknown, expired, or already used OAuth flow state".

## Fix

`packages/core/src/connectors/account-manager.ts`: the private storage getter now returns one stable facade. Every operation resolves the backend and, when a durable backend has appeared while the fallback still holds state, first drains the fallback into it (accounts + pending unexpired flows) on a serialized migration chain, then clears the fallback. Handoffs cannot interleave; a failed handoff rejects the awaiting operation and keeps the fallback state for the next attempt (no silent loss). `getStorage()` consumers (routes, providers, credential resolver) get the same facade, so external holders cannot straddle the transition either.

## Tests (`account-manager.test.ts`, new `fallback-to-durable state handoff` describe — all fail on develop)
