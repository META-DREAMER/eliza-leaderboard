14:T899,**Is your feature request related to a problem? Please describe.**

`ContextRegistry` seeds ~39 "LifeOps personal assistant" context definitions unconditionally at boot (`packages/core/src/runtime/default-contexts.ts`, registered via `_initializeCore` → `tryRegisterMany(DEFAULT_CONTEXT_DEFINITIONS)`, `runtime.ts`). Per-turn selection (`listAvailableContextsForRole` → `ContextRegistry.listAvailable`) filters only by role gate. For a character built around a narrower domain (e.g. a single-purpose trading/social-posting agent with no email/calendar/contacts/phone/health/screen_time/subscriptions/payments/tasks/goals/todos/game/browser/files/terminal/code plugin loaded), the full catalog still renders into the Stage-1 routing prompt every turn via `formatAvailableContextsForPrompt`/`{{availableContexts}}`, burning prompt tokens on categories the agent can never act on — for a 24/7 autonomous agent this compounds daily.

There's no supported extension point to trim it: `compose_state_providers` filters a different registry (provider names), and `pre_model`/`post_model` only see the already-rendered prompt string.

**Describe the solution you'd like**

An `unregister(id)` (or `unregisterMany`) method on `ContextRegistry`, or a constructor/character-level option to seed a reduced definition set (e.g. `Character.contexts?: { exclude?: AgentContext[] }` consulted in `listAvailableContextsForRole`), so a non-LifeOps deployment can drop irrelevant contexts without patching core.

**Describe alternatives you've considered**

- Regex-stripping the rendered catalog lines out of the prompt in a `pre_model` pipeline hook — works, but fragile (breaks silently if `formatAvailableContextsForPrompt`'s line format changes) and duplicates the id list outside the registry.
- Reaching into `ContextRegistry`'s private `#definitions` field — not viable, it's a genuine private class field.

**Additional context**

Confirmed still open on `develop` as of this writing — `ContextRegistry` (`packages/core/src/runtime/context-registry.ts`) is unchanged from our vendored pin (`184a4cc8`): `register`/`registerMany`/`tryRegister`/`tryRegisterMany`/`listAvailable` only, no removal path.15:T135f,Record model calls, context choices and tool results for each app-chat turn.

## #31464: per-account Discord disconnect (partial, `Refs`)
`deleteAccount` used to be a no-op. It now works as follows:

1. **Persist a disabled policy first.** It goes in the runtime cache, keyed by account id and a SHA-256 fingerprint of the token. The token itself is never stored.
2. **Disconnect the account.** `DiscordService.disconnectAccount`:
   - blocks new messages for that account only;
   - drains its admitted turns, within the existing shutdown-drain timeout;
   - tears down its client, login retry, debouncer, managers and audio sinks.
3. **Siblings are unaffected.** Other accounts keep running, and the default alias moves to a remaining account.
4. **Failures are retryable.** A teardown failure throws before the manager deletes its row, and a retry repeats the teardown.
5. **Restart honors the policy.** After a restart, the service skips the disabled token and the provider stops listing it. Configuring a new token under the same id counts as a replacement and runs normally.

Remaining, outside this plugin:
- Removing the token from character settings or env. The host's settings owner has to do this; the plugin cannot write it.
- The issue's gating of all-channel onboarding completion, which belongs to the onboarding flow.

24:T92e,## Problem

`loadDefaultMasterKeySync` resolves a single persistent process-wide master key, but it is invoked **once per credential file** decoded by `account-storage.ts` (`masterKey()` → `decodeAccountRecord`). A `listAccounts()` over N pooled accounts therefore re-resolves the same key N times:

- **Keychain hosts:** N `readKeychainKeySync` child-process spawns, each ~80-150ms (cold Node boot + `@napi-rs/keyring` dynamic load + Secret Service round trip).
- **Passphrase hosts:** N scrypt derivations at 2^15 cost, ~90ms each.

With ~17 pooled subscription accounts this is **~2.5s of serialized, redundant key resolution**, and it runs inside the account-pool **lease** that every chat turn takes before its first model call.

### Observed impact

On a live deployment the `model:TEXT_EMBEDDING` inference span measured **1.4–9.6s** while the embedding backend itself (`curl` to the same local endpoint) answered in **20-40ms**. `strace` of a turn showed the lease blocking on ~17 keychain child processes (fd read of the base64 key) back-to-back before the embedding HTTP call was even issued — the span wraps the lease, so the redundant key work is charged to the embedding.

## Fix

Memoize the resolved key per `service/account` for the process lifetime.

- The value already lives in process memory for the duration of every vault/credential op; the cache is keyed by the same `service/account` tuple the resolver reads.
- **Security posture unchanged:** no key is ever fabricated, failures are never cached (transient keychain/passphrase errors still retry on the next call), and the `ELIZA_VAULT_PASSPHRASE` length guard still runs before the cache lookup.
- Adds a test-only `resetLoadDefaultMasterKeySyncCache()`.

## Test

`packages/auth/test/master-key-sync-cache.test.ts` asserts reference identity across a 17-call fan-out (simulating a `listAccounts()` decode loop):

- **Fails on clean develop:** un-memoized resolver returns a fresh `Buffer` per call → `expect(key).toBe(first)` fails.
- **Passes with the memo:** one resolution serves the whole fan-out.

The test tolerates the absence of the reset helper (falls back to a no-op) so the *behavioral* identity assertion is the bidirectional signal, not the new API symbol.

# Change

# Background

## What does this PR do?

The Capacitor Agent web fallback (`AgentWeb`) did **not** check `res.ok` in `start()`, `getStatus()`, or `stop()`. The agent HTTP server deliberately answers lifecycle/status failures with core `writeJsonError`'s `{ error: message }` body and a 4xx/5xx status (`packages/agent/src/api/agent-lifecycle-routes.ts`):

- `POST /api/agent/start` → `503` "Agent runtime is not available and this server cannot boot one on demand" when the host cannot boot; or `500` with the reported state flipped to `"error"` on a failed boot.

Because the web fallback blindly parsed and returned the body, callers received a **malformed `AgentStatus`** missing the required `state`/`agentName`/`port`/`startedAt` fields:

- `start()` did `return data.status ?? data`, so on error it returned `{ error }` (no `state`).
- `getStatus()` and `stop()` did `return res.json()` directly, returning the raw `{ error }` body.

The server's designed `"error"` / not-bootable state was silently discarded, violating the repo DTO/error policy (a failed producer must yield an explicit error/unavailable state, not healthy-looking/partial data). This is an internal inconsistency: `chat()` in the same file already checks `res.ok` and throws.

**User-facing impact:** consumers cast the result to `AgentStatus` and read `.state`. `packages/app/src/main.tsx` `initializeAgent()` dispatches `AGENT_READY_EVENT` with the status, and `packages/ui/src/api/client-agent.ts` casts `Agent.start()`/`Agent.getStatus()` to `AgentStatus` and branches on `.state === "running"`. When a local-agent boot returns 503/500, the missing `.state` makes a failed boot surface as an unrecognizable status rather than the intended `error` state.

### Fix

In `web.ts`, added `res.ok` handling to the three methods (mirroring `chat()`):

- `start()` / `getStatus()`: when `!res.ok`, read the JSON body's `error` (falling back to `statusText`) and return a well-formed `{ state: 'error', agentName: null, port: null, startedAt: null, error: <message> }`.
- `stop()`: when `!res.ok`, return `{ ok: false }` instead of the raw error body.
