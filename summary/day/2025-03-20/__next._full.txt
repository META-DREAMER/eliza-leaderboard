Is your feature request related to a problem? Please describe.
Yes, this feature request addresses the challenge of ensuring data integrity when handling dynamic inputs in elizaos/eliza, such as API responses, user inputs, or LLM-generated JSON. Without proper validation, malformed data can lead to runtime errors, inconsistent behavior, or bugs that are hard to debug. For example, if eliza processes a JSON response expecting a confidence field as a number between 0 and 1, but receives a string or out-of-range value, it could cause unexpected failures or incorrect logic.
Describe the solution you'd like
I propose integrating TypeBox, a lightweight TypeScript library, to introduce type safety into eliza. TypeBox combines JSON schema validation with TypeScript type inference, providing both compile-time and runtime safety. Here’s how it could work:
Define Schemas: Create TypeBox schemas for key data structures, such as API responses:
typescript

import { Type, Static } from '@sinclair/typebox';

const ElizaResponseSchema = Type.Object({
  intent: Type.String(),
  confidence: Type.Number({ minimum: 0, maximum: 1 }),
  entities: Type.Array(Type.String())
});

type ElizaResponse = Static<typeof ElizaResponseSchema>;

Validate Data: Use TypeBox to validate incoming data at runtime:
typescript

function validateElizaResponse(json: unknown): ElizaResponse {
  const result = ElizaResponseSchema.safeParse(json);
  if (!result.success) throw new Error(`Validation failed: ${result.error.message}`);
  return result.data;
}

Integrate: Apply this to a small component (e.g., API response parsing) to start, ensuring data integrity without disrupting existing workflows.

This solution ensures eliza processes data safely, reducing errors and improving reliability.
Describe alternatives you've considered  
Zod: Another popular schema validation library for TypeScript. While Zod offers similar features (type inference, runtime validation), it has a slightly larger footprint and a different syntax that might feel less JSON Schema-like compared to TypeBox. TypeBox’s alignment with JSON Schema standards makes it more interoperable with existing systems.

Manual Type Guards: Writing custom type guards in TypeScript (e.g., isElizaResponse functions) can provide some safety but lacks the robustness of schema-based validation and doesn’t scale well for complex data structures.

No Validation: Continuing without validation risks runtime errors, especially as eliza scales to handle more dynamic data sources, which could degrade user experience or system stability.

Additional Context
TypeBox is lightweight (minimal overhead), widely used, and well-documented, making it an easy adoption for the Eliza team. It provides immediate benefits—error prevention, improved developer productivity through TypeScript integration, and a foundation for scaling to more advanced validation or formal methods in the future. Starting with a small integration allows the team to evaluate its impact with minimal risk, paving the way for broader adoption across elizaos/eliza.

## Overview

This document outlines the changes made to the agent management system in this update. The main focus has been on improving agent creation, plugin management, and secret handling, while providing a temporary solution for plugin discovery until the official registry is available.

## Temporary Changes

### Plugin Registry Access

The `usePlugins` hook has been temporarily modified to return a hardcoded list of available plugins instead of fetching from the GitHub registry:

```typescript
// packages/client/src/hooks/use-plugins.ts
export function usePlugins() {
```

When the GitHub registry is ready with published plugins, this code can be reverted to use the commented fetch request.

### PluginsPanel Component

The `PluginsPanel` component has been updated to handle both the temporary hardcoded plugin list and the future registry-based approach:

```typescript
// Get plugin names from available plugins
const pluginNames = useMemo(() => {
  const defaultPlugins = ['@elizaos/plugin-sql', '@elizaos/plugin-local-ai'];
  if (!plugins) return defaultPlugins;
  return [
    ...defaultPlugins,
    ...(Array.isArray(plugins) ? plugins : Object.keys(plugins))
      .map((name) => name.replace(/^@elizaos-plugins\//, '@elizaos/'))
      .filter((name) => !defaultPlugins.includes(name)),
  ];
}, [plugins]);
```

This ensures that:

1. Default plugins are always available
2. The component works with both array and object formats
3. Plugin names are properly normalized

### Agent Partial Update System

A significant addition is the `useAgentUpdate` and `usePartialUpdate` hooks that provide more intelligent handling of agent updates:

1. `usePartialUpdate` is a generic hook for handling updates to nested objects and arrays
2. `useAgentUpdate` builds on it to provide agent-specific update methods
3. This approach allows for more granular tracking of changes
4. Only changed fields are sent to the server during updates

### Improved Secret Management

The `SecretPanel` component has been completely redesigned to:

1. Track new, modified, and deleted secrets
2. Send only changed secrets during updates
3. Handle null values for secret deletion
4. Provide visual indicators for added/modified secrets

### Server-Side Secret Handling

A new `mergeAgentSettings` method has been added to the `BaseDrizzleAdapter` class:

```typescript
// packages/plugin-sql/src/base.ts
private async mergeAgentSettings(
  tx: DrizzleOperations,
  agentId: UUID,
  updatedSettings: any
): Promise<any> {
  // ...
  // Handle secrets with special null-values treatment
  if (updatedSettings.secrets) {
    const currentSecrets = currentSettings.secrets || {};
    const updatedSecrets = updatedSettings.secrets;

    // Create a new secrets object
    const mergedSecrets = { ...currentSecrets };

    // Process the incoming secrets updates
    for (const [key, value] of Object.entries(updatedSecrets)) {
      if (value === null) {
        // If value is null, remove the key
        delete mergedSecrets[key];
      } else {
        // Otherwise, update the value
        mergedSecrets[key] = value;
      }
    }

    // Replace the secrets in updatedSettings with our processed version
    updatedSettings.secrets = mergedSecrets;
  }
  // ...
}
```

This ensures that:

1. Secret updates are handled intelligently on the server
2. Null values are interpreted as deletion requests
3. Existing secrets are preserved if not explicitly changed

## Security Considerations

### Current State of Secret Encryption

Currently, the system does not encrypt secrets in the database. They are stored in plaintext within the agent's settings object. This is a security concern that should be addressed in a future update.

### Proposed Encryption Approach

Based on the codebase analysis, the best place to implement encryption for secrets would be:

1. **Client-side encryption in `SecretPanel`**: When a secret is added or modified, encrypt it before sending to the server
2. **Server-side handling in `mergeAgentSettings`**: Add logic to detect encrypted values and handle them appropriately
3. **Decryption on use**: Implement a secure method to decrypt secrets when they're needed by plugins

### Possible Implementation Path

The codebase already contains encryption methods in the Phala TEE module that could serve as a reference:

```typescript
// packages/cli/src/tee/phala/index.ts
async function encryptSecrets(secrets: Env[], publicKey: string): Promise<string> {
  // ...
}
```

A similar approach could be adapted for the agent secrets system, potentially using:

1. A derived key from user authentication
2. A separate encryption service
3. Integration with a key management system

## Future Recommendations

1. **Implement Secret Encryption**: As noted above, adding encryption for secrets should be a priority for future updates
2. **Simplify Plugin Management**: Consider adding support for plugin categories and better search/filtering
3. **Visual Plugin Configuration**: Add a UI for configuring plugin settings beyond just adding/removing them
4. **Plugin Activation Status**: Allow enabling/disabling plugins without removing them
5. **Secret Validation**: Add validation for secrets based on plugin requirements
6. **Fine-grained Access Control**: Implement permissions for which agents can access which secrets

## Migration Notes

When moving from the temporary plugin approach to the full registry:

1. Revert the `usePlugins` hook to use the fetch request
2. No other code changes are needed since the `PluginsPanel` component handles both data formats
3. Existing agents with plugins will continue to work since the plugin handling logic is format-independent

## Conclusion

This partial update provides a solid foundation for agent management with improved data handling, while offering a temporary solution for plugin discovery. The next major update should focus on security enhancements, particularly for secret management.
