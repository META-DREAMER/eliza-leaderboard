## Problem

Steward browser authority is serialized only inside one JavaScript realm. The SSO bridge queue, logout epoch, cookie-sync abort controller, passive `AuthTokenSync` dedupe, shared token mutation queue, refresh single-flight, and several callback/restore paths are module-local. Two same-origin tabs can therefore mutate the browser token and HttpOnly session cookie out of order.

Concrete failure classes reproduced from current source inspection:

- tab A can finish a stale token-to-cookie POST after tab B logs out;
- two accounts can leave localStorage bound to token B while the final HttpOnly cookie was set by token A;
- logout followed by a fresh login can let an older operation resume unless logout authority uses a non-resettable generation (ABA);
- a stale passive sync or refresh response can clear or republish authority owned by a newer tab.

This is pre-existing on `develop@63368527be1221e2b45236d308c87d5bc2f50b7d` and is not introduced by #30243. That PR explicitly limits its guarantee to the same browser realm; a bridge-local lock would be incomplete because cookie/token mutations also occur in login callbacks, refresh, startup restore, repair, first-run, native apps studio, and passive session mirroring.

## Acceptance criteria

- Use one origin-wide coordinator for every browser operation whose request/response can mutate Steward cookies or canonical token authority: session sync, nonce exchange, refresh, callback/restore writes, passive mirroring, logout, and cookie DELETE cleanup.
- Use a durable opaque logout generation stored separately from the UX auto-bridge marker. Advance it on every logout and never clear/reset it, so logout → fresh login → stale completion cannot pass an ABA check.
- Capture expected token/generation before work and revalidate inside the coordinator before persistence, before cookie mutation, after response settlement, and before publishing/clearing markers.
- Bound every network operation held by the coordinator with timeout/abort; a crashed or hung tab must not strand login/logout for the origin.
- Treat `session_ended` and `invalid_token` as definitive only at the documented server boundary, and clear only the exact authority that received the rejection.
- If origin-wide coordination is unavailable, automatic SSO must fail closed to ordinary login rather than claim a safe cross-tab bridge.
- Add deterministic two-context coverage for logout during persistence, logout during cookie sync, inverse A/B responses, ABA logout/login/resume, stale passive sync, refresh/logout overlap, and cleanup DELETE ordering.
- Pin live staging acceptance to an exact deployed SHA with two real same-origin contexts; mocked storage events alone are insufficient.

# Risk

**Medium.** This changes one-time SSO code custody, exchange finalization, local token publication, cookie synchronization, and logout ordering. A regression could strand a login, publish a stale token, navigate after a superseding exchange, or recreate a session after logout.

The implementation keeps the API contract narrow, serializes same-realm finalization, bounds cookie synchronization, and adds deterministic tests for StrictMode, unmount, state changes, out-of-order responses, stale persistence, navigation failure, cookie ordering, and logout races.

# What does this PR do?

It hardens both legs of the cloud SSO bridge.

1. **Abandoned mint custody**
   - Burns a minted one-time code exactly once if the route unmounts, changes authorization state, or cannot hand off.
   - Adds a sessionless, destruction-only `POST /burn` endpoint restricted to exact bridge origins.
   - Keeps successful handoff and StrictMode replay single-shot.

2. **Generation-safe exchange and recovery**
   - Consumes state/verifier once and ignores late results from superseded route generations.
   - Prevents stale exchanges from publishing a token or navigating.
   - Serializes token publication and server-cookie synchronization so the newest valid exchange wins.
   - Makes cookie synchronization abortable and bounded to 10 seconds.
   - Orders logout/account-switch teardown with exchange finalization and prevents any session POST from starting after a concurrent logout.
   - Recovers from rejected bridge redirects instead of leaving the app or join page on a permanent spinner.

The same-realm browser contract is covered. Cross-tab/cross-realm coordination is not claimed; the generation queue, abort controller, and logout epoch are module-local.

- Once a valid persistence begins, later valid generations are ordered after it and the newest one wins.
- A stale generation never navigates.
- Logout wins over an exchange still waiting on persistence or cookie synchronization.
- The burn endpoint remains destruction-only and exposes no validity oracle.

32:T1765,## Problem

`getOrCreateApiKeyHydration` races a background API-key hydration against a deadline so a hung attempt cannot hold the single-flight slot. The cache projection was chained off that **race**:

```ts
const decision = Promise.race([attempt, /* deadline timer → resolve(undefined) */]);
const projection = decision.then(async (result) => {
  if (!result) return;    // deadline won → attempt's result is abandoned
```

`attempt` appeared at only two places in the file — its definition and inside the race — so nothing consumed a late success. When the deadline won, a hydration that **subsequently succeeded** wrote nothing. The next request re-hydrated from scratch, so any key whose authoritative lookup routinely exceeds the deadline never populates and warms forever, which is the failure mode `#18246` is about.

Existing coverage did not reach it: the deadline test used an `authImpl` that never resolves — the one case where discarding the result is harmless. The uncovered neighbour is slow-but-successful.

## Why the obvious fix is wrong

Chaining the projection off `attempt` instead is a one-token change, and it trades the dropped write for a hang:

```
(fail) a hung hydration hits the deadline, frees the slot, and counts toward escape [5000.01ms]
```

`projection` is the promise registered with `executionCtx.waitUntil`, so pointing it at a never-settling `attempt` holds the Worker open indefinitely. The deadline is load-bearing.

## Fix

The two concerns are separate: the deadline exists to free the single-flight slot and count a strike, and abandoning the *write* was collateral rather than intent. So the race still governs the slot, and when the deadline wins, a non-blocking second stage projects the attempt's late result:

```ts
if (!result) {
  void attempt
    .then((late) => (late ? projectResolution(late) : undefined))
    .catch(() => undefined);
  return;
}
return await projectResolution(result);
```

The projection body is lifted into `projectResolution` so both stages share one implementation rather than duplicating the write-and-telemetry block. **Behaviour on the non-deadline path is unchanged** — the diff there is pure extraction.

The late stage is deliberately **best-effort**: it is not registered with `waitUntil`, because registering a possibly-never-settling attempt is exactly the hang above. On a Worker the isolate may be torn down before the late write lands. That is strictly better than guaranteed-abandoned, and a durable version would need its own bounded second deadline — happy to add that instead if maintainers prefer it.

# Background

## What does this PR do?

The fix: `stop()` advances an `epoch` and wakes any pending backoff sleep; the ladder captures the epoch on entry and returns after every `await` once it has moved; the backoff timer is stored and cleared instead of left dangling.
