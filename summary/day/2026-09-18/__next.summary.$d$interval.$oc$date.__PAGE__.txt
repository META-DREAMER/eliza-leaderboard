# Background

## What does this PR do?

The agent's outer gate admits any authenticated host session — a non-owner host
session resolves to `actorRole: USER` (`server.ts:1811-1848`) — and
`resolveBoundaryRole` maps any non-`isAuthorized` caller to `GUEST`
(`server-helpers-auth.ts:470`). Only `/api/apps/launch` checked
`canLaunchApps(actorRole)`, so a non-owner could:

- `POST /api/apps/relaunch` — stop then launch (fixed in the first commit),
- `POST /api/apps/install` — install a plugin (code execution),
- `POST /api/apps/load-from-directory` — load apps from an arbitrary directory,

# Background

## What does this PR do?

`buildPromptCacheKey` emitted `` `v5:${prefixHash}` `` and capped the result at
1024 characters. The canonical `prefixHash` is a 64-character SHA-256 hex digest,
so every generated `prompt_cache_key` was 67 characters. OpenRouter's Azure
upstream rejects `prompt_cache_key` longer than 64 characters with HTTP 400
(`maximum 64 characters, received 67`), which prevented a model reply during
onboarding.

The key is now a fixed-width digest of the complete prefix hash: re-hashing the
input keeps every input bit influential (so prefix hashes that differ only near
the end stay distinct) while the emitted key is exactly 64 characters. The
`eliza.prefixHash` / `promptSegments` sidecar and the Cerebras
`eliza-workflow-v1:<digest>` affinity key are unchanged.

# Background

## What does this PR do?

`getActionResultActionName` read only `result.data?.actionName` and otherwise
returned `"Unknown Action"`. Real executors carry the name elsewhere:

- multi-op actions report `{ actionName, action }` side by side — `LINEAR`
  (`plugins/plugin-linear/src/action.ts`), `BROWSER`, `MANAGE_PLUGINS`
  (`packages/core/src/features/plugin-manager/actions/plugin.ts:687`);
- some results attach the name at the top level.

When `data.actionName` was omitted, chain action summaries and the prompt
formatter (`formatActionResultsForPrompt`,
`packages/core/src/utils/action-results.ts:211`) printed `"Unknown Action"`,
losing which action ran and what it returned.

The helper now tries `data.actionName` → `data.action` → top-level `actionName`
→ top-level `action`, returning the first non-blank string, and still defaults
to `"Unknown Action"` when no carrier holds a usable name.

# Background

random `clientId` in the query, and a `crypto.randomUUID()` value can contain
the digits `2653`, so a correct endpoint (`ws://127.0.0.1:31337/ws?...`) failed
intermittently.

The test now parses the URL and asserts the endpoint (`ws:`,
`127.0.0.1:31337`, `/ws`) plus the `clientId` and `token` query values. It stubs
`crypto.randomUUID` to a deterministic id containing `2653`, so the dev-origin
digits are guaranteed present in the URL while the endpoint assertion still
fails if the dev origin is used.

# Background

## What does this PR do?

The agent's outer gate admits any authenticated host session — a non-owner host

`resolveBoundaryRole` maps any non-`isAuthorized` caller to `GUEST`
(`server-helpers-auth.ts:470`). Only `/api/apps/launch` checked
`canLaunchApps(actorRole)`, so a non-owner could:

- `POST /api/apps/relaunch` — stop then launch (fixed in the first commit),
- `POST /api/apps/install` — install a plugin (code execution),
- `POST /api/apps/load-from-directory` — load apps from an arbitrary directory,
- `POST /api/apps/create` — invoke the APP create action,
- `POST /api/apps/stop` and `POST /api/apps/runs/:runId/stop` — stop apps,
- `PUT /api/apps/permissions/:slug` — change app permission grants.

All of these now return 403 unless the actor is OWNER/ADMIN. `GET` permissions
and viewer-only run routes (attach/detach/heartbeat) are unchanged.

# Background

## What does this PR do?

`buildPromptCacheKey` emitted `` `v5:${prefixHash}` `` and capped the result at
1024 characters. The canonical `prefixHash` is a 64-character SHA-256 hex digest,
so every generated `prompt_cache_key` was 67 characters. OpenRouter's Azure
upstream rejects `prompt_cache_key` longer than 64 characters with HTTP 400
(`maximum 64 characters, received 67`), which prevented a model reply during
onboarding.

The key is now a fixed-width digest of the complete prefix hash: re-hashing the
input keeps every input bit influential (so prefix hashes that differ only near
the end stay distinct) while the emitted key is exactly 64 characters. The
`eliza.prefixHash` / `promptSegments` sidecar and the Cerebras
`eliza-workflow-v1:<digest>` affinity key are unchanged.
