# Background

## What does this PR do?

The group-room `requireMention` gate built `new RegExp(\`@?${escapeRegExp(localpart)}\`, "i")`
and tested it against the raw body with no word boundary. Because the localpart
was matched as a bare substring, any message containing the localpart inside
another word satisfied the gate. For short or common localparts this defeats
`requireMention` almost entirely — a bot at `@ai:example` dispatches on
`"let's wait for the build"` (the `ai` inside `wait`), runs the full inbound
path (`ensureConnection`, `createMemory`, `MESSAGE_RECEIVED`), and with
`MATRIX_AUTO_REPLY` on, replies unprompted.

The gate now requires the localpart to appear as a whole token, optionally
`@`-prefixed, using the same boundary shape the addressed-to gate uses in core
(`(^|[^\p{L}\p{N}_])@?<local>[^...]`) while keeping regex escaping.

# Background

## What does this PR do?

`EmailCurationPolicyEffect.kind` includes `"add_reason"`, but nothing consumed
it. A policy hook returning `{ kind: "add_reason", code, message }` had its
effect pushed into `decision.policyEffects` and then ignored, so:

- `decision.reasons` contained no entry for the hook's explanation;
- `bulkReviewForDecision` derived `reasonLabels` from `reasons` only, so the
  reviewer-facing rationale fell back to the literal text
  `"... because of insufficient signal."` even though the hook supplied a
  reason.

Grep on `develop` confirms the kind is declared once and referenced nowhere
else.

`reasonsFromEvidence` now takes the collected `policyEffects` and projects each
`add_reason` effect into a `"policy"` reason whose `label`/`reviewText` come from
the hook message and whose `citations` carry the effect citation when present.
Because the rationale is built from `reasons`, the hook's explanation now
appears there too and no longer falls back to "insufficient signal".

`readyChecks: [{ selector: "main, [role='main']" }]` on the rolodex probe never asserts anything the probe was not already getting. `probeRoute` calls `expectMainShell` for every route, and that requires:

```
main, [data-testid='home-view'], [data-testid='lifeops-shell'], [role='main'],
h1, [role='region'], [aria-label='Chat workspace']
```

`main, [role='main']` is a strict subset of that union, so the rolodex probe has had **no destination-specific assertion at all**. With `expectedUrl` satisfied, any rendered page passes: a wrong view, or a stranded shell at `/apps/relationships`, both go green.

## The fix

```ts
readyChecks: [{ selector: '[data-testid="relationships-view"]' }],
```

Not an invented selector. It is the one the repo already treats as canonical for this route:

- `scripts/ai-qa/route-catalog.ts:63` declares `"/apps/relationships": [{ selector: '[data-testid="relationships-view"]' }]`
- it renders at `plugins/plugin-relationships/src/components/relationships/RelationshipsSpatialView.tsx:157`
- `packages/app/test/ui-smoke/apps-session-route-cases.ts:97` already uses it as the readiness selector for `/apps/relationships` in this same Playwright suite
- `packages/app/test/ui-smoke/view-switching-core-matrix.ts:142` uses it as `readySelector` for the same route

That covers the contract as asked: the view is ready when its own root renders, an empty relationship graph still satisfies it because the testid is on the view rather than on its contents, and a failure to render leaves the testid absent so the probe fails instead of passing on the shell.
