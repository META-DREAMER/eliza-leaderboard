## Summary
Add an evaluator that measures per-step execution duration and asserts against bounds (max/min/target). This is foundational for performance benchmarking and simple SLAs.

## Goals
- Measure execution duration for each `run` step
- Expose timing data to evaluations
- Evaluate against `max_duration_ms`, optional `min_duration_ms`, and optional `target_duration_ms`

## Acceptance Criteria
1. New evaluator type `execution_time` supported by scenarios
2. Duration recorded for both Local and E2B environments
3. Evaluator passes when duration <= `max_duration_ms` (and >= `min_duration_ms` if provided)
4. Detailed message includes actual duration
5. Unit tests and example scenario added

## EvaluationEngine Changes
Add a new evaluator implementation:

```ts
// type: execution_time
class ExecutionTimeEvaluator implements Evaluator {
  async evaluate(params: EvaluationSchema, runResult: ExecutionResult): Promise<EvaluationResult> {
    if (params.type !== 'execution_time') throw new Error('Mismatched evaluator');
    const duration = runResult.durationMs ?? ((runResult as any).endedAtMs - (runResult as any).startedAtMs);
    if (duration == null || Number.isNaN(duration)) {
      return { success: false, message: 'No timing information available for this step' };
    }
    const tooSlow = duration > params.max_duration_ms;
    const tooFast = params.min_duration_ms != null && duration < params.min_duration_ms;
    const success = !tooSlow && !tooFast;
    return {
      success,
      message: `Execution time ${duration}ms (min=${params.min_duration_ms ?? '-'}, target=${params.target_duration_ms ?? '-'}, max=${params.max_duration_ms})`,
    };
  }
}
```

Register in `EvaluationEngine` constructor:

this.register('execution_time', new ExecutionTimeEvaluator());

**Root cause**: The `ensureDirectory` function was incorrectly passing parameters to `updateFile`. It was passing the full repository string (e.g., `"username/repo"`) as a single parameter, but `updateFile` expects separate `owner` and `repo` parameters.

**2. Remove GitHub repository references when using `--npm` flag**

When running `elizaos publish --npm`, we publish to npm only (skipping GitHub repo creation), but the package.json still included repository and bugs URLs pointing to a non-existent GitHub repository. This shows up on the npm package page as broken links.

**Root cause**: The publish flow was setting repository placeholders regardless of the --npm flag.

**Fix**: 
- Delete `repository` and `bugs` fields from package.json when `--npm` flag is used
- Make the `repository` field optional in `PackageMetadata` interface
- Only include repository in metadata when it actually exists
