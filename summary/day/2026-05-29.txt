14:T1c4e,## Summary

Native ElizaCloud agents are currently inconsistent after the Hetzner/control-plane cutover:

- A newly-created native agent can be listed, but provisioning fails after retries. One retry gets to `Sandbox health check timed out`; the final job error is `ELIZA_KMS_BACKEND=steward requires steward.{baseUrl, tokenProvider}`.
- An existing agent is marked `running` and the container log job proves the runtime is alive, but both the Cloud bridge endpoint and the public subdomain are unreachable.
- This does not look like a client app integration issue. The app-scoped Cloud API remains healthy; the failure boundary is native agent provisioning/routing.

Credentials, tenant identifiers, agent IDs, job IDs, host IPs, node names, and app-specific prompt/config content are intentionally redacted from this public issue. I can share exact IDs privately with maintainers if needed.

## Live evidence, redacted

Source baseline checked locally: current `origin/develop` at the time of testing.

### Existing running agent is alive over logs but unreachable over bridge/public ingress

`GET /api/compat/agents/:id/status` returns a running agent record similar to:

```json
{
  "status": "running",
  "lastHeartbeat": "recent timestamp",
  "bridgeUrl": "http://<docker-host>:<dynamic-bridge-port>",
  "webUiUrl": "https://<agent-id>.waifu.fun",
  "currentNode": "<node-id>",
  "databaseStatus": "ready"
}
```

But `POST /api/v1/eliza/agents/:id/bridge` with a JSON-RPC heartbeat returns:

```json
{
  "jsonrpc": "2.0",
  "id": "probe-heartbeat",
  "error": {
    "code": -32000,
    "message": "Sandbox bridge is unreachable"
  }
}
```

Direct probes to the saved bridge URL time out:

- `http://<docker-host>:<dynamic-bridge-port>/` -> timeout
- `http://<docker-host>:<dynamic-bridge-port>/api/health` -> timeout
- `http://<docker-host>:<dynamic-bridge-port>/health` -> timeout

Public ingress also fails:

- `https://<agent-id>.waifu.fun/` -> Cloudflare `502`
- `https://<agent-id>.waifu.fun/api/agents` -> Cloudflare `502`

However, `GET /api/compat/agents/:id/logs` completes and shows the container runtime is up:

```text
[eliza-api] Listening on http://0.0.0.0:2138
[eliza] Control UI: http://localhost:2138
[eliza] Running in server-only mode (no interactive chat)
[eliza-api] Serving dashboard UI from /app/packages/app/dist
```

That suggests the control-plane/log path can reach the node/container, but the saved bridge/public routes cannot reach the published runtime.

### New agent provisioning shows mixed worker/config failures

For a fresh native agent provision job, polling first reported:

```json
{
  "status": "pending",
  "result": {
    "error": "Sandbox health check timed out",
    "status": "error",
    "cloudAgentId": "<agent-id>"
  },
  "error": "Sandbox health check timed out",
  "attempts": 1,
  "maxAttempts": 3
}
```

The final state became:

```json
{
  "status": "failed",
  "result": {
    "error": "Sandbox health check timed out",
    "status": "error",
    "cloudAgentId": "<agent-id>"
  },
  "error": "ELIZA_KMS_BACKEND=steward requires steward.{baseUrl, tokenProvider}",
  "attempts": 3,
  "maxAttempts": 3
}
```

The agent record then has:

```json
{
  "status": "error",
  "databaseStatus": "ready",
  "bridgeUrl": null,
  "errorMessage": "Provisioning permanently failed after 3 attempts: ELIZA_KMS_BACKEND=steward requires steward.{baseUrl, tokenProvider}"
}
```

This looks like multiple provisioning workers or retries with inconsistent runtime env/config: one attempt reaches Docker health checking, another dies during managed API-key/KMS work.

### Route/API sanity checks

The mounted native routes are agent-based, not instances-based:

- `GET /api/v1/eliza/agents` -> 200
- `GET /api/compat/agents` -> 200
- `GET /api/v1/instances` -> 404
- `GET /api/v1/eliza/instances` -> 404
- `GET /api/instances` -> 404

`GET /api/health` returns 200, but `GET /api/health/operational` returns `degraded` with a `steward_platform.configured: false` check.

## Source observations

Relevant current code paths:

- `packages/cloud-shared/src/lib/services/managed-eliza-config.ts` creates a managed per-agent API key during environment preparation (`prepareManagedElizaBaseEnvironment`). That is the KMS-touching path before Docker launch.
- `packages/security/src/kms/index.ts` defaults non-local/non-test KMS to `steward`; it only falls back to local if `ELIZA_LOCAL_ROOT_KEY` is present. Otherwise it throws `ELIZA_KMS_BACKEND=steward requires steward.{baseUrl, tokenProvider}`.
- `packages/cloud-shared/src/lib/services/docker-sandbox-provider.ts` sets `ELIZA_PORT` and `PORT` to the agent port, sets `BRIDGE_PORT`, and publishes both allocated host ports to the same container `PORT`:
  - `-p ${bridgePort}:${PORT}`
  - `-p ${webUiPort}:${PORT}`
- `docker-sandbox-provider.ts` health checks `http://127.0.0.1:${bridgePort}/api/health` and `http://127.0.0.1:${webUiPort}/` from the Docker host.
- `packages/scripts/cloud/admin/daemons/agent-router.ts` resolves public subdomain routing to `${host}:${webUiPort}`, preferring `headscale_ip` and otherwise falling back to the bridge URL host.

Given the live symptoms, the likely boundaries are:

1. At least one production provisioning worker is missing valid KMS config (`ELIZA_KMS_BACKEND=local` + persistent `ELIZA_LOCAL_ROOT_KEY`, or a real Steward KMS config/token provider).
2. The Docker host dynamic ports / agent-router / firewall path is not consistently reachable from public ingress or Cloud API bridge calls. Affected records observed during testing had no `headscale_ip`, so the current route depends on public host + dynamic ports being reachable.

## Expected behavior

- A provisioning worker with invalid KMS config should report unhealthy and avoid claiming jobs, instead of consuming retries.
- A native agent should not be left as `running` if Cloud's bridge endpoint and public subdomain cannot reach it.
- A successful provision should produce a reachable bridge/public route, or fail with one clear actionable provisioning error.

## Suggested next checks / fixes

- Verify all production provisioning-worker instances use the same env and no stale workers are still claiming jobs.
- Explicitly configure KMS on the provisioning worker host(s): either `ELIZA_KMS_BACKEND=local` with a persistent `ELIZA_LOCAL_ROOT_KEY`, or wire real Steward KMS `baseUrl`/`tokenProvider` into `createKmsClient` before using `ELIZA_KMS_BACKEND=steward`.
- Verify Hetzner firewall/security groups/Nginx allow the dynamic port ranges used by Docker sandboxes (`BRIDGE_PORT_MIN..MAX`, `WEBUI_PORT_MIN..MAX`) from the routing layer, or switch the router/bridge path to a stable internal route.
- If Headscale is intended to be the route source, ensure containers register and persist `headscale_ip`.
- Surface the health timeout diagnostics already collected by `docker-sandbox-provider.ts` into the job result or an admin-visible field, so operators do not need sidecar logs to see `docker port`, `docker inspect`, and container logs.
- Consider adding a provisioning-worker startup preflight for KMS, Docker node reachability, and routing config. If any required dependency is missing, fail the worker health check instead of claiming jobs.
