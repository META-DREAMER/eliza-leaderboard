A live production audit of the provisioning pipeline (2026-07-29) found **agent deletion is failing 100% of the time**, and has been for days. This is customer-visible and accelerating.

Over the last 7 days: **554 failed jobs vs 153 completed** (78% failure rate).

## 1. `agent_delete` is completely broken — 160/160 failures, one identical cause

Every failed `agent_delete` job in the window carries the same error:

```
value.toISOString is not a function
```

- 160 failures, all identical, most recent **2026-07-28 18:03 UTC** (still current).
- All of them exhausted `attempts >= max_attempts` — so each one also burned the full retry budget.
- Consequence: **37 agents are stuck in `deletion_failed`**, up from 5 five days ago, and accelerating: **17 of them in the last 24 hours alone**.
- Customers who ask to delete an agent get a failure, the agent stays, and it keeps occupying node capacity.

`value.toISOString is not a function` is Drizzle's timestamp serializer receiving a **string where a `Date` is expected** — the same class as the cache/JSON round-trip defect fixed in #16859/#16860 for `resolveSharedAgent`.

One concrete candidate worth checking first (not yet proven to be the site): `prepareAgentBackupInsertData` (`packages/cloud/shared/src/db/repositories/agent-sandboxes.ts`) does

```ts
const createdAt = data.created_at ?? new Date();
// ...
created_at: createdAt,
```

`??` only guards `null`/`undefined` — a value that already crossed a JSON boundary as an ISO **string** passes straight through into the timestamp column. The 4 non-restart `agent_snapshot` failures in the same window are literally `Failed query: insert into "agent_sandbox_backups" (...)`, which is that insert.

## 2. `agent_snapshot`: 386 failures, 381 of them not the job's fault

```
Job interrupted by worker restart 2 times - max attempts reached   (381)
Failed query: insert into "agent_sandbox_backups" ...              (4)
Job timed out 2 times - max attempts reached                       (1)
```

The worker keeps restarting mid-snapshot, and **each restart consumes an attempt**. Two restarts exhaust `max_attempts` and the job is marked permanently failed — even though nothing about the job itself failed. A restart is an infrastructure event, not a job defect, and should not spend the job's retry budget (the codebase already has the shape for this: `retryLaterWithoutIncrementingAttempts`).

Why the worker restarts so often is the second half of this: it is consistent with the heap abort in #17154 and with the unbounded source-side snapshot capture in #17172 §1 (a large agent's capture is materialized entirely in the worker's heap).

| eliza-core-prod-3 | 24 | **25** |
| eliza-core-prod-4 | 24 | 24 |
| eliza-core-prod-5 | 24 | 24 |
| eliza-core-prod-6 | 24 | 24 |

prod-3 is **over** its declared capacity, and every robot is full, so new work is spilling onto autoscaled cloud nodes (3 × 4 running). 15:Tf05,## Summary

`markStuckProvisioningWithoutActiveJobAsError` exempts only two job types, but **four** job types legitimately hold a row in `provisioning`. A `agent_wake` or `agent_resume` that takes longer than 10 minutes — while still well inside its **own 15-minute cold-boot budget** — has its sandbox flipped to terminal `error` mid-flight, and the container can then be reaped out from under the still-running job.

This is not hypothetical. It is the mechanism behind **19 of the 44 agents stranded on 2026-07-13** (RCA in #17162): those 19 carry exactly the message this predicate writes.

## The defect

`packages/cloud/shared/src/db/repositories/agent-sandboxes.ts:747` writes:

> `Agent was stuck in provisioning state with no active provisioning job.`

and 13 lines below, `:760`, decides who is exempt:

```sql
AND ${jobs.type} IN ('agent_provision', 'agent_restart')
```

The same two-type predicate appears three times in that file (`:360`, `:760`, `:1040`).

But `provisioning` is also owned by wake and resume:

- `eliza-sandbox.ts` `executeResume` → `this.provision(...)`
- `eliza-sandbox.ts` `executeWake` → `this.provision(...)` (two call sites)

and `provision()` takes the row to `status: 'provisioning'` via `trySetProvisioning`.

Both types are declared **cold boot** with a 15-minute budget (`provisioning-jobs.ts`: `AGENT_RESUME` / `AGENT_WAKE` in `COLD_BOOT_JOB_TYPES`, `COLD_BOOT_STALE_JOB_THRESHOLD_MS = 15 * 60 * 1000`), while the sweeper cutoff is **10 minutes** (`packages/cloud/api/cron/cleanup-stuck-provisioning/route.ts`, `STUCK_THRESHOLD_MINUTES = 10`, fired every 5 min).

So the window `10 min < elapsed < 15 min` is a legitimate cold boot that the sweeper treats as abandoned.

## Why it is worse than a bad status

`error` is in `TERMINAL_SANDBOX_STATUSES`, and the orphan reconciler reaps a terminal-status container with **no age grace**. So the container the wake/resume just created is `docker rm`'d while its job is still running — the agent is destroyed mid-boot, and the row is left terminal with no retry.

## Prior art in this same predicate

`agent_restart` was added to this exact `IN (...)` list precisely because a warm-claim restart legitimately owns a `provisioning` row and was being flipped to `error`. That fix was correct — it just stopped one type short of the other two that do the same thing. The route's own doc comment states the intended rule as *"no jobs row in ('pending','in_progress')"*, with **no** type filter at all, which is further evidence the narrow list is an oversight rather than a deliberate allow-list.

## Evidence it already fired

From the live prod audit in #17162 (2026-07-13, 04:00–18:00 UTC): 44 dedicated agents in terminal `error` across 42 orgs, of which **19** carry `Agent was stuck in provisioning state with no active provisioning job` — the string written at `agent-sandboxes.ts:747`. 37 of those orgs had no other running agent.

## Acceptance criteria

- [ ] A job type that can legitimately own a `provisioning` row is never treated as abandoned by the sweeper. Prefer importing the same `COLD_BOOT_JOB_TYPES` constant the daemon uses, so the two lists cannot drift apart again (the drift is the bug; a second hand-maintained list would reproduce it).
- [ ] The sweeper threshold is not shorter than the longest cold-boot budget it can observe — today 10 min vs 15 min.
- [ ] All three occurrences of the predicate (`:360`, `:760`, `:1040`) move together, or share one source.
- [ ] A regression test pins that a `provisioning` row owned by an in-flight `agent_wake`/`agent_resume` past the sweeper cutoff is **not** flipped to `error`.
- [ ] Recovery for rows already stranded by this path is considered separately (#17162 tracks the 44).

## 1. Orphan reconciler reaps live warm-claimed customer containers — `high`

`packages/cloud/shared/src/lib/services/docker-node-workloads.ts:87-91`

The orphan diff keys a container on the id embedded in its **name**. A warm-pool container keeps the name it was born with, which carries the **pool** row's id — and that pool row is deleted at claim time. So after a claim, the live customer container maps to an id with no DB row, and the sweep classifies it `no_db_row` and force-removes it.

This hits **every agent created through the warm-pool fast path** — the default happy path. The agent goes unreachable mid-conversation while its row still says `running` with a `bridge_url` pointing at a dead container; the heartbeat only flips it to `disconnected` after the 120s grace, and for non-`dedicated-always` tiers it never self-heals. It is logged as a routine `Reaped orphan container … reason: no_db_row`, so it reads as correct behaviour in the logs.

What has spared production so far is that the reconciler is gated off by default (`ORPHAN_RECONCILER_ENABLED`, `provisioning-worker.ts:223`). **Arming it on an environment with warm pool enabled would delete live customer containers.** Worth a comment on the flag saying so until it is fixed.

Fix direction: resolve keys against `agent_sandboxes.container_name = 'agent-' || key`, or OR-in `warm_claim_source_pool_id IN (keys)` which `claimWarmContainer` already persists. Add a container-age grace on the `no_db_row` branch as defence in depth.

## 2. The cold-boot job budget is shorter than the provision path it is supposed to cover — `high`

`provisioning-jobs.ts:877` (`COLD_BOOT_STALE_JOB_THRESHOLD_MS = 900_000`), leaf budgets in `docker-sandbox-provider.ts:524/533/545/550/553`

The stale-job threshold is 15 minutes. The sum of the leaf SSH timeouts on the **single** provision path is ~19.8 minutes. A dedicated agent on a slow node — cold registry pull, slow SSH, a `docker pull` heading for its 300s cap — crosses 15 minutes of wall clock while perfectly healthy.

The daemon then **re-claims its own still-running job**, and the first act of the retry is to force-remove the container the first attempt just booted and delete its headscale node. This one refines #17215/#17231 rather than duplicating it. Raising the *sweeper* threshold does not help here — the job budget itself is below the real worst case, so the job dies before the sweeper is even relevant.

Fix direction: a renewable lease. Have the executing daemon periodically bump `started_at` (or a dedicated `heartbeat_at` that `recoverStaleJobs`, `jobs.ts:675-687`, keys on) so a still-running job is never re-claimed. Raising the constant alone just moves the cliff.

21:T1333,## P4 multiplayer coordination: group-room primitive in the Discord connector

Multiple humans + multiple agents in one room currently produce three structural failures: two agents answering the same human message, agents replying to superseded ("stale") human edges, and bot-to-bot reply loops. The Sol+Vera coordination protocol solved this behaviorally; this PR productizes it as a **runtime primitive** in `plugins/plugin-discord`, opt-in via `DISCORD_GROUP_COORDINATION_ENABLED` (default **off** — zero behavior change for existing deployments).

**Scope note:** deliberately does NOT touch outbound DM participant registration (#17167, @nubs's lane).

### What it does

New module `group-coordination.ts`, wired into `MessageManager.handleMessage` + the gateway `messageCreate` listener:

1. **One active speaker per human edge.** Before committing a model turn, an agent must win a durable *speaker lease* keyed `(channelId, edgeMessageId)`. The lease row id uses `stringToUuid` (agent-**independent**, unlike `createUniqueUuid`) so all agents sharing a coordination store contend on the same row. The claim is the adapter's existing atomic `onConflictDoNothing` insert followed by a read-back — the read-back decides the winner, both racers converge on the same holder. No CAS, no advisory locks, no new schema.
2. **Safe expiry/reclaim.** Leases carry `expiresAt`. A crashed holder's edge is reclaimed at **generation+1** (another atomic unique-row insert; expired rows are never mutated). A revived stale holder fails `verifySpeakerLease` (expired / superseded / not-holder) and **aborts before the third-party send** and before persisting any reply.
3. **Latest-human-edge-wins.** The gateway records each human (non-bot) message as the channel's edge. A claimed turn superseded by a newer human edge aborts at claim time *and* again pre-send. Explicit addressing (mention/reply-to-bot) overrides staleness — explicitly addressed work is never dropped — and a coalesced batch containing the latest edge stays current, so bursts coalesce per policy without dropping addressed work.
4. **Bot-to-bot loop prevention.** Bot messages never advance the human edge. A bot-authored message earns a reply only when it explicitly addresses this bot AND the per-channel consecutive bot-reply budget (`DISCORD_BOT_REPLY_BUDGET`, default 1, reset on every human message) is not exhausted. Two mutually-mentioning bots structurally stall after the budget until a human speaks.
5. **Auditable receipts.** Every decision (lease-claim won/lost/reclaimed/renewed, stale-edge abort, lost-lease abort, bot-loop suppression) persists a row in `discord_coordination_receipts` scoped to the room, with edge id, outcome, generation, and holder.

Retry/redelivery cannot double-send: the lease claim is idempotent per holder ("renewed"), and the existing durable-turn machine (#16696 lineage) reconciles a redelivery to REPLIED from the persisted reply memory.

# Background

## What does this PR do?

Introduces the **one typed composer-bridge contract** (`eliza.native-composer/v1`) so an iOS / Android / desktop shell can push content INTO the chat composer and drive it, and the renderer can report the composer's state back — without coupling to the #16200 UI monolith.

- **`contract.ts`** — two versioned discriminated-union logs: `ComposerOperation` (native → renderer: `text.insert`/`text.set`, `attachment.add`/`remove`, `reply.set`/`clear`, `mention.add`, `send`, `cancel`, `focus.set`, `voice.handoff`) and `ComposerEvent` (renderer → native: `draft.changed`, `send.result`, `focus.changed`, `voice.state`). Applying an op returns a typed **`DispatchResult`** (`applied` / `duplicate` / `deferred` / `rejected{reason}`) — **never a bare boolean**. Attachment sources are media-store vocabulary only (`inline` / `data-url` / `remote` / `stored`) — **there is no file-id variant, so a second file store is structurally unrepresentable**.
- **`decode.ts`** — strict boundary decoder. Every field of an untrusted op/attachment is validated; a malformed frame yields a typed `{ok:false,error}` (error-policy **J3**), never a throw on per-op input and never a fabricated default. Structurally rejects any second-store shape (an unknown attachment `source`, e.g. `file-id`, is refused).
- **`attachments.ts`** — normalizes a native attachment into the **existing content-addressed store's** vocabulary: `inline`/`data-url` → a `data:` URL the existing outgoing pipeline (`api/media-runtime.ts` → `persistAttachmentUrlIfInline`) persists to `${STATE_DIR}/media/<sha256>` on send; `remote` → an http(s) URL flagged for the existing server-side SSRF-guarded rehost; `stored` → an `/api/media/<hash>` passthrough. First-line private-host guard; the server's DNS-pinned SSRF guard (`packages/core/src/network`) remains authoritative. **No new store, no file IDs.**
- **`reduce.ts`** — the state machine / behavioral spec: `opId` idempotency (duplicate native callback = no-op), offline-send deferral + reconnect replay, cancellation (`send` vs `draft` scope), and permission/limit enforcement.
- **`client.ts`** — the renderer-side bridge client: decode → reduce → emit events; `serialize()`/`hydrate()` preserve the draft + idempotency ledger + offline queue across app backgrounding, window reload, and reconnect. Malformed native input degrades to `rejected: "invalid-input"` — one bad frame never tears down a live composer.

# Risks

Low by construction and off by default in effect: the budget's default ceiling is the shared canonical restorable limit, so it refuses exactly what the downstream consumer would already have rejected — a capture that succeeds today and is restorable still succeeds. The behavior change is *where* the refusal happens (in the producer, before the heap is spent) rather than *what* is refused.

# Background

## What does this PR do?

Cloud's restorable-size check is strictly **downstream** of the agent having already assembled and serialized the whole payload. It bounds what Cloud *retains*; it never bounds what the agent's own heap burns getting there. `createAgentSnapshot` ran its five captures concurrently with **no size awareness at all**:

- file capture reads a file and base64-encodes it — ~2.33× the file size transiently (Buffer + base64 string), ~1.33× durably;
- the **media** set has no include predicate whatsoever, so the whole content-addressed store is base64'd into the manifest;
- `stat.size` was already read and never compared to anything.

So a large agent can exhaust its container mid-capture. The memory watchdog then force-restarts it, and the lifecycle sites that snapshot before **upgrade / shutdown / sleep** silently degrade to a stale or missing backup — the failure this issue is about, one layer earlier than the Cloud fix.

Adds a produce-side budget:

- charged **as bytes are produced**, so an over-budget capture is refused at the first byte past the line instead of after everything is resident;
- file entries are refused from the **declared `stat` size before the read** — charging afterwards is charging after the allocation;
- a file-count ceiling mirroring the hydration-side cap;
- an optional `AbortSignal`, threaded through the directory walk so a cancelled capture stops descending;
- a typed `AgentSnapshotBudgetExceededError`, so "this state is too large to snapshot" is distinguishable from a transport/disk failure (the former is deterministic; retrying identical state cannot help).

## What kind of change is this?

Bug fix (source-process memory safety on the snapshot path).

# Background

## What does this PR do?

**A barge-in silently erased the exchange from the agent's memory.**

`bridgeSharedMessageStream` persisted a turn **only** on the model stream's
`finish` part. Any interruption before that — a voice **barge-in** cancelling
the SSE consumer, a client disconnect, or an upstream stream drop — unwound the
stream without writing anything, so the user's utterance never reached
`saveSharedRuntimeHistory`.

Voice and text chat read the **same** shared-runtime history for a room. So the
human spoke, heard the agent start answering, interrupted — and both the
question and the partial answer vanished from the transcript that text chat and
the next voice turn read back. Barge-in is the signature voice interaction, so
the most natural way to use voice was the way that lost your data.

This persists the turn on the interrupt paths too:

- the user's utterance is **always** kept (it was really said);
- any partial reply is kept as an assistant turn flagged `interrupted: true`, so
  later context knows it is a fragment, not a finished thought — honest context
  instead of either amnesia or a fabricated-complete reply;
- a **persist-once** guard shared with the `finish` path means a completion
  racing an interrupt cannot double-write;
- a failed recovery write is logged, never masked.

## What kind of change is this?

Bug fix (non-breaking).

# Documentation changes needed?

No. The behaviour change is described in code comments at the persistence seam.

## Root cause

`RESOLVE_REQUEST` used plugin-local error classes while the live `ApprovalService` throws the distinct classes exported by `@elizaos/agent`. Duplicate or concurrent decisions could therefore escape as uncaught errors. More importantly, treating `approved` as completed could suppress execution after a crash before dispatch, while retrying an `executing` row could duplicate an external side effect after a crash following dispatch.

## Repair

- import and recognize the exact error constructors from both queue implementations; forged lookalike errors still propagate
- require `byId` and the execution-transition methods before any decision mutation
- treat `approved` as a durable outbox row that can be claimed after a pre-dispatch crash
- use `markExecuting` as the atomic at-most-once dispatch claim
- treat only `done` as completed success
- surface `executing` as `APPROVAL_EXECUTION_OUTCOME_UNKNOWN` and never retry it blindly
- re-read after compare-and-swap races so approve/approve and approve/reject races preserve the single winning decision

# Background

## What does this PR do?

- **Failure A (attacker-timed mute).** A dexscreener price listing appearing on a spam token (fake liquidity) on the SAME tick as a real crash in priced holdings read as a coverage flip and re-baselined the whole total — the crash notification was swallowed, falsifying the #17039 PR-body invariant that a spam airdrop can never mute a concurrent material move.
- **Failure B (permanent mute via flap).** A coverage bit flapping priced↔unpriced on one dust position re-baselined the whole total EVERY tick, so slow material drift on the honestly-priced holdings never accumulated — the watcher was permanently muted, with no signal above debug.

The fix records per-position USD values in the baseline alongside the coverage bits (same key set, validator-enforced congruence). On a flip, the comparison excises ONLY the flipped positions from both totals:

- a material move in the residual (consistently-priced) holdings still notifies;
- an immaterial residual re-baselines just the flipped contribution, so the anchor keeps accumulating drift;
- three consecutive silent flip re-baselines escalate via `runtime.reportError("WalletBalanceDelta.coverageFlap", …)` → `RECENT_ERRORS`, so a flapping feed is a visible systemic problem instead of a silent debug loop.

- the failing tests differ run-to-run (18:03 → a vitest test, 19:25 → core-runtime green, 20:49 → typecheck dead) — the moving-target signature of a runner resource crash, not a code failure

## Fix

`run-turbo.mjs` now pipes turbo output through a signature scanner and retries the whole invocation **once** when a task died with `-1073741502` — the Turbo cache makes the retry resume from the crashed task, so completed work is not repeated. The retry is:

- **loud** — announced on stderr with the crash code and attempt count, so a deterministic failure can never hide behind it;
- **narrow** — only that exact failure signature; an ordinary task failure is never retried;
- **bounded** — one retry, then the original exit code propagates;
- **Windows-only** by default (`RUN_TURBO_NO_INIT_CRASH_RETRY=1` disables; the tests force the loop cross-platform via `RUN_TURBO_FORCE_INIT_CRASH_RETRY`).

Piped (not inherited) stdio is safe here because run-turbo already forces `--ui=stream --log-order=stream`, so turbo's output shape does not depend on TTY detection.

- ordinary failure without the signature → never retried (1 attempt)
