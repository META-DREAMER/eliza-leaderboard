14:T3331,# 🔄 Migrate packages/client to leverage @elizaos/api-client

## 📋 Summary

We have a new `@elizaos/api-client` package that provides a type-safe, service-oriented API client for ElizaOS. We need to migrate `packages/client` to heavily leverage this new package instead of its current custom API implementation. This migration will improve type safety, reduce code duplication, and provide better error handling.

## 🎯 Goals

- **Primary**: Replace the current monolithic API client (`src/lib/api.ts`) with `@elizaos/api-client`
- **Secondary**: Maintain 100% backward compatibility during migration
- **Tertiary**: Preserve existing React Query patterns and WebSocket integration
- **Quality**: Improve type safety and reduce code duplication

## 📊 Current State Analysis

### Current Implementation
- **Location**: `packages/client/src/lib/api.ts` (610+ lines of custom API code)
- **Pattern**: Custom `fetcher` function with manual endpoint definitions
- **Auth**: localStorage-based API key with `X-API-KEY` header
- **Error Handling**: Custom error handling with status code mapping
- **State Management**: React Query for caching and optimistic updates

### Most Used API Endpoints
1. **Agent Management**: `getAgents()`, `getAgent()`, `startAgent()`, `stopAgent()`
2. **Messaging**: `getChannelMessages()`, `postMessageToChannel()`, `getServers()`
3. **Memory/Logs**: `getAgentMemories()`, `getAgentLogs()`
4. **Media**: `uploadAgentMedia()`, `ttsStream()`, `transcribeAudio()`

### Integration Points
- **React Query Hooks**: `hooks/use-query-hooks.ts` (complex polling and caching)
- **WebSocket Manager**: `lib/socketio-manager.ts` (real-time updates)
- **Connection Context**: `context/ConnectionContext.tsx` (connection state)
- **File Upload**: `hooks/use-file-upload.ts` (media handling)

import { ElizaClient, ApiClientConfig } from '@elizaos/api-client';

export function createApiClientConfig(): ApiClientConfig {
  const getLocalStorageApiKey = () => \`eliza-api-key-\${window.location.origin}\`;
  const apiKey = localStorage.getItem(getLocalStorageApiKey());
  
  return {
    baseUrl: window.location.origin,
    apiKey: apiKey || undefined,
    timeout: 30000,
    headers: {
      'Accept': 'application/json',
    }
  };
}

export function createElizaClient(): ElizaClient {
  return ElizaClient.create(createApiClientConfig());
}

import { connectionStatusActions } from '../context/ConnectionContext';

export function handleApiError(error: unknown): never {
  if (error instanceof ApiError) {
    // Map new API errors to old error handling patterns
    if (error.status === 401) {
      connectionStatusActions.setUnauthorized(error.message);
    }
    // Add other status code mappings as needed
    throw new Error(error.message);
  }
  throw error;
}

18:Tb0d,# Add ELIZA_UI_ENABLE environment variable to control web UI in production

## Problem

elizaOS currently serves the web UI to anyone who can reach the server. While there's `ELIZA_SERVER_AUTH_TOKEN` for API endpoints, the web interface itself is wide open. In production deployments, this creates an unnecessary attack surface.

## Solution

Added `ELIZA_UI_ENABLE` environment variable with sensible defaults:
- **Development**: UI enabled by default
- **Production**: UI disabled by default
- **Override**: Set `ELIZA_UI_ENABLE=true/false`

When disabled, the web UI returns a standard HTTP 403 Forbidden error, but all API endpoints continue to work normally.

## Implementation

~20 lines in `packages/server/src/index.ts`:

1. Check `NODE_ENV` and `ELIZA_UI_ENABLE` to determine UI status
2. Conditionally serve static files only when UI is enabled
3. Replace SPA fallback with 403 response when UI is disabled
4. Update startup logging to clearly show UI status

## Testing

```bash
# Development (UI enabled)
bun start

# Production (UI disabled)  
NODE_ENV=production bun start

# Force enable in production
NODE_ENV=production ELIZA_UI_ENABLE=true bun start

# Force disable in development
ELIZA_UI_ENABLE=false bun start
```

When UI is disabled:
- `http://localhost:3000` → HTTP 403 Forbidden  
- `http://localhost:3000/api/server/ping` → Still works fine

## Test Coverage

Added tests:
- **Unit tests**: Environment variable parsing and default behaviours (development vs production)
- **Integration tests**: Server configuration impact and HTTP response handling
- **Security validation**: API functionality preservation when UI disabled

`bun test packages/server/src/__tests__/ui-disable-feature.test.ts`

25 tests passing, including both new tests and existing functionality verification.

## Justification

I'm working on scripting prod deploys and wanted a straighforward way to shut the UI off, but keep API open. I've purposely kept the API authentication (`ELIZA_SERVER_AUTH_TOKEN`) separate from this UI disable feature to minimise any clashes. 


## ⚠️ Desktop App Compatibility

Any remote deploy breaks the desktop anyway, as it's a wrapper to an iframe polling localhost:3000. 

In future iterations of the desktop app, with the correct plumbing, it could:

1. **Explicitly override**: `ELIZA_UI_ENABLE=true elizaos start`
2. **Environment file**: Add `ELIZA_UI_ENABLE=true` to `.env`
3. **Startup script**: Desktop app launcher can set the environment variable

(I'd be happy to help with this!)

## Backward compatibility

Should be fully backward compatible - no breaking changes, development experience stays the same. Only affects deployments that explicitly set `NODE_ENV=production`.
