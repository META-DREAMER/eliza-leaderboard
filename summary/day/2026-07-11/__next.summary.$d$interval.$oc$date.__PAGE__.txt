6:T8c1,## Problem

`computeEffectiveMaxTokens` currently applies:

`Math.max(request.max_tokens, 4096)`

to every model classified as using reasoning tokens. Both pass-through and SDK paths send that raised value upstream.

A client requesting `max_tokens:512` therefore authorizes an upstream ceiling of 4096 without any response field or header indicating that the request was changed.

The controlled Gemma/GLM latency run discovered this because direct requests used 512 while the gateway silently sent 4096, invalidating the original comparison.

## Why this is delicate

The floor was intentionally introduced by #8189/#8486 to prevent reasoning models from consuming a low budget entirely in hidden reasoning and returning an empty but billed answer. It must not simply be deleted.

Nevertheless, silently increasing an explicit caller ceiling is an API-contract and money-integrity problem: it can permit more generation, reservation, and spend than the caller requested.

## Required decision

Choose and document one safe contract:

1. Preserve an explicit caller cap; only apply a default floor when the field is absent.
2. Reject a reasoning-enabled request whose cap is too small with a clear 4xx.
3. Permit a low cap when reasoning is explicitly disabled.
4. Introduce explicit answer-vs-reasoning budget semantics.

Whichever contract is selected, expose requested and effective values in bounded telemetry and ensure billing admission uses the same effective value sent upstream.

## Acceptance

- An explicit output ceiling is never silently increased.
- Low-budget reasoning requests cannot regress to misleading `finish_reason:"stop"` with empty billed content.
- GLM-4.7 with `reasoning_effort:"none"` can use a genuinely small budget.
- Streaming and non-streaming routes behave consistently.
- Reservations and final billing are tested against the exact provider-facing budget.

9:Tc11,Sibling to #16021 (which fixed the *create*-path orphan). The **edit** path (`DocumentService.updateDocument`) has a strictly worse, non-atomic failure mode: an embed-time failure during re-fragmentation **destroys the document's existing, working fragments** and leaves the parent row showing the new content with **zero fragments** — data loss on edit, not just an orphan on create.

## Root cause

`packages/core/src/features/documents/service.ts` `updateDocument` performs a destructive re-fragmentation in this order:

1. `runtime.updateMemory(...)` — overwrites the parent `DOCUMENT` row with the **new** content/metadata.
2. Deletes **every existing fragment** for the document (`deleteMemory` in a loop over `relatedFragments`).
3. `splitAndCreateFragments(...)` then `processDocumentFragmentsBatched(fragments, { continueOnError: false })` — re-embeds and persists the new fragments.

Step 3 embeds via `addEmbeddingToMemory → useModel(TEXT_EMBEDDING)`. When the embedding backend is unavailable or returns a dimension/shape mismatch — the exact failure class #16021 addressed for the create path — `processDocumentFragmentsBatched` with `continueOnError: false` **throws**. But by then:

- the old (working) fragments are already **deleted**, and
- the parent row already holds the **new** text.

Result: the document is now **searchable-empty** (parent visible in lists, unmatchable in fragment/vector/BM25 search) **and the previously-working fragments are permanently gone**. The caller (`documents` action `handleEdit`, and `plugin-documents` PATCH route) gets a thrown error, but the store is already corrupted — there is no compensation and no snapshot to restore.

## Why #16021's fix does not cover this

#16021 / PR #16103 add all-or-nothing compensation to the **create** path (`addDocument`/`processDocument`): on embed failure the freshly-written parent row is rolled back. `updateDocument` is a separate method with a *mutating* sequence (overwrite parent + delete old fragments **before** the new embeds), so it needs a different, snapshot-based repair, not a parent-row delete.

## Acceptance

- An embed-time (or fragment-persist) failure during `updateDocument` must **not** leave the document with fewer fragments than it had before, and must **not** silently swap in the new content while dropping all fragments.
- Preferred: stage the new fragments first (embed + validate before any destructive delete/overwrite), and only swap parent content + delete-old + insert-new once the new fragments are known-good; on failure, the pre-edit state is preserved and a typed `ElizaError` propagates. (A snapshot/restore of the old fragments + parent content is an acceptable alternative.)
- Surface the failure via `runtime.reportError("DocumentService.updateDocument", …)` consistent with #16021.
- Add fails-before/passes-after coverage: embed-down during re-fragmentation, fragment-persist throw, and a healthy edit (must still re-fragment). Prove old fragments survive on failure.

elizaOS constructs a stable prompt-cache routing key, and `plugin-elizacloud` emits it, but the Cloud chat gateway silently drops it before Cerebras.

Current path:

1. `packages/core/src/runtime/provider-cache-plan.ts` builds `v5:<prefixHash>` and places it in Cerebras provider options as both `promptCacheKey` and `prompt_cache_key`.

3. `packages/cloud/api/v1/chat/completions/route.ts` defines a separate `ChatRequest` that contains neither field.

## Existing implementation showing intended support

`packages/cloud/shared/src/lib/providers/types.ts` already declares `OpenAIChatRequest.prompt_cache_key`.

`packages/cloud/shared/src/lib/providers/vercel-ai-gateway.ts::mergeGatewayProviderOptions` already reads that field and maps it into Cerebras/eliza provider options.

The Cloud chat route’s duplicate request shape has diverged from that shared contract.

Cerebras now accepts an optional `prompt_cache_key` routing hint. Requests sharing a key are routed to the same prompt cache on a best-effort basis, improving cache-hit rate and Time to First Token for repeated stable prefixes.

This is particularly relevant to long-context agent/planner calls and GLM-4.7. Cerebras’s current supported-model list includes GLM-4.7, GPT-OSS 120B, and Qwen 3 235B; Gemma should not be claimed as benefiting without live evidence.

Automatic prefix caching still works without the field, so this is not an outage. The bug loses an explicit affinity hint under load and makes the already-implemented client cache plan ineffective through Eliza Cloud.

- Accept canonical `prompt_cache_key`.
- Accept `promptCacheKey` only as a backward-compatible client alias.
- Canonicalize to one provider-facing `prompt_cache_key`; do not send both forms upstream.
- Validate a nonempty string with maximum length 1024.
- Never log the raw key.
- Preserve the key through:
  - Cerebras pass-through streaming.
  - AI-SDK streaming.
  - AI-SDK non-streaming.
- Merge cache provider options without overwriting Anthropic reasoning, web-search, or other provider options.
- Keep requests without a key byte-for-byte unchanged.
- Verify that the platform Cerebras account has `prompt_cache_key` routing enabled before production rollout; if unavailable, use an explicit capability/rollout decision rather than silently dropping caller intent.

Both present identically as "newest jobs row is old", so the check **cannot tell a real split from a quiet env**.

## Live evidence (staging, right now)

`eliza-provisioning-worker` logs a **level=`error`** line every ~5 min infra sweep:

```
[provisioning-worker] DB LIVENESS: the jobs table on switchback.proxy.rlwy.net:49295 looks abandoned —
the newest row is 40.1h old, threshold 24h (CONTAINERS_DB_LIVENESS_MAX_AGE_HOURS). ...
```

But the daemon is on the **correct** DB — that same DB has **4030 jobs** (newest 07-10 07:39), staging is just idle (no one provisioned in 40h). So this is a **false alarm firing ~288×/day at error level** for a healthy daemon.

The current escape hatch — the message's own "if this env is intentionally idle, raise the threshold" — is a trap: raising `CONTAINERS_DB_LIVENESS_MAX_AGE_HOURS` to silence idle **also delays detection of a real split** (the exact #15160 failure the check exists for). # Background

## Root cause

Paired staging/direct evidence showed Cerebras responding in roughly 89–333 ms while the Cloud gateway could spend 2.45–3.11 seconds before the handler after idle. Privacy-safe unauthenticated probes reproduced two sequential Railway TCP Redis checks at 2.38–3.46 seconds without calling a model.

The two outer protective limiters were paying cross-cloud TCP setup before every chat turn. Independent review also found that a timed-out SocketRedis operation could resume after its 50 ms teardown bound and touch a successor connection's mutable reader/parser.

## What this PR changes

- moves the global 600/min flood backstop and chat 200/min gate to Cloudflare Rate Limiting bindings;
- preserves the exact organization inference limiter on Redis;
- hashes API-key/anonymous identifiers before using them as counter keys;
- batches carried Redis lease increments and TTL lookup into one pipeline exchange;
- makes SocketRedis reader/writer/parser state connection-local and protects publication with an ownership epoch;
- bounds teardown while ensuring timeout losers cannot read from, publish over, or close successor connections;
- starts independent input/output pricing reads concurrently and evicts the short-lived balance hint on central credit mutations;
- preserves Cerebras `promptCacheKey` when `reasoningEffort` also contributes provider options, with streaming and non-streaming regressions;
- preserves the inner 200/min chat limiter's headers while Hono unwinds through the outer 600/min limiter, for both allowed and denied responses; and
- repairs/restores process-global Redis mocks used by the complete Cloud lane.

It does **not** change provider/model selection, billing rates, response streaming bytes, database schema, or production deployment state. Native rate-limit metadata is intentionally more truthful than before.

## Problem

`DocumentService.updateDocument` re-fragments the document destructively and **out of order**:

1. `runtime.updateMemory(...)` — overwrites the parent `DOCUMENT` row with the **new** content/metadata.
2. Deletes **every existing fragment** for the document.
3. `splitAndCreateFragments(...)` then `processDocumentFragmentsBatched(fragments, { continueOnError: false })` — re-embeds + persists the new fragments.

Step 3 embeds via `addEmbeddingToMemory → useModel(TEXT_EMBEDDING)`. On an **embed-time failure** (embedding model down, dimension/shape mismatch — the same failure class #16021 fixed for the *create* path) the batched/serial path throws with `continueOnError:false`. But by then the old (working) fragments are **already deleted** and the parent row already holds the **new** text. Result: the document is left **searchable-empty** (visible in lists, unmatchable in fragment/vector/BM25 search) **and its previously-working fragments are permanently gone**. Data loss on edit — strictly worse than the create-path orphan, and not covered by #16021/#16103 (a separate method with a mutating sequence).

## Fix

Make the edit **atomic with respect to the document's fragments**: split + embed the new fragments **in memory first**, and only once every new fragment is known-good mutate the store.

- New private `embedFragmentsInPlace(fragments)` populates `fragment.embedding` with **no persistence**, mirroring `processDocumentFragmentsBatched`'s embed semantics exactly (one `TEXT_EMBEDDING_BATCH` round-trip when a batch model is registered, with the same count/shape/empty-vector validation; else serial per-fragment). It **throws** on any embed failure.
- `updateDocument` now: split → `embedFragmentsInPlace` → **(commit)** `updateMemory` (overwrite parent) → delete old fragments → persist the already-embedded new fragments. The embed stage runs **before a single destructive write**, so a failure preserves the pre-edit state (original parent content + original fragments intact).
- Failure is surfaced via `runtime.reportError("DocumentService.updateDocument", …)` and a typed `ElizaError` (`code: DOCUMENT_UPDATE_FAILED`, `severity: fatal`), consistent with #16021.

The persist step for the (already-embedded) new fragments no longer re-hits the embedding backend, so the commit phase cannot fail at embed time.

## Tests

New `service-update-atomic.test.ts` drives the real `updateDocument` path with `createMockRuntime` (no live model/DB), backed by an in-memory fragment store so the effect of a failed edit on persisted fragments is observable:

1. **embed-down during re-fragmentation** — embedding throws for the new content → the two pre-existing fragments **survive** (store still has exactly them), the parent row still reflects the **original** content, `reportError("DocumentService.updateDocument")` fires, and a typed `DOCUMENT_UPDATE_FAILED` `ElizaError` propagates.
2. **healthy edit** — embedding works → new content is re-fragmented + re-embedded, old fragments replaced, parent row shows the new content.

## Problem

`DocumentService.addDocument` (via `processDocument`) writes the parent `DOCUMENT` row (`createMemory(memoryWithScope, DOCUMENTS_TABLE)`) **before** `processFragmentsSynchronously`. That fragment pipeline **counts and logs** per-chunk embedding failures rather than throwing — it returns `savedCount`, not an error. So on an embed-time failure (embedding model down, dimension mismatch) every chunk fails, `savedCount === 0`, and the already-written parent row is left as an **orphaned zero-fragment DOCUMENT**: visible in document lists, unmatchable in fragment search.

`#16002` fixed the *validation-time* case (pre-write hoist), but the embed-time orphan remained. The `addDocument` catch only logged+rethrew with no compensating `deleteMemory`.

## Fix

- `processFragmentsSynchronously` now returns `{ savedCount, failedCount, chunkCount }` (new exported `FragmentProcessingResult`) so the caller can distinguish a **legitimately empty** document (`chunkCount === 0`, nothing to embed) from an **embed-time failure** (`chunkCount > 0 && savedCount === 0`).
- `processDocument` compensates: when chunks existed but nothing embedded, it deletes the parent row and throws a typed `ElizaError` (`code: DOCUMENT_EMBED_FAILED`, `severity: fatal`), restoring all-or-nothing document ingestion. A **hard throw** inside fragment processing gets the same rollback.
- The failure is surfaced via `runtime.reportError("DocumentService.addDocument", …)` (agent/owner escalation path, J7). A failed *compensating* delete is itself reported so a surviving orphan stays observable. The compensating delete is best-effort and never masks the original failure.

Preferred fix from the issue (compensating `deleteMemory` of the parent row) — restores all-or-nothing at the document level rather than relying on a later reconciliation sweep.

## Tests

New `service-orphan-compensation.test.ts` drives the real ingestion path with `createMockRuntime` (no live model/DB):

2. **fragment-store-throw** — embedding succeeds but the fragment `createMemory` throws → same rollback + report.
3. **healthy** — a document that embeds ≥1 fragment is **never** rolled back.

`computeEffectiveMaxTokens` currently applies:

`Math.max(request.max_tokens, 4096)`

to every model classified as using reasoning tokens. Both pass-through and SDK paths send that raised value upstream.

A client requesting `max_tokens:512` therefore authorizes an upstream ceiling of 4096 without any response field or header indicating that the request was changed.

The controlled Gemma/GLM latency run discovered this because direct requests used 512 while the gateway silently sent 4096, invalidating the original comparison.

## Why this is delicate

The floor was intentionally introduced by #8189/#8486 to prevent reasoning models from consuming a low budget entirely in hidden reasoning and returning an empty but billed answer. It must not simply be deleted.

Nevertheless, silently increasing an explicit caller ceiling is an API-contract and money-integrity problem: it can permit more generation, reservation, and spend than the caller requested.

## Required decision

Choose and document one safe contract:

1. Preserve an explicit caller cap; only apply a default floor when the field is absent.
2. Reject a reasoning-enabled request whose cap is too small with a clear 4xx.
3. Permit a low cap when reasoning is explicitly disabled.
4. Introduce explicit answer-vs-reasoning budget semantics.

Whichever contract is selected, expose requested and effective values in bounded telemetry and ensure billing admission uses the same effective value sent upstream.

The **edit** path (`DocumentService.updateDocument`) has a strictly worse, non-atomic failure mode: an embed-time failure during re-fragmentation **destroys the document's existing, working fragments** and leaves the parent row showing the new content with **zero fragments** — data loss on edit, not just an orphan on create.

## Root cause

`packages/core/src/features/documents/service.ts` `updateDocument` performs a destructive re-fragmentation in this order:

1. `runtime.updateMemory(...)` — overwrites the parent `DOCUMENT` row with the **new** content/metadata.
2. Deletes **every existing fragment** for the document (`deleteMemory` in a loop over `relatedFragments`).
3. `splitAndCreateFragments(...)` then `processDocumentFragmentsBatched(fragments, { continueOnError: false })` — re-embeds and persists the new fragments.

Step 3 embeds via `addEmbeddingToMemory → useModel(TEXT_EMBEDDING)`. When the embedding backend is unavailable or returns a dimension/shape mismatch — the exact failure class #16021 addressed for the create path — `processDocumentFragmentsBatched` with `continueOnError: false` **throws**. But by then:

- the old (working) fragments are already **deleted**, and
- the parent row already holds the **new** text.

Result: the document is now **searchable-empty** (parent visible in lists, unmatchable in fragment/vector/BM25 search) **and the previously-working fragments are permanently gone**. The caller (`documents` action `handleEdit`, and `plugin-documents` PATCH route) gets a thrown error, but the store is already corrupted — there is no compensation and no snapshot to restore.

## Why #16021's fix does not cover this

#16021 / PR #16103 add all-or-nothing compensation to the **create** path (`addDocument`/`processDocument`): on embed failure the freshly-written parent row is rolled back. `updateDocument` is a separate method with a *mutating* sequence (overwrite parent + delete old fragments **before** the new embeds), so it needs a different, snapshot-based repair, not a parent-row delete.

## Acceptance

- An embed-time (or fragment-persist) failure during `updateDocument` must **not** leave the document with fewer fragments than it had before, and must **not** silently swap in the new content while dropping all fragments.
- Preferred: stage the new fragments first (embed + validate before any destructive delete/overwrite), and only swap parent content + delete-old + insert-new once the new fragments are known-good; on failure, the pre-edit state is preserved and a typed `ElizaError` propagates. (A snapshot/restore of the old fragments + parent content is an acceptable alternative.)
- Surface the failure via `runtime.reportError("DocumentService.updateDocument", …)` consistent with #16021.
- Add fails-before/passes-after coverage: embed-down during re-fragmentation, fragment-persist throw, and a healthy edit (must still re-fragment). Prove old fragments survive on failure.


But the daemon is on the **correct** DB — that same DB has **4030 jobs** (newest 07-10 07:39), staging is just idle (no one provisioned in 40h). So this is a **false alarm firing ~288×/day at error level** for a healthy daemon.

The current escape hatch — the message's own "if this env is intentionally idle, raise the threshold" — is a trap: raising `CONTAINERS_DB_LIVENESS_MAX_AGE_HOURS` to silence idle **also delays detection of a real split** (the exact #15160 failure the check exists for). Give the check a signal that survives idle: something the cloud-api writes to the **same** database on a fixed cadence regardless of provisioning traffic, and have the daemon read *that* for the split decision.

This separates idle from split deterministically and lets the loud warning stay loud because it only fires on a real problem.
- **Interim (self-contained):** stop emitting the loud error every sweep — warn once on transition-to-stale, then throttle re-emission (e.g. hourly) — so an idle env doesn't produce 288 error events/day while the deeper fix lands.

## Problem

`DocumentService.updateDocument` re-fragments the document destructively and **out of order**:

1. `runtime.updateMemory(...)` — overwrites the parent `DOCUMENT` row with the **new** content/metadata.
2. Deletes **every existing fragment** for the document.
3. `splitAndCreateFragments(...)` then `processDocumentFragmentsBatched(fragments, { continueOnError: false })` — re-embeds + persists the new fragments.

Step 3 embeds via `addEmbeddingToMemory → useModel(TEXT_EMBEDDING)`. On an **embed-time failure** (embedding model down, dimension/shape mismatch — the same failure class #16021 fixed for the *create* path) the batched/serial path throws with `continueOnError:false`. But by then the old (working) fragments are **already deleted** and the parent row already holds the **new** text. Result: the document is left **searchable-empty** (visible in lists, unmatchable in fragment/vector/BM25 search) **and its previously-working fragments are permanently gone**. Data loss on edit — strictly worse than the create-path orphan, and not covered by #16021/#16103 (a separate method with a mutating sequence).

## Fix

Make the edit **atomic with respect to the document's fragments**: split + embed the new fragments **in memory first**, and only once every new fragment is known-good mutate the store.

- New private `embedFragmentsInPlace(fragments)` populates `fragment.embedding` with **no persistence**, mirroring `processDocumentFragmentsBatched`'s embed semantics exactly (one `TEXT_EMBEDDING_BATCH` round-trip when a batch model is registered, with the same count/shape/empty-vector validation; else serial per-fragment). It **throws** on any embed failure.
- `updateDocument` now: split → `embedFragmentsInPlace` → **(commit)** `updateMemory` (overwrite parent) → delete old fragments → persist the already-embedded new fragments. The embed stage runs **before a single destructive write**, so a failure preserves the pre-edit state (original parent content + original fragments intact).
- Failure is surfaced via `runtime.reportError("DocumentService.updateDocument", …)` and a typed `ElizaError` (`code: DOCUMENT_UPDATE_FAILED`, `severity: fatal`), consistent with #16021.

The persist step for the (already-embedded) new fragments no longer re-hits the embedding backend, so the commit phase cannot fail at embed time.

## Tests

New `service-update-atomic.test.ts` drives the real `updateDocument` path with `createMockRuntime` (no live model/DB), backed by an in-memory fragment store so the effect of a failed edit on persisted fragments is observable:

1. **embed-down during re-fragmentation** — embedding throws for the new content → the two pre-existing fragments **survive** (store still has exactly them), the parent row still reflects the **original** content, `reportError("DocumentService.updateDocument")` fires, and a typed `DOCUMENT_UPDATE_FAILED` `ElizaError` propagates.
2. **healthy edit** — embedding works → new content is re-fragmented + re-embedded, old fragments replaced, parent row shows the new content.

## Problem

`DocumentService.addDocument` (via `processDocument`) writes the parent `DOCUMENT` row (`createMemory(memoryWithScope, DOCUMENTS_TABLE)`) **before** `processFragmentsSynchronously`. That fragment pipeline **counts and logs** per-chunk embedding failures rather than throwing — it returns `savedCount`, not an error. So on an embed-time failure (embedding model down, dimension mismatch) every chunk fails, `savedCount === 0`, and the already-written parent row is left as an **orphaned zero-fragment DOCUMENT**: visible in document lists, unmatchable in fragment search.

`#16002` fixed the *validation-time* case (pre-write hoist), but the embed-time orphan remained. The `addDocument` catch only logged+rethrew with no compensating `deleteMemory`.

## Fix

- `processFragmentsSynchronously` now returns `{ savedCount, failedCount, chunkCount }` (new exported `FragmentProcessingResult`) so the caller can distinguish a **legitimately empty** document (`chunkCount === 0`, nothing to embed) from an **embed-time failure** (`chunkCount > 0 && savedCount === 0`).
- `processDocument` compensates: when chunks existed but nothing embedded, it deletes the parent row and throws a typed `ElizaError` (`code: DOCUMENT_EMBED_FAILED`, `severity: fatal`), restoring all-or-nothing document ingestion. A **hard throw** inside fragment processing gets the same rollback.
- The failure is surfaced via `runtime.reportError("DocumentService.addDocument", …)` (agent/owner escalation path, J7). A failed *compensating* delete is itself reported so a surviving orphan stays observable. The compensating delete is best-effort and never masks the original failure.

Preferred fix from the issue (compensating `deleteMemory` of the parent row) — restores all-or-nothing at the document level rather than relying on a later reconciliation sweep.

## Tests

New `service-orphan-compensation.test.ts` drives the real ingestion path with `createMockRuntime` (no live model/DB):

1. **embed-down** — every chunk's embedding throws → parent row is deleted, no fragments persisted, `reportError` fired with the documentId, and a typed `DOCUMENT_EMBED_FAILED` `ElizaError` propagates.
2. **fragment-store-throw** — embedding succeeds but the fragment `createMemory` throws → same rollback + report.
3. **healthy** — a document that embeds ≥1 fragment is **never** rolled back.
