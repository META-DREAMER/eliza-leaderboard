Overall summary API endpoints return 404 for dates with no repository activity:
- `/api/summaries/overall/day/2026-01-01.json` → 404 ❌
- `/api/summaries/overall/day/2026-01-02.json` → 200 ✅

## Expected Behavior

The API should return a summary for **every day the pipeline runs**, even if there's no activity:

```json
{
  "version": "1.0",
  "type": "overall",
  "interval": "day",
  "date": "2026-01-01",
  "generatedAt": "2026-01-02T00:00:00.000Z",
  "contentFormat": "markdown",
  "content": "No activity recorded for January 1, 2026."
}
```

## Root Cause

[`generateOverallSummaryForInterval()`](https://github.com/elizaOS/elizaos.github.io/blob/main/src/lib/pipelines/summarize/generateOverallSummary.ts#L70-L76) returns `null` when no repository summaries exist:

```typescript
const repoSummaries = await getAllRepoSummariesForInterval(interval);
if (repoSummaries.length === 0) {
  intervalLogger?.debug(
    `No repository summaries found for ${intervalType} of ${startDate}, skipping overall summary generation.`,
  );
  return null; // ← This causes the 404
}
```

## Evidence

```bash
# Jan 1 had ZERO activity (New Year's Day)
$ sqlite3 data/db.sqlite "SELECT COUNT(*) FROM raw_pull_requests WHERE DATE(created_at) = '2026-01-01';"
0

$ sqlite3 data/db.sqlite "SELECT COUNT(*) FROM raw_issues WHERE DATE(created_at) = '2026-01-01';"
0

# Database has monthly summary but NO daily summary
$ sqlite3 data/db.sqlite "SELECT date, interval_type, LENGTH(summary) FROM overall_summaries WHERE date = '2026-01-01';"
2026-01-01|month|4320
```

## Solution

Always generate a summary, even when `repoSummaries.length === 0`:

```typescript
const repoSummaries = await getAllRepoSummariesForInterval(interval);

// Generate summary even if no repo summaries exist
const summary = repoSummaries.length > 0
  ? await generateOverallSummary(
      repoSummaries,
      aiSummaryConfig,
      { startDate },
      intervalType as RepoIntervalType,
    )
  : `No activity recorded for ${intervalType} of ${startDate}.`;

if (\!summary) {
  intervalLogger?.debug(
    `Overall summary generation resulted in no content for ${startDate}, skipping storage.`,
  );
  return;
}

// Store and export the summary...
```

## Impact

- API consumers can't distinguish between "no data" and "endpoint not generated"
- 404s break API contract that promises daily summaries
- Inconsistent API behavior (some days exist, others don't)
- Downstream tools must handle unexpected 404s

## Design Philosophy

Per the API documentation:
> "404 responses indicate artifacts not yet published."

But this should mean "pipeline hasn't run yet", NOT "no activity that day". If the pipeline runs daily, every day should have a summary—even if it says "no activity."

# Background

## What does this PR do?

This PR makes the elizaOS Rust core **fully WASM-compatible**, enabling it to run in browsers and Node.js via WebAssembly. The existing Rust crate had WASM bindings but they were stubs - the `WasmAgentRuntime` was a placeholder that didn't actually wrap the real `AgentRuntime`.

The key challenge was that Rust's `async_trait` and many traits require `Send + Sync` bounds for thread-safety, but WASM is single-threaded and doesn't support these traits. This PR implements platform-aware macros and conditional compilation to provide the correct bounds for each target.

### Key Changes

#### 1. Platform-Aware Macros (`src/platform.rs`)

```rust
// Native: #[async_trait] (requires Send)
// WASM:   #[async_trait(?Send)] (no Send requirement)
platform_async_trait! {
    pub trait MyTrait { ... }
}

// Native: pub trait MyTrait: Send + Sync { ... }
// WASM:   pub trait MyTrait { ... }
define_platform_trait! {
    pub trait MyTrait { ... }
}
```

#### 2. Core Trait Migration

All core traits now compile for both targets:
- `ActionHandler`, `ProviderHandler`, `EvaluatorHandler`
- `DatabaseAdapter`, `Service`, `IAgentRuntime`
- Bootstrap traits: `Action`, `Provider`, `Evaluator`, `Service`

#### 3. Real WasmAgentRuntime

The `WasmAgentRuntime` now wraps the actual `AgentRuntime` using WASM-appropriate primitives:

```rust
pub struct WasmAgentRuntime {
    inner: Rc<RefCell<Option<AgentRuntime>>>,  // Not Arc - WASM is single-threaded
    character: RefCell<Character>,
    agent_id: UUID,
}
```

#### 4. Structured WASM Errors

Rich error objects for JavaScript consumers:

```rust
pub struct WasmError {
    pub code: String,      // "VALIDATION_ERROR", "RUNTIME_ERROR", etc.
    pub message: String,   // Human-readable message
    pub source: Option<String>,  // Field/component that caused error
}
```

#### 5. JavaScript Shims

Type-safe wrappers for JS callbacks:

Overall summary API endpoints return 404 for dates with no repository activity:
- `/api/summaries/overall/day/2026-01-01.json` → 404 ❌
- `/api/summaries/overall/day/2026-01-02.json` → 200 ✅

## Expected Behavior

The API should return a summary for **every day the pipeline runs**, even if there's no activity:

```json
{
  "version": "1.0",
  "type": "overall",
  "interval": "day",
  "date": "2026-01-01",
  "generatedAt": "2026-01-02T00:00:00.000Z",
  "contentFormat": "markdown",
  "content": "No activity recorded for January 1, 2026."
}
```

## Root Cause

[`generateOverallSummaryForInterval()`](https://github.com/elizaOS/elizaos.github.io/blob/main/src/lib/pipelines/summarize/generateOverallSummary.ts#L70-L76) returns `null` when no repository summaries exist:

```typescript
const repoSummaries = await getAllRepoSummariesForInterval(interval);
if (repoSummaries.length === 0) {
  intervalLogger?.debug(
    `No repository summaries found for ${intervalType} of ${startDate}, skipping overall summary generation.`,
  );
  return null; // ← This causes the 404
}
```

## Evidence

```bash
# Jan 1 had ZERO activity (New Year's Day)
$ sqlite3 data/db.sqlite "SELECT COUNT(*) FROM raw_pull_requests WHERE DATE(created_at) = '2026-01-01';"
0

$ sqlite3 data/db.sqlite "SELECT COUNT(*) FROM raw_issues WHERE DATE(created_at) = '2026-01-01';"
0

2026-01-01|month|4320
```

## Solution

Always generate a summary, even when `repoSummaries.length === 0`:

```typescript
const repoSummaries = await getAllRepoSummariesForInterval(interval);

// Generate summary even if no repo summaries exist
const summary = repoSummaries.length > 0
  ? await generateOverallSummary(
      repoSummaries,
      aiSummaryConfig,
      { startDate },
      intervalType as RepoIntervalType,
    )
  : `No activity recorded for ${intervalType} of ${startDate}.`;

if (\!summary) {
  intervalLogger?.debug(
    `Overall summary generation resulted in no content for ${startDate}, skipping storage.`,
  );
  return;
}

// Store and export the summary...
```

## Impact

- API consumers can't distinguish between "no data" and "endpoint not generated"
- 404s break API contract that promises daily summaries
- Inconsistent API behavior (some days exist, others don't)
- Downstream tools must handle unexpected 404s

## Design Philosophy

Per the API documentation:
> "404 responses indicate artifacts not yet published."

But this should mean "pipeline hasn't run yet", NOT "no activity that day". If the pipeline runs daily, every day should have a summary—even if it says "no activity."

## What does this PR do?

This PR makes the elizaOS Rust core **fully WASM-compatible**, enabling it to run in browsers and Node.js via WebAssembly. The existing Rust crate had WASM bindings but they were stubs - the `WasmAgentRuntime` was a placeholder that didn't actually wrap the real `AgentRuntime`.

The key challenge was that Rust's `async_trait` and many traits require `Send + Sync` bounds for thread-safety, but WASM is single-threaded and doesn't support these traits. This PR implements platform-aware macros and conditional compilation to provide the correct bounds for each target.

### Key Changes

#### 1. Platform-Aware Macros (`src/platform.rs`)

```rust
// Native: #[async_trait] (requires Send)
// WASM:   #[async_trait(?Send)] (no Send requirement)
platform_async_trait! {
    pub trait MyTrait { ... }
}

// Native: pub trait MyTrait: Send + Sync { ... }
// WASM:   pub trait MyTrait { ... }
define_platform_trait! {
    pub trait MyTrait { ... }
}
```

#### 2. Core Trait Migration

All core traits now compile for both targets:
- `ActionHandler`, `ProviderHandler`, `EvaluatorHandler`
- `DatabaseAdapter`, `Service`, `IAgentRuntime`

#### 3. Real WasmAgentRuntime

The `WasmAgentRuntime` now wraps the actual `AgentRuntime` using WASM-appropriate primitives:

pub struct WasmAgentRuntime {

#### 4. Structured WASM Errors

Rich error objects for JavaScript consumers:
