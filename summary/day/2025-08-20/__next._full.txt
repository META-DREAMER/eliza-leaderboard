### **Epic 1: Scenario Matrix Runner**

**Goal:** Create a robust CLI tool to execute a scenario multiple times across a matrix of different configurations.

* **Ticket 1.1:** [ELIZA-651](https://linear.app/eliza-labs/issue/ELIZA-651/design-and-implement-scenario-matrix-configuration)
  * **Task:** Define a clear and extensible YAML schema for the matrix configuration file (e.g., `matrix.scenario.yaml`).
  * **Acceptance Criteria:**
    * The schema must support defining a `base_scenario` path.
    * It must support a `runs_per_combination` integer.
    * It must include a `matrix` array where each item specifies a `parameter` (using dot-notation like `character.llm.model`) and a list of `values`.
    * Create TypeScript interfaces for this schema.
    * Implement a validation function using a library like Zod to provide clear errors on misconfiguration.
* **Ticket 1.2:** [ELIZA-652](https://linear.app/eliza-labs/issue/ELIZA-652/implement-elizaos-scenario-matrix-cli-command)
  * **Task:** Create the new top-level CLI command `elizaos scenario matrix <config_path>`.
  * **Acceptance Criteria:**
    * The command is registered in `packages/cli` using `yargs`.
    * It correctly parses the path to the matrix config file.
    * The command's main function should read, parse, and validate the specified config file.
* **Ticket 1.3:** [ELIZA-653](https://linear.app/eliza-labs/issue/ELIZA-653/develop-parameter-override-system)
  * **Task:** Implement the core logic that dynamically overrides parameters in the base scenario for each run.
  * **Acceptance Criteria:**
    * Create a utility that takes a loaded scenario object, a dot-notation path (e.g., `run[0].input`), and a value.
    * The utility must correctly set the value in the object, handling nested objects and array indices.
    * This function will be the engine that creates the unique scenario configurations for each matrix run.
* **Ticket 1.4:** [ELIZA-655](https://linear.app/eliza-labs/issue/ELIZA-655/implement-run-orchestration-and-isolation)
  * **Task:** Build the main execution loop that runs all generated scenario combinations.
  * **Acceptance Criteria:**
    * The command must generate a Cartesian product of all matrix parameters.
    * It must loop through each unique combination the specified number of times (`runs_per_combination`).
    * For each run, it must programmatically invoke the existing scenario runner logic with the overridden in-memory scenario object.
    * **Crucially**, ensure each run is completely isolated by cleaning up any generated artifacts (e.g., test databases, temporary files) between executions.

# Background

## What does this PR do?

This PR implements asynchronous embedding generation to prevent blocking the message processing pipeline. Previously, generating embeddings for messages would block the runtime for 500ms+ per API call, delaying message responses. Now embeddings are queued and processed in the background by a dedicated service.

Key changes:
- Added `queueEmbeddingGeneration` method to `AgentRuntime` that emits events instead of blocking
- Created `EmbeddingGenerationService` that listens for `EMBEDDING_QUEUED` events and processes them asynchronously
- Implemented a priority queue system (high/normal/low) for embedding generation
- Added comprehensive test coverage for both the runtime method and service

## What kind of change is this?

**Features** (non-breaking change which adds functionality) + **Improvements** (performance enhancement to existing features)
