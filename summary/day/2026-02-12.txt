14:Te73,### Problem Statement
Currently, ElizaOS scenario testing lacks the ability to mock internal agent runtime calls (particularly LLM interactions) when testing via the API client. This makes it difficult to create deterministic tests for agent behavior and workflows.

### Current Limitations
- Global function mocks only work for code executed in the same process
- No way to intercept `runtime.useModel` calls from the bootstrap plugin
- Agent behavior is non-deterministic due to real LLM calls
- Difficult to test specific agent decision paths and responses

### Why Different Approach Was Needed

The existing mocking system was designed for **code execution environments** (E2B sandbox and local `node -e` processes), where mocks are applied to the execution context. However, **agent testing** works differently:

- **E2B/Local Execution**: Code runs in isolated processes/sandboxes where global mocks can be applied
- **Agent Testing**: Agent runs as a service with API client interaction, requiring direct runtime method interception
- **Architecture Gap**: The bootstrap plugin calls `runtime.useModel` internally, which can't be mocked through the execution environment approach

This architectural difference necessitated a new approach that directly intercepts runtime methods rather than relying on execution context mocking.

### Proposed Solution: Runtime Method Mocking

We've implemented a new mocking approach that directly intercepts `IAgentRuntime` method calls:

#### Key Components

1. **MockEngine Enhancement**
   - Added `runtimeMethodMocks` to support mocking runtime methods
   - Priority system: `runtimeMethod` > `service` > `globalFunction`
   - Direct method replacement on the runtime instance

2. **Schema Updates**
   - Extended `MockSchema` to include `runtimeMethod: z.string().optional()`
   - Supports mocking any `IAgentRuntime` method (e.g., `useModel`, `getService`)

3. **Conditional Matching**
   - Matcher functions can inspect method arguments
   - Example: `"return args[1] && args[1].prompt && args[1].prompt.includes('should respond')"`
   - Supports complex conditional logic for when to apply mocks

#### Usage Example

```yaml
setup:
  mocks:
    - runtimeMethod: "useModel"
      method: "useModel"
      when:
        matcher: "return args[1] && args[1].prompt && args[1].prompt.includes('should respond')"
      response: "<response><name>agent</name><reasoning>Mocked response</reasoning><action>RESPOND</action></response>"
```

#### Benefits

1. **Deterministic Testing**: Replace LLM calls with static responses
2. **Full Workflow Testing**: Test complete agent decision flows
3. **Conditional Mocking**: Apply mocks based on specific conditions
4. **Runtime Integration**: Works seamlessly with existing agent architecture
5. **Backward Compatibility**: Existing mocks continue to work

#### Implementation Steps

- MockEngine runtime method support
- Schema updates for runtimeMethod mocks
- Conditional matching with matcher functions
- Integration with scenario runner
- Basic useModel mocking working
- Add support for mocking other runtime methods (getService, etc.)
- Create comprehensive test scenarios
- Add documentation and examples
- Consider adding mock recording/replay capabilities

### Technical Details

The implementation works by:
1. Creating the `IAgentRuntime` instance in the scenario runner
2. Applying mocks directly to the runtime object before agent initialization
3. The bootstrap plugin receives the mocked runtime and uses the mocked methods
4. Mocks are reverted after scenario completion

## Summary
Add an evaluator that asserts on the number of agent/tool/action steps taken to complete a scenario step. This encourages concise trajectories and prevents thrashing.

- Assert against `max_steps`, `min_steps`, optional `target_steps`

3. Evaluator passes if within bounds and returns a clear message

## Schema Changes

```ts
const StepCountEvaluationSchema = BaseEvaluationSchema.extend({
  type: z.literal('step_count'),
  max_steps: z.number().optional(),
  min_steps: z.number().optional(),
  target_steps: z.number().optional(),
  // optional filter by action name prefix to scope counting
  action_prefix: z.string().optional(),
});
```

## Evaluation Implementation
Leverage the existing `TrajectoryContainsActionEvaluator` patterns.

```ts
class StepCountEvaluator implements Evaluator {
  async evaluate(params: EvaluationSchema, _runResult: ExecutionResult, runtime: AgentRuntime): Promise<EvaluationResult> {
    if (params.type !== 'step_count') throw new Error('Mismatched evaluator');
    try {
      const memories = await runtime.getMemories({
        tableName: 'messages', agentId: runtime.agentId, count: 200, unique: false,
      });
      const actionResults = memories.filter(m => m?.type === 'messages' && m.content?.type === 'action_result');
      const filtered = params.action_prefix
        ? actionResults.filter(m => (m.content?.actionName ?? '').startsWith(params.action_prefix!))
        : actionResults;
      const steps = filtered.length;

      const tooMany = params.max_steps != null && steps > params.max_steps;
      const tooFew = params.min_steps != null && steps < params.min_steps;
      const success = !(tooMany || tooFew);
      return {
        success,
        message: `Steps taken: ${steps} (min=${params.min_steps ?? '-'}, target=${params.target_steps ?? '-'}, max=${params.max_steps ?? '-'})`,
      };
    } catch (error: any) {
      return { success: false, message: `Step count evaluation failed: ${error.message ?? String(error)}` };
    }
  }
}
```

## Summary
Add an evaluator that runs the same step multiple times and asserts consistency over a chosen metric (response content, length, execution time, token counts). Useful for detecting non-determinism and regression in prompt/rules.

## Goals
- Re-run a step N times
- Compare result metrics across runs
- Allow tolerance configuration

## Acceptance Criteria
1. New evaluator type `consistency_check`
2. Supports metrics: `response_length` | `execution_time` | `token_count`
3. Configurable `runs` (>=2) and `tolerance` (absolute or percentage)
4. Consolidated pass/fail with clear variance message

## Schema Changes
Edit `packages/cli/src/commands/scenario/src/schema.ts`:

```ts
const ConsistencyEvaluationSchema = BaseEvaluationSchema.extend({
  type: z.literal('consistency_check'),
  runs: z.number().min(2),
  metric: z.enum(['response_length', 'execution_time', 'token_count']),
  tolerance: z.number().min(0), // if < 1 treat as proportion, else absolute
});
```

## Orchestration Changes
Add a helper to re-execute the current step within the selected environment provider without re-running the entire scenario:

- Expose a `runSingleStep(step, scenarioContext)` on providers that mirrors the logic in `run`, returning an `ExecutionResult`.
- In `EvaluationEngine`, when encountering `consistency_check`, call this helper to collect multiple `ExecutionResult`s for the same step.
- Fallback: If helper is not implemented, re-run `run([step])` via a shim.

## Evaluation Implementation

```ts
class ConsistencyEvaluator implements Evaluator {
  constructor(private rerunStep: (times: number) => Promise<ExecutionResult[]>) {}

  async evaluate(params: EvaluationSchema, runResult: ExecutionResult): Promise<EvaluationResult> {
    if (params.type !== 'consistency_check') throw new Error('Mismatched evaluator');

    const runs = await this.rerunStep(params.runs);
    const values = runs.map(r => {
      switch (params.metric) {
        case 'response_length': return r.stdout.length;
        case 'execution_time': return r.durationMs ?? 0;
        case 'token_count': {
          const llm = r.metrics?.llm ?? [];
          return llm.reduce((sum, m) => sum + (m.totalTokens ?? (m.promptTokens ?? 0) + (m.completionTokens ?? 0)), 0);
        }
      }
    });

    const min = Math.min(...values);
    const max = Math.max(...values);
    const spread = max - min;
    const baseline = values[0] || 1;
    const proportion = baseline ? spread / baseline : spread;
    const threshold = params.tolerance < 1 ? params.tolerance : params.tolerance / baseline;
    const success = proportion <= threshold;

    return {
      success,
      message: `Consistency ${success ? 'ok' : 'failed'} for ${params.metric}: min=${min}, max=${max}, spread=${spread}, tolerance=${params.tolerance}`,
    };
  }
}
```

Register in `EvaluationEngine` with a provider-specific `rerunStep` function wired from the scenario runner.

## Example Usage

```yaml
evaluations:
  - type: consistency_check
    runs: 3
    metric: execution_time
    tolerance: 0.2   # 20% spread allowed
```

## Tests
- Unit: evaluator math on synthetic values
- Integration: deterministic small prompt with low tolerance; non-deterministic with higher tolerance

## Notes
- This evaluator requires access to the step context. Implementation will pass a `rerunStep(times)` closure into the evaluator at construction time.

## Pricing Source
Add a small utility `packages/cli/src/commands/scenario/src/pricing.ts`:

```ts
export type ModelPricing = {
  inputPer1K: number;    // USD per 1000 input tokens
  outputPer1K: number;   // USD per 1000 output tokens
};

export const DEFAULT_MODEL_PRICING: Record<string, ModelPricing> = {
  TEXT_SMALL: { inputPer1K: 0.15, outputPer1K: 0.60 },
  TEXT_LARGE: { inputPer1K: 0.50, outputPer1K: 1.50 },
  OBJECT_SMALL: { inputPer1K: 0.50, outputPer1K: 1.50 },
};

export function getPricing(modelType: string, overrides?: Record<string, ModelPricing>): ModelPricing | null {
  const table = overrides ?? DEFAULT_MODEL_PRICING;
  return table[modelType] ?? null;
}
```

Allow overrides via `SCENARIO_MODEL_PRICING` env (JSON string) in a follow-up.

## Evaluation Implementation
Add to `EvaluationEngine`:

```ts
class LlmCostEvaluator implements Evaluator {
  async evaluate(params: EvaluationSchema, runResult: ExecutionResult): Promise<EvaluationResult> {
    if (params.type !== 'llm_cost') throw new Error('Mismatched evaluator');
    const llm = runResult.metrics?.llm ?? [];
    if (!llm.length) return { success: false, message: 'No LLM metrics found for cost calculation' };

    const pricingOverrides = process.env.SCENARIO_MODEL_PRICING ? JSON.parse(process.env.SCENARIO_MODEL_PRICING) : undefined;
    let total = 0;
    for (const m of llm) {
      const pricing = getPricing(m.modelType, pricingOverrides);
      if (!pricing) continue;
      const inTok = m.promptTokens ?? 0;
      const outTok = m.completionTokens ?? 0;
      total += (inTok / 1000) * pricing.inputPer1K + (outTok / 1000) * pricing.outputPer1K;
    }

    const success = total <= params.max_cost_usd;
    return { success, message: `Estimated cost: $${total.toFixed(4)} (limit $${params.max_cost_usd.toFixed(4)})` };
  }
}
```

```ts
      prompt: acc.prompt + (m.promptTokens ?? 0),
      completion: acc.completion + (m.completionTokens ?? 0),
      total: acc.total + (m.totalTokens ?? ((m.promptTokens ?? 0) + (m.completionTokens ?? 0))),
    }), { prompt: 0, completion: 0, total: 0 });

    const tooManyInput = params.max_input_tokens != null && totals.prompt > params.max_input_tokens;
    const tooManyOutput = params.max_output_tokens != null && totals.completion > params.max_output_tokens;
    const tooManyTotal = params.max_total_tokens != null && totals.total > params.max_total_tokens;

    const success = !(tooManyInput || tooManyOutput || tooManyTotal);
    return {
      success,
      message: `Tokens — input:${totals.prompt}, output:${totals.completion}, total:${totals.total}`,
    };
  }
}
```

Register in constructor:

```ts
this.register('token_count', new TokenCountEvaluator());
```

```yaml

    max_output_tokens: 1000
    max_total_tokens: 2500
```
